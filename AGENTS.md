# AGENTS.md

- Agent-first project: act autonomously, including commits and pushes. Block on a human only for expensive or hard-to-undo operations.
- When the user asks a question or for an opinion, answer and propose; implement after their go.
- Track all work in GitHub issues; reference the issue in commits. Issues are cheap and focused (one spec, one implementation, one fix), never umbrellas or checklists; order them with GitHub's "blocked by" dependencies; a commit that finishes one says "Closes #n". Outstanding work found anywhere becomes an issue, never just a note.
- Don't use harness memory systems; record durable knowledge here.
- Every instruction here must earn its tokens: cut prose that doesn't change agent behavior.
- No status disclaimers in docs ("currently", "early days", "coming next"); they go stale. Track status in issues.
- AGENTS.md is not README.md: project descriptions go in README.md; only agent instructions go here.
- Every source file starts with SPDX headers: `SPDX-FileCopyrightText: 2026 Maksym Motorny` (current year for new files) and `SPDX-License-Identifier: BSD-3-Clause`, in the file's comment syntax.
- Naming: product crate `volya-engine`, role sub-crates `volya-engine-<role>` in `crates/`, platform packages `platforms/<platform>` with crate `volya-engine-<platform>`, tools `tools/<tool>` with crate `volya-engine-<tool>` (except `xtask`) (see docs/architecture/README.md). Create a crate only when its code exists.
- Never open pull requests, issues or comments on other people's repositories; forks under the user's account are fine.
- Never add URL query parameters (`?…`) without the user's explicit approval.
- Follow docs/architecture/; update the document a decision belongs to when it changes.
- Verify how browsers and platforms behave (storage, caching, APIs) before relying on it, and say whether it's measured, documented, or believed. Before inventing a mechanism or a design, check how it's commonly done.
- Bazel builds and tests everything (docs/architecture/build.md): tasks are Bazel targets, operational commands `bazel run //tools/xtask -- <task>`. Cargo doesn't build the workspace; its manifests are crate_universe's input, and editors use `rust-project.json` (`bazel run @rules_rust//tools/rust_analyzer:gen_rust_project`).
- No shell scripts: project tasks live in `tools/xtask`. One exception: `tools/bazel`, Bazelisk's bootstrap wrapper, which only computes the installer's fingerprint and runs Bazel.
- Run shell pipelines with `set -o pipefail`.
- Never wait on a process with `pgrep -f` of a pattern that also matches the waiting shell's own command line; wait on a PID or a file. Stop every background loop you start before finishing.
- Live at head: run `bazel run //tools/xtask -- update` when starting a chunk of work; fix what it breaks rather than pinning.
- Run `bazel test //:checks` (fast static checks) before every push; it must pass.
- Performance and memory budgets are measured and reported, never release gates: ship working features, file an issue for any regression past a budget, and optimise separately.
- Iteration speed first: before reporting done, run `bazel test //...` (cached: it reruns only what the change affects; unit and game-data tests, the static checks, and the smoke, platform, render and import suites on Chrome), then the manual suites the change touches by name (`bazel test //tests/browser:<suite>_<target>`, dashes as underscores); a drawing change runs the render suite of its area, cheapest first: `render` (synthetic scenes), `render-screens`, `render-level`, `draw-calls` (`VOLYA_DUMP_DIR` keeps their frames, `VOLYA_COMPARE_DIR` holds them to an earlier run's). A change to the game's behaviour runs the game suite of its area: `game-startup` (logos, title menu, touchpad, the import), `game-level` (New Game, start view, objects, lights, effects, frame times), `game-input` (keyboard, touch, gamepad, pointer lock, inventory), `game-screens` (save, load, options, rebinding, settings read back), `game-memory` (heap, quit to menu, relaunch, repeat New Games, hidden page, the diagnostic log). The iPhone only for changes to the page, input, audio, storage or the WebGL 2 path; all game-data tests only for changes to loading or formats; every suite on both targets (`bazel test //tests/browser:chrome //tests/browser:iphone`) only for changes crossing page and engine, or on demand. Land in small steps; measurement tooling is its own step.
- The game data's extraction format is `EXTRACTION_FORMAT` in `tools/gog-extract/src/main.rs`: bump it only when the extracted layout or contents change (a bump extracts 6 GB again; nothing else does).
- On this machine the game data is `VOLYA_GOG_INSTALLER=~/<downloads folder>`, set in the main checkout's `user.bazelrc`, which every worktree reads. A test that skipped for missing data proved nothing: don't report it as passed.
- Avoid GitHub CI whenever possible (cost); all testing runs locally.
- Deploy (`bazel run //tools/xtask -- deploy`) after each landed feature, i.e. a change to what the app does or shows; spec, docs and test-only commits don't need one.
- This machine's memory is shared by every agent: run `bazel run //tools/xtask -- wait-memory` before any build or test (it returns once macOS memory pressure is normal, at least 20% free; browser suites call it themselves), and only one agent uses the iOS Simulator at a time (the iPhone suites hold a lock). Exceeding memory caused a kernel panic (2026-11-25).
- Subagents commit in their own worktree and push only its branch, never main, and don't switch it to other commits; the orchestrating session lands their branches on main from the main checkout after `//:checks`.
- Clean up a finished worktree once its work is merged: in it run `bazel clean --expunge` (deletes its output base and stops its Bazel server), then `git worktree remove` it; leave worktrees with uncommitted changes. Stop any container, Wine run or background loop it started. Never delete entries of Bazel's shared caches by hand (live output bases point into them); its GC removes unused ones.
- Tests and investigations are silent on this machine: Chrome muted (`--mute-audio`), suite pages send live audio through a gain of 0 (`harness.js`; the iOS Simulator can't be routed to no device), the original run with Wine's audio driver disabled in its prefix. Never change the Mac's system volume.
- Work by the priorities in docs/roadmap.md; record roadmap decisions there, not here. The roadmap stays high-level: decisions and priorities, no issue numbers or work queues.
- Exactly two browser targets; don't add more. Desktop Chrome (headless, on WebGL 2, where fidelity is judged) is the default, and the only place drawing is tested: nothing draws natively (the Mac is not a target); checks that draw are Rust run in the engine worker (the render suites), the rest stay native tests. The iOS Simulator (textures transcoded to ETC2) for changes to the page, input, audio or storage. WebKit drawing is checked by the user's use of the deployed app; a drawing bug Chrome can't reproduce gets a one-off look in desktop Safari, not a target. The user is not QA: never ask them to run tests or checks; real-device feedback comes only from them using the deployed app.
- Any UI change updates the UX audit board (`platforms/web/static/ux-audit/states.js`, deployed at `/volya-engine/ux-audit/`) in the same commit: every state of the app's own interface is on it, sections and states in the order a user meets them. The user audits designs there instead of clicking through the app.
- Interface text is plain, concise and professional, and says only what's known and what applies where it's shown: no text meant for another device or browser, no guessed causes or unbacked advice, no facts that vary with the user's game data (sizes, versions) unless read from that data.
- Interface design: no information the user doesn't need there, including repeats of what they just saw; tell them about blockers before they invest effort; never interrupt them on their behalf (e.g. reloading the app), offer the action instead.
- Build features compatible with the original game. A temporary stub that unblocks dependent work is fine when an issue tracks replacing it. Any permanent deviation from the original, or addition on top of it, goes to the user first. What is fatal in the original is fatal here too (`App::fatal`), never recovered from.
- Web build must keep functional parity between mobile and desktop browsers; every feature ships with both input paths (touch and keyboard/mouse/gamepad) and is tested on both.
- Dependencies must be permissively licensed (no copyleft, including LGPL/MPL). One exception (the user's): copyleft tools may run as build tools of the Wine image (e.g. bison, m4), never linked into or shipped with anything.
- Patching third-party code: a permissively licensed project's patch is a file in the repo that Bazel applies (as `third_party/inno/`); a copyleft project's patch lives only on a branch of a fork under the user's account, fetched at a pinned commit, so the repo stays permissive.
- Never use or derive from leaked X-Ray source or its forks (e.g. OpenXRay).
- Knowledge of the original game's formats and behavior enters only through docs/clean-room.md; never from memory.
- Name code after the approved specs' own words, never the original program's internal terms.
- The orchestrating session and implementers stay clean: never read the dirty workspace (`~/Sources/mmotorny/volya-dirty/`) or dirty agents' findings; dirty agents report only a verdict and a path.
- Never commit game assets, including test fixtures; tests needing game data skip when it's absent.
