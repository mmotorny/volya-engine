# Architecture

Decisions and the reasons behind them. Update this file when a decision changes.

## Crates

Split only where a split buys compile-time isolation, a compiler-enforced boundary, or reuse outside the product; subsystems (AI, physics, A-Life, UI) are modules, not crates.

| Package | Contents | Why separate |
|---|---|---|
| `crates/volya-engine` | The platform-free product: composes the role crates into one engine (screens such as the startup sequence and the title menu, driven by a clock and input, producing scenes the presenter turns into draw lists), defines the traits platforms implement (storage, input, audio, surface, clock), and hosts the test interface. | The product as one library every platform ships. |
| `crates/volya-engine-core` | Platform-free engine: VFS trait, native backend and game-archive tree, configuration loading, audio mixing, simulation (world, A-Life, AI, physics, scripting), save/load. | Deterministic and headless-testable; cannot reach rendering or any platform. |
| `crates/volya-engine-render` | `wgpu` renderer: textures, video textures, draw lists to frames. | Keeps `wgpu` rebuilds off the simulation's edit loop; keeps rendering out of simulation. |
| `crates/volya-engine-formats` | Parsers and decoders over `Read + Seek` or bytes, no I/O: the game's own formats (from clean specs) and the public ones it uses (DDS, Ogg Vorbis, Ogg Theora). | Reused by tools; one home for clean-room provenance and game-data tests. |
| `crates/volya-engine-script` | The script runtime: the vendored LuaJIT 1.0.3 interpreter (C), our C library for wasm32, a thin safe Rust API, and the loader of the game's script files over core's VFS (see Scripts). | Keeps the C build (build.rs, LLVM clang for wasm) and all `unsafe` FFI in one place; one home for the third-party source and its provenance. |
| `crates/volya-engine-installer` | GOG offline installer reader and extractor (Inno Setup headers, GOG parts). | Unrelated to the game; runs in the importer worker; has its own CLI. |
| `platforms/web` | Crate `volya-engine-web` (wasm `cdylib`: entry point, OPFS, workers, `OffscreenCanvas`) plus `static/` (HTML, JS, CSS, icons). Only package using `web-sys`. | Platform packaging and APIs; compiles to nothing elsewhere. |
| `platforms/ios` (later) | Crate `volya-engine-ios` (`staticlib`) plus the Xcode project / Swift shell. | Same, for iOS. VR decided when it starts (visionOS may sit with iOS). |

Dependencies point one way: `volya-engine-<platform>` → `volya-engine` → role crates (`render` → `core` → `formats`; `script`; `installer`). Everything in `crates/` builds and tests natively. Tooling lives in `tools/` (`devserver`, `xtask`).

## Threading: one engine thread, in a worker

The engine (VFS, simulation, scripting, A-Life, physics, rendering) runs on a single thread inside a dedicated Web Worker.

- **Single-threaded simulation** matches the original X-Ray engine's observable behavior and update order, keeps simulation deterministic, and fits comfortably within the reference device's budget (iPhone 17 Pro Max).
- **In a worker** because OPFS `FileSystemSyncAccessHandle` is worker-only. Synchronous reads let archive readers be plain `Read + Seek` Rust.
- **Rendering** uses WebGPU on an `OffscreenCanvas` transferred from the main thread. Verified on iPhone 17 Pro Max (WebKit, via Chrome for iOS) and desktop Chrome (#11). Where the browser gives no WebGPU adapter, wgpu's WebGL 2 backend draws on the same canvas instead (#113, decided by the user): detected by the failed adapter request (asked for before any surface, since a canvas keeps the first kind of context it gives), not by the absence of `navigator.gpu` (the iOS Simulator's WebKit has it and gives no adapter; measured). The Simulator draws through WebGL 2 on its GPU (measured: ETC2 and ASTC, no BC); WebGPU checks need the real device. `status` reports the backend (`webgpu`, `webgl2`) and how BC textures reach the GPU (`bc`, `etc2`, `rgba8`).
  - Two wasm builds (#186): `pkg/` without wgpu's GL backend, `pkg-webgl/` with it (the `webgl` feature of `volya-engine-web`, `volya-engine` and `volya-engine-render`); the GL backend is most of the difference (release, gzipped: 1.17 MB against 2.04 MB, measured). The engine worker asks for a WebGPU adapter as the engine does and loads the matching build (`static/wasm-build.js`), the WebGL one (which draws through WebGPU too) where the WebGPU one can't be had (offline, once a browser gained WebGPU with only the WebGL build kept); the import worker loads the build the engine worker runs, named in the page's messages. So a browser downloads and keeps only the one it runs (Hosting). `status` reports the build (`build`). `cargo xtask web` makes both, one after the other in the same target directory.
  - WebGL 2's vertex programs have no storage buffers and it has no base-vertex draws, so on such a device (`Renderer::compat`: no storage buffers) the world reads its per-draw records from an RGBA32F texture (9 texels a draw, 64 draws a row; a variant of `world.wgsl` made by `world::world_source`), indexed by instance (wgpu emulates the first instance on GL with a uniform), and its index ranges are rebased at upload: each range a draw uses is written with the draw's first vertex added, ranges one after another per index buffer (a range two draws use from different first vertices twice), the objects' 32-bit where they pass 16 bits; the draws then start at vertex 0. wgpu's GL backend keeps every written byte in CPU memory (the wasm heap) until it knows the submission finished (wgpu-hal's GLES buffers with emulated mapping are a `Vec`, read in its source), and a WebGL sync object never signals in the frame it was issued (documented, WebGL 2 specification), so an upload made in one go passes through the heap whole: pieces are submitted one by one, and a level's geometry is uploaded before the level shows, a few pieces per task turn with two frames between (`Renderer::begin_geometry`, `GeometryUpload::step`, `Presenter::prepare_world`, #184; below). The WebGPU path is unchanged. Native tests run the world's tests both ways on Metal (`set_compat`) and translate the programs to GLSL ES 3.00 with naga as wgpu's GL backend does.
  - BC textures on a GPU without BC are transcoded at run time to ETC2 (`volya-engine-formats::etc2`, our encoder from the Khronos Data Format Specification: BC1 to RGB8, or RGB8A1 when the texture has cut-out texels; BC2 and BC3 to RGBA8 with EAC alpha); with neither BC nor ETC2 they are decoded to RGBA8. ETC2 over ASTC: ETC2 takes BC's memory (127 MiB of textures for `l01_escape` either way, measured natively), ASTC 4×4 64 % more (BC1's 4 bits a texel become 8) for a difference only visible magnified, and ASTC 6×6 is worse than ETC2 and slower (measured with astcenc on the level's textures, #113). The encoder fits every texel's colour whatever its alpha (the game's alpha is often data: light maps keep a lighting term there).
  - The encoder works from a BC block's four colours, judges ETC1 tables and T/H candidates along the grey axis (a modifier moves every channel alike, so one sum per colour decides; as etcpak's table search on luma differences), tries planar only where the best unquantized plane could win and T/H only where the error is large and the colours differ in hue, and walks T/H distances outwards while they improve (QuickETC2, Nah 2020) (#183). For `l01_escape`'s 429 BC textures (218 megapixels): 4.1 s natively, single-threaded (13 s before), and 6.8–7.0 s in the iOS Simulator's wasm (35 s before), measured; PSNR against the BC texels within 0.11 dB of the previous encoder's per kind (`volya-engine/tests/transcode.rs`). The release build compiles `volya-engine-formats` at `opt-level = 3`, about twice as fast as "s" (measured natively). Transcoding stays on the engine worker, decided by the user: transcode workers only if the encoder alone leaves a load well above a few seconds.
  - Transcoding is still too slow for a frame, so where WebGL 2 draws (on a GPU with BC too, for the geometry below) a New Game's loading waits under `st_loading_textures` once its work is done (`App::set_prepare_textures`, our addition), while the platform prepares the level's textures: about 30 ms of them per task turn, so frames run between and the loading screen keeps drawing (a turn per texture cost 5 s of waiting, measured); each is transcoded (without BC) and uploaded, and the presenter takes it at the world's upload (`Renderer::add_prepared`). Once the level is made the loading waits again, under its last caption, while the platform uploads the level's geometry (`App::world_to_prepare`; the level's clocks wait with it, `LevelScreen::wait`). In the iOS Simulator the preparation takes 10.9 s: 6.9 s transcoding, 2.4 s uploading, 0.3 s reading, 0.3 s for the geometry, and the first caption to the level's first frame 12.9 s (measured). Nothing is stored: every load transcodes again, decided by the user: the WebGL 2 path serves tests first, and stored transcodings would take as much storage as the BC textures (133 MB for the first level, 2.05 GB for all 5,087 of the game's BC textures; measured), too much on a phone on top of the game. Other textures (the menus') are transcoded when first drawn. On this path the wasm heap is 107–110 MiB after the first New Game in the Simulator (two runs; 148 MiB with the geometry uploaded at once; 98 MiB in Chrome on WebGPU; measured).
  - The page sends the canvas's CSS size and `devicePixelRatio` on start and on change; the worker sizes the canvas and surface in device pixels. The frame loop runs in the worker on `requestAnimationFrame` (a 60 Hz timer where workers lack it) and presents only when something changed.
  - The game draws at its video mode (`vid_mode`, docs/behavior/options-screens.md section 9), not at the canvas's size: menus and 3D go to an offscreen frame of that size, which is drawn into the canvas scaled to fit with its aspect kept, black around it (#49). The resolution list offers the canvas's own size and the common 4:3, 5:4, 16:10 and 16:9 sizes that fit it (browsers expose no display modes); the page counts as windowed, so a stored mode not in the list is used as it is. Pointer positions are taken relative to the drawn picture.
  - With neither WebGPU nor WebGL 2 the engine still starts, without graphics; `status` and the page's status line say why.
  - A level's static world uploads `level.geom`'s vertex and index buffers as stored; packed attributes are decoded in the vertex programs (WebGPU vertex formats reproduce the spec's decoding). Its draws are recorded once into a render bundle replayed every frame; what depends on the camera (near/far shader variants, size culling) is decided per draw in the shaders from per-draw data. No CPU copy of the geometry is kept: its loading stage reads only the buffers' layout, the spatial stage checks the draws' indices reading them a piece at a time, and the presenter streams the file to the GPU in pieces of at most 2 MiB with `Queue::write_buffer` (which, unlike a buffer mapped at creation, copies nothing into the wasm heap on the web, per wgpu 30's WebGPU backend source). The wasm heap never shrinks, so a load's peak is the page's for good: about 98 MiB after the first and the second New Game in headless Chrome (measured, #79). The 57 MB of `l01_escape`'s geometry is therefore read in the first world frame, under the loading image, with the textures: that frame takes about 100 ms native in release and 330–354 ms in the dev profile (measured); spreading it over frames is #114. Scripted shader definitions (Lua) are not run: the specified effect of each script the level uses is implemented directly.
  - A level's spawned objects (docs/behavior/level-objects.md) are loaded in its loading stages: the switch pass under `st_server_connecting`, the model files under `st_client_spawning`, their surfaces with the level's under `st_loading_textures`, their light inputs (rays against the collision world, taken converged at once) under `st_client_synchronising`. Each model file is read once and shared by every object showing it; its vertices are quantized as the first renderer stores them (16 bytes: `s16` position, `u8` normal, `s16` texture coordinate) into one vertex buffer for all models, with only the full-detail indices, uploaded with the static world and then dropped on the CPU. Objects are drawn at rest (every vertex at its stored position, transformed per object in the vertex program) in the world's render bundles, with element 1 of their model shaders (the projected light texture is unestablished); hanging lamps' lights are kept as data, not drawn.
  - Colour values pass through unconverted (non-sRGB targets). UI blending and filtering follow docs/formats/ui-layout.md (#23). Video frames upload as Y'CbCr planes, are packed unconverted into the video texture on the GPU and convert to RGB when drawn, after filtering (docs/behavior/startup.md 6.6; measured: ~0.2 ms per 876×400 frame vs ~1.2 ms converting on the CPU, native).
- **Main thread** owns DOM UI and input. It forwards normalized input events (touch, keyboard/mouse, gamepad) to the engine worker via `postMessage`. `platforms/web/static/main.js` starts the worker (`engine-worker.js`) and transfers the canvas; requests to the engine are `{type: "call", id, op, args}` messages answered by id.
  - The app always opens on its own home screen (a reminder of where the engine's settings live); its Play button (which also unlocks audio) launches the game when graphics are available (WebGPU or WebGL 2): the engine owns the screen (input capture on), and the page hides its own interface until the player quits ("Yes" in the menu's quit box, or Q), which returns to the home screen.
  - Touch is a touchpad for the cursor wherever the game shows it (the title menu and its screens, options, the in-game menu, save and load screens, message boxes, the on-screen keyboard's screen, the inventory screen): a Volya Engine addition, decided by the user (#108). A touch never clicks where it lands there, no exception (text fields included). The page recognises the gestures (`static/touchpad.js`, a pure recognizer; our values): a swipe anywhere moves the cursor by its motion; a tap (lifted within 500 ms, moved at most 10 CSS pixels) clicks at the cursor; a touch beginning less than 250 ms after a tap's lift (the engine's double-click time) is a second touch: lifted as a tap it is a double click, moved past the slop or held 500 ms it presses (a single press, so a drag never acts as a double click: it never loads a save) and holds until lifted, so double-tap and hold, then move, drags (sliders, scroll bars, list thumbs); the button a drag holds is tracked apart from the gesture and released when its finger lifts, on any cancelled touch and on a reset (blur, the cursor hiding, capture ending); two fingers swiped up or down scroll, one wheel step per 40 CSS pixels of their mean travel, content following the fingers; a long press (500 ms within 10 pixels, as Android's) is a right click, fired while held (or at the lift, if that comes before its timer). It sends semantic messages (`cursor_motion` with the swipe's speed smoothed over 75 ms, `cursor_button` with the recognizer's double-click flag, `wheel`); the engine holds the touchpad's buttons apart from direct touch's; the engine applies the acceleration (`volya-engine-core::input::touchpad_gain`: one to one below 200 CSS px/s, rising linearly to 2.5 times at 1200, level beyond), then the menu's motion rule (title-menu.md section 7: normalised position, sensitivity, clamped to the screen). The mode follows the engine's `cursor_shown` (the phases whose screens draw the cursor), told to the page with `{type: "cursor", shown}`; a touchpad touch stays one until lifted (a drag is released when the cursor hides); direct touches still down when the cursor appears are dropped, their button released without moving the cursor (`touch_drop`). While the cursor shows the page also cancels `touchend`, which the Touch Events specification documents suppresses the compatibility mouse events and the click, so none blurs the text entry just focused. Elsewhere (logos, loading, the level) touches go as before; the level keeps its own touch controls.
  - Input (`static/input.js`: pointer events for mouse and touch, keyboard, polled Gamepad API) is forwarded as `{type: "input", event}` only while the engine owns the screen; otherwise the DOM UI keeps it. The engine turns this on with the `input_capture` op and tells the page with `{type: "capture", on}`. `volya-engine-core::input` reduces every source to the menu's mouse/keyboard vocabulary (touch = a touchpad wherever the game's cursor shows, below, elsewhere the touch point and the left button; gamepad = arrow keys, Enter, Escape); `input_state` reports it. In a level the player's controls (`volya-engine::controls`) map every path onto the game's movement actions: keyboard and mouse by the game's bindings, with mouse look under Pointer Lock (taken on a click in the level, released when the level's controls stop); gamepad sticks and buttons; and the page's on-screen touch controls (`static/touch-controls.js`, DOM elements over the canvas, shown on touch devices while the level's controls are live), which send semantic messages (the stick's reach, past its rim too; look drags; buttons and the Crouch swipe) rather than raw contacts (Menu at the top left, Inventory at the top right: our design, #110; the UI textures have no inventory icon, so its glyph is our backpack); the engine owns their logic (the sprint lock, the look curve over the drag speed the page measures: `volya-engine::controls`), the page only draws it and places the lock target. They look like instruments of the game's HUD (#105), drawn from its own UI textures, which the engine decodes for the page once per session (the `ui_images` op: still images by texture path or texture description id, optionally cut to a rectangle, as RGBA, through `volya-engine::ui_image`; nothing of the game is shipped); until then, or without game data (the UX audit page), vector approximations in the same palette stand in. The engine tells the page when the level's controls go live or stop, and the toggles they show, with `{type: "controls"}`. Keys pressed with Control reach the engine only while the character takes keys (the level's controls live, or the inventory screen over them; Control is the crouch key); Chrome reserves Ctrl+W, Ctrl+T and Ctrl+N, which a page can't block outside fullscreen with the Keyboard Lock API (documented, not measured); the level offers that full screen (below).
- **Audio**: the engine worker decodes (Vorbis, `lewton`) and mixes (`volya-engine-core::audio::Mixer`); the page's AudioWorklet pulls mixed stereo blocks straight from the engine worker over a transferred MessagePort. Audio resumes on the first user gesture (browser policy). It is an output channel, not shared state.
  - Decoder: `lewton` 0.10.2 (MIT or Apache-2.0, pure Rust, runs in wasm). Its last release is from 2021 and its repository's last commit from 2023 (documented, crates.io and GitHub; #312); Symphonia, the maintained pure-Rust alternative, is MPL-2.0 and so excluded; `vorbis_rs` wraps the C libvorbis. `lewton` decodes a single-page stream's whole last block (its issue 106; measured on `ambient\indoors\small_fan.ogg`, 666 frames too many), so `VorbisStream` ends its output at the last page's granule, the stream's end by the Vorbis I specification. The browser's `decodeAudioData` is not an option: Web Audio's contexts are exposed to windows only (`[Exposed=Window]` in the Web Audio specification), not to the engine worker, and WebKit reads Ogg Vorbis only from iOS 18.4 (documented, WebKit's Safari 18.4 notes).
  - Sounds by name (`volya-engine-core::sound`, docs/formats/sound-ogg-params.md): the first request of a name resolves its file (`$level$` first, then `$game_sounds$`), checks it (mono, 44,100 Hz; anything else, a missing, empty or invalid file, or a max distance below 0.1 is a `Fatal`), and keeps only its parameters; each play reads the compressed file again and decodes it block by block, so no PCM is held (`sound_params` in `volya-engine-formats` reads the record). Measured on the first level's 11 files (`volya-engine-core/tests/sound.rs`, native release, M-series Mac): about 1,300 times real time (2,224 s of audio in 1.7 s), a heap peak of the file plus about 0.25 MiB while decoding (`music\amb01_l.ogg`: 4.4 MiB file, 4.7 MiB peak, where its PCM would take 88 MiB); in wasm under Node about the same speed and growth (521 s of `amb01_l` in 411 ms, heap +4.7 MiB). A record shorter than its version's size, which the spec leaves unestablished, is treated as an unknown version (defaults and a warning; our choice).
  - Positional playback (`volya-engine-core::sound::system`, docs/behavior/sound-positional.md): sounds, emitters, the per-frame update, the voices and the device parameters as the spec gives them, against a `Device` trait shaped like its OpenAL interface. `volya-engine::audio::SoundHost` owns it with its clock (real time since the first update, without the page's hidden time, #93) and plays its voices on the mixer (`MixerDevice`): each a mixer voice in `Category::Scaled` (its gain already holds the category volume) whose gain is the source gain times OpenAL's inverse distance clamped factor and whose pan is the direction's component along the listener's right vector (how a direction is rendered is unestablished; our choice); gain changes ramp over one mixed block; the listener's overall gain is the mixer's master gain. A voice resuming mid-sound decodes up to its offset (#309). On the web the host lives beside the mixer in the engine worker and updates every worker frame, game running or not; the app gives it the voice count (`snd_targets` from the user file, else 16) once, the level's camera as the listener, a pause while the menu is open over the level, and stops every sound when the level is left. The `debug_play_sound` and `sound_state` ops (test builds) play a named sound at a position and report the emitters. Output stays the AudioWorklet pulling from the worker (one path for all sounds); the page suspends the AudioContext while hidden and resumes it on return and on any gesture while its state isn't `running`, which covers WebKit's non-standard `interrupted` (documented: MDN; WebKit bugs 263627 and 281955 report contexts left interrupted on return, which the gesture recovers; not measured on a device). Measured, native release (`volya-engine/tests/sound.rs`): with 24 of 32 looped emitters playing, an update takes about 35 µs and mixing a 60th of a second at 48 kHz about 390 µs; starting all 24 voices at once (reading their files) about 21 ms (#310).
  - The level's sounds (`volya-engine::level_sound` over `volya-engine-core::sound::{static_sources, music, ambient, rain_thunder, occlusion}`; docs/behavior/sound-static-sources.md, sound-level-music.md, sound-weather-ambient.md, sound-rain-thunder.md, sound-occlusion.md; #316 – #318): their data (`level.snd_static`, `level.som`, the track list of `game.ltx`, the weather's ambient sets and thunderbolt collections) is read under `st_client_spawning` with the weather; their sounds are created in the sound system on the first frame the level runs with audio output, and discarded when the level is left. The rules run in the specs' order (static sources, music, thunder, rain, ambience) on every frame of the level while the pause is off; the static sources and the music also not under the loading image (S3 4.1, S5 4.1), which the other specs don't exempt. A sound file that can't be opened (docs/formats/sound-ogg-params.md section 5) and a draw from a range with equal bounds (S3 4.2, S4 4.7) are fatal: the game ends and the title menu says why, as when loading fails, and none of the level's sounds is kept. Their clock is the global clock of S4 3.1 (`volya-engine-core::pause`, kept by the app): the engine clock's real time, loading included, standing still while the pause is on; its rate is 1 and it has no fixed-step mode, the original's initial values (S3's review gap). The pause (S4 3.1's table) is on while the main menu shows (the title menu, the menu over a level; it closes as a New Game starts, before loading), while an interface sequence's item with `pause_state` `on` plays (the logos, the New Game intro), and while the page is hidden, our platform's focus loss (#93; after the menu hiding opens, so the return leaves the pause to the menu). Off at start, and no unpaused frame passes between logo items or before the title menu (the spec's review gaps, #335); the `pause` action, the level-change window and the rest of the table's events wait for their systems (#334). S8's frame time is the engine clock's step between updates, smoothed, 0 while the pause is on. S2's sound clock stays its own. The ambience's and the thunder's state is kept for the run, as the specs keep it. Random draws come from one generator, the specs' linear congruential one seeded with 1 (any uniform generator serves, as its sequence can't be reproduced). The occlusion target is computed along a jittered segment against the level's collision world (shared with the level as an `Arc`) and `level.som`, without the original's remembered-triangle shortcut, which the spec lets an implementation omit. The player's sky visibility (outdoors for the ambience, the rain's sky factor) follows level-objects.md 5.4's per-frame rays from the eye, the player's model not being loaded (#320). Reverb (docs/behavior/sound-reverb.md) is the device's EAX 2.0, which our mixer lacks, so none is heard, as on `l01_escape` with it (#320: whether to render one is the user's decision). Effects' particles and the bolts' pictures are P11's and P21's. Measured with `l01_escape` at the New Game's start (four looped static sources, the ambience's random sounds; occlusion against the level): the sound update takes about 150 µs a frame in headless Chrome (300 µs worst; `level_stats`, the `audio` suite) and about 26 µs natively in release (`volya-engine/tests/level_sound.rs`); the wasm heap after the New Game stays at 99 MiB; creating the level's 97 sounds (reading every file once) takes about 64 ms natively.
  - The player's footsteps (`volya-engine::footsteps` over `volya-engine-core::{footsteps, cycles}` and `volya-engine-formats::{gamemtl, skeletal_motions}`; docs/formats/material-pairs.md, docs/behavior/player-cycle-lengths.md, player-footsteps.md; #324): the material pairs are read with the materials under `st_loading_cform` (`gamemtl.xr` is read there, not at game start, our choice) and their lists' sounds (5,439 sounds of 169 files) are created with the level's sounds and discarded with them; a list of more than 4 items, or a pair naming no material, fails the load. The player's cycles come from its record's model and that model's motion files, read under `st_client_spawning` as streams: chunk 15 and each motion's name and key count, no tracks (about 50 ms natively for `stalker_animation.omf`); only each cycle's length, speed, duration and stop flag are kept, since no pose is drawn (so no cycle time is kept either). On each frame that advances game time with audio output and the pause off, after the movement update, the leg cycle is chosen from the movement state and the steps timed on the step clock, which is the global clock of the level's sounds (S11 3.1 names the same clock as sound-weather-ambient.md 3.1); the app plays them independently at the feet. Compressed chunks of motion files are decoded, as chunks.md section 5 has every reader do. Body turning while standing, climbing and physical objects underfoot don't exist, so the turn and climbing cycles never play and only the level's geometry gives the ground material (#325). Measured natively in release (`volya-engine/tests/footsteps.rs`): the footsteps take about 0.14 µs a frame (2 µs worst); creating the pairs' sounds about 95 ms, which the first level frame with audio output now spends on top of the level's own sounds (about 170 ms for all 266 files).
- **I/O is synchronous on the engine thread**: `Read + Seek` over OPFS sync access handles (opened read-only through web-sys's unstable bindings, enabled in `.cargo/config.toml`: Chrome lets several copies of the app hold them, so two tabs or a tab and the installed app can both play; Safari ignores the mode and locks each file to one handle, so a second copy's Play reports its error, measured as `InvalidStateError`), for parsing, loading screens and in-game loads alike, like the original engine. Keep large reads out of the frame loop where practical. A browser shows a presented frame only once the worker yields, so a loading screen runs one load stage per engine frame: the frame that begins a stage draws its image, the next does that stage's work under it (docs/behavior/loading-screen.md). An I/O worker for streaming is deferred until measurements show hitches (#17).
- **Other workers** do self-contained jobs and exchange messages only, never simulation state: the importer (multi-GB unpack), and later, if profiling demands it, asset decoding.
- **No `SharedArrayBuffer`, no wasm threads.** This removes the need for cross-origin isolation (COOP/COEP), which GitHub Pages cannot provide. Revisit only with profiling data.

## Settings

- The options screen's settings and the key bindings live in a console (`volya-engine-core::console`): the variables of docs/behavior/options-screens.md section 7 with their kinds and ranges, the 77 actions' bindings, and every other `<name> <value>` line of the user configuration file kept as written, so settings of systems Volya Engine lacks survive. Lines a preset's script alone sets are not kept (the script sets them again at the next start); with that, the installer's `user.ltx` read and saved again is written byte for byte as shipped.
- The user configuration file (section 12) is Volya Engine's own `user.ltx` in the OPFS namespace beside the imported game, never written into the game's files. Without one, the installer's copy in the game root (`__support/userdocs/user.ltx`) is read. It is stored when the options screen closes and when the player quits from the menu: the original stores it only at exit, but a browser tab is usually closed without one.
- What the settings do: `vid_mode` sets the size drawn at (at the video restart Apply and Cancel run); `snd_volume_eff` and `snd_volume_music` the mixer's effects and music volumes, at once; `mouse_sens`, `mouse_invert`, `g_always_run` and the bindings the player's controls, of a running level too once the setting is applied; the `quit` binding which key skips movies; New Game sets `g_game_difficulty`. ## The inventory screen

- docs/behavior/inventory-screen.md, in `volya-engine::inventory_screen` (#110). Its layout is loaded when the level is made (the `_16` rule of that moment); the moves between places act on the player character's inventory (`volya-engine-core::character::inventory`).

## The menu during a game

- The key bound to `quit` (and a gamepad's east button, the touch Menu button, and losing pointer lock, since the browser takes Escape to leave it) opens the menu over the level once the loading image is gone. Asked for while the image covers the level's first frames, it is not dropped: it opens in the first frame the player's controls are live, after the intro (a Volya Engine addition, decided by the user, #96; presses during the intro skip it). On the menu's main page the key closes it again (`volya-engine::menu_screens`, docs/behavior/save-load-screens.md section 2). The level stays loaded and paused; its world stays in the scene, covered, so its GPU copy is kept while nothing of it is drawn.
- The menu's save and load screens and its boxes are mouse screens; touch reaches them through the touchpad (above), gamepads through the options screen's mapping (`volya-engine::dialog`).
- Typing the save screen's name without a keyboard is a Volya Engine addition, decided by the user (#94); the field keeps its own rules (the characters its keys type, its width limit), and physical keyboards type as before.
  - Touch (typographic quotes typed as plain ones; an input method's composed text sent when composing ends): the field is clicked with the touchpad's cursor like everything else (#108). The engine tells the page where the field is, whether it has focus and whether the cursor is over it (`{type: "text_field"}`, `over` from the engine's own cursor); on touch devices the page keeps an unseen text input there that never takes taps itself (`static/text-entry.js`, `pointer-events: none`). A device's keyboard rises only for an input focused within a user gesture (iOS; believed, not measured), so when a touchpad gesture presses the left button while the cursor is over the field, the page focuses the input in that very event handler, and the same press focuses the engine's field as a mouse click does; if the engine doesn't focus its field within 500 ms the input is blurred again. While the on-screen keyboard or a box covers the screen the field isn't reported. Typed characters are sent as text (`["text", s]`, `Event::Text`) and the input emptied at once; Backspace, Enter and the arrows go as keys. The field losing focus (Enter) closes the keyboard.
  - Gamepad: an on-screen keyboard drawn by the engine (`volya-engine::on_screen_keyboard`), plain flat keys over the screen's bottom: the field's character keys as on a US keyboard, Shift (a toggle), Space, Backspace and Done, the last four drawn as line symbols rather than words (an arrow up, a space bar's bracket, an arrow left, a check mark). While it shows, the mouse and touch don't reach the screen under it; keys do. The field is a d-pad target; south pressing in it focuses it and opens the keyboard, which then takes the gamepad (d-pad moves, south presses, west is Backspace, east is Done) until the field loses focus.
- Saved games live in the `savedgames` directory of the OPFS namespace (`$game_saves$`, beside `user.ltx`). The page lists it when the game starts (names, modification times, the first 8 bytes of each `.sav`, all the validity test needs) and keeps the `.sav` files' `File` snapshots, from which the load screen reads a selected save synchronously (`FileReaderSync`); no access handle is held, so another copy of the app can delete saves meanwhile. The engine hands back files the player deleted and the page removes them (one file each, never a directory). Nothing writes saves yet, so the listing at start stays current.
- Writing and loading saves are stubs until #75 (`TODO(#75)` in `volya-engine::save_load`): the save screen's last step (`save N`) writes nothing and the screen stays; loading a valid save (load screen, last save) does nothing. Neither shows anything. The load screen shows no save picture (always `ui\ui_noise`).

## Full screen while playing

A Volya Engine addition, decided by the user (#85): the game crouches on Control, and outside full screen with Keyboard Lock the browser keeps Ctrl+W (close the tab), Ctrl+T and Ctrl+N from the page (documented: the Keyboard Lock specification and Chrome's article on it). Offered, never imposed (`static/fullscreen.js`):

- A small offer ("Full screen", and that it keeps such shortcuts in the game and that holding Esc leaves it, with a close control) shows in the level's top right corner on desktop browsers with `navigator.keyboard.lock` (desktop Chrome; Safari and Firefox lack the API, documented by MDN as limited availability) while the level's controls are live and the mouse is free; the system pointer shows with it. Not on macOS, read from `navigator.userAgentData.platform` (else `navigator.platform`): its browser shortcuts use Command, which is never locked (our choice). At most once per game, from Play until the player leaves: once hidden (by the click that takes pointer lock, the menu, accepting or closing it) it doesn't come back until the next game (our choice). The first click in the level takes pointer lock as before and hides it; it can't be clicked under the lock anyway. Presses on it stay with the page.
- Accepting, in the click (full screen needs a user gesture): `navigator.keyboard.lock()` with the keys bound to any action (the `bound_keys` op, read as the controls go live) but Tab, F4 and the OS keys, which stay the system's even when bound so Alt+Tab, Alt+F4 and the OS key still work (our choice), and W, T, N and Escape, then `requestFullscreen()` on the page's root, in the order the specification recommends (lock first, so the browser shows one exit notice). Keyboard Lock works only in full screen a page requested (documented, not F11's).
- Under the lock a short Escape reaches the game, which opens the menu as before; holding it two seconds leaves full screen (documented: the specification's long press, and Chrome's own notice says so). A hold begins as a press the page receives (documented: the specification delivers locked keys until the hold reaches two seconds; not measured), so the menu opens on the way out; the offer's note doesn't say so. Pointer lock works inside full screen as before (documented: the specification leaves it unchanged but for the exit notice; whether a short Escape still releases it under the lock is not measured, and either way the menu opens: a lost lock opens it too). Bindings changed while in full screen are locked anew as the controls go live again. Leaving full screen ends the lock; when the player leaves the game the page leaves the full screen it entered, then unlocks.
- Headless Chrome can't enter full screen from a synthesized click: the `menu` suite stubs `navigator.keyboard` and `requestFullscreen` and checks the calls and their order.

## A hidden page

A Volya Engine addition, decided by the user (#93): every browser throttles or suspends hidden pages, so the engine stops while the page is hidden (another tab, a minimised window, a Home Screen app sent to the background).

- The page listens to `visibilitychange` and tells the engine worker (`{type: "visibility", hidden}`). It is the one event for all of these: documented by MDN for tab switches, minimising and mobile app switches; measured in the iOS Simulator's Safari (an app switch fires `blur` then `visibilitychange` to hidden, the return `focus` then `visibilitychange` to visible; no `pagehide`, `freeze` or `resume`). Chrome's `freeze` only ever follows hidden (documented, Page Lifecycle API; Safari and Firefox lack it), so it needs no handler; `pagehide` ends the worker (bfcache, above). Believed, not measured: an iPhone Home Screen app behaves as Safari does.
- Hidden: in a level whose controls are live the menu opens, as a lost pointer lock opens it, with the same guard against an Escape closing it at once (`App::set_hidden`); the menu or one of its screens already open stays as it is; during the loading and the intro nothing opens. The app runs no update, so the engine clock, game time, movement and movies stand still; the first update back takes the clock on from where it stopped (a zero delta). The worker's frame loop idles (no update, no drawing) and the page suspends its AudioContext and sends the input a `blur` (everything released).
- Shown: the frame loop resumes and the page resumes audio (when the browser refuses without a gesture, the next gesture resumes it). The player resumes from the menu.

## Scripts

Scripts run on the runtime the original embeds (docs/behavior/script-environment.md): the public **LuaJIT 1.0.3** (Lua 5.1 alpha) in interpreter mode, decided by the user (#91, #97). `crates/volya-engine-script`.

- **Source.** `vendor/luajit-1.0.3/` holds only the files the interpreter needs (the Lua core, the base, table, string, math, jit and coco libraries, their headers, and `COPYRIGHT`), plus `lcoco.c`, not built, for its licence notice; all unmodified. `csrc/volya_jit.c` and `csrc/volya_coco.c` derive from `ljit_core.c` and `lcoco.c` and carry their MIT licence too. Licence: MIT (`COPYRIGHT` for Lua; the notice in `luajit.h` and `lcoco.c` for Mike Pall's parts). Provenance: `LuaJIT-1.0.3.tar.gz` from `http://luajit.org/download/LuaJIT-1.0.3.tar.gz` (luajit.org no longer serves 1.x releases; fetched from the Internet Archive's capture of that URL, `https://web.archive.org/web/20160318172846id_/http://luajit.org/download/LuaJIT-1.0.3.tar.gz`, whose captures from 2007 to 2016 all have the same SHA-1), 308,336 bytes, SHA-256 `e39204aad8d2a3f9ef74a4a515fedf3cce3f55ff247af8ae50f2a8cb01f257c3`. `LUA_VERSION` in its `lua.h` is `Lua 5.1 (alpha) + LuaJIT 1.0.3`, the spec's string.
- **Build** (`build.rs`, the `cc` crate). Natively with the system C compiler; for wasm32 with Homebrew's LLVM clang (Apple's has no wasm target), found at `/opt/homebrew/opt/llvm`, `/usr/local/opt/llvm` or `brew --prefix llvm`, else the build fails saying so. Vendored files are compiled from a copy in `OUT_DIR`, patched by `build.rs` (each replacement must match exactly once). `llex.c` gets the original's C-style comments (docs/behavior/script-loading.md 1): a case for `/` where a token can start, so in every chunk the runtime compiles; `//` to the next LF, `/* */` without nesting, end or counted line breaks, a `*` taken with the byte after it. `luaconf.h` (Lua's configuration header, meant for embedders): numbers convert to integers with the header's own x86 method on every target (add 2^52 + 2^51, take the double's low 32 bits): rounding to nearest, ties to even, as the spec's x86 build does (2.5), and out-of-range values wrapping as there, where our targets' casts truncate; and string-to-number conversion is our own decimal-only `strtod` on every target (C99 libraries also read hexadecimal, `inf` and `nan`; Lua 5.1 alpha is written for ANSI C's). The release's other `luaconf.h` defaults stand (`string.gfind` is `gmatch`, `math.mod` is `fmod`, `table.setn` raises "obsolete"); the spec doesn't establish the original's.
- **No machine-code compiler.** DynASM and the x86 backend (`ljit_core.c`, `ljit_mem.c`, `ljit_backend.c`, `ljit_dasm.c`) aren't built; `csrc/volya_jit.c` implements the engine interface without them. Our choice: the `jit` library keeps every function, `jit.on`, `jit.off`, `jit.debug` and per-function modes change only flags, nothing is ever compiled (`jit.compile` and `jit.compilesub` return `jit.util.status.ENGINE_OFF`, every function's status is `ENGINE_OFF`). `jit.util`'s bytecode introspection (`stats`, `bytecode`, `const`, `upvalue`, `closure`, `closurenup`) works; `mcode`, `mcodeaddr` and `jsubmcode` raise "… is unavailable".
- **Coco without C stacks.** Coco's stack switching (`lcoco.c`) can't be done in wasm; `csrc/volya_coco.c` provides its C API with plain Lua threads, and Coco's coroutine library is kept (`create`, `resume`, `yield`, `wrap`, `cstacksize`, `coroutine.coco`). A yield across a C call (metamethod, `pcall`, iterator, Rust function) raises `attempt to yield across metamethod/C-call boundary` (#100).
- **`math.random`** uses one generator on every target, the C standard's example `rand` (`RAND_MAX` 32767, seed 1; `csrc/volya_rand.c`, swapped in for the C library's by a header included before every vendored file): our choice until the original's is established (#106).
- **Libraries.** Each state opens what the original's game state opens by default (spec 2.1): base, table, string, math, jit, coco; never io, os, debug or package.
- **Errors.** Lua's setjmp/longjmp: natively the C library's; in wasm32, LLVM's lowering to WebAssembly exception handling (`-mllvm -wasm-enable-sjlj`, legacy `try`/`catch` encoding) with our runtime for it (`csrc/wasm/libc.c`, the `__c_longjmp` tag in `c_longjmp.S`). Legacy exception handling is in Chrome 95+, Safari and iOS Safari 15.2+, Firefox 100+ (documented, MDN browser-compat-data); measured with the `platform` suite in Chrome 158 and the iOS 27.2 Simulator's Safari. The newer `exnref` encoding needs Chrome 137+ and Safari 18.4+, so it isn't used.
- **C library for wasm32** (`csrc/wasm`): headers and the functions the interpreter calls. Memory and Lua's allocator go through Rust's (aborting when memory runs out, so Lua never raises a memory error; a recoverable per-state budget is #107); `printf`-family formatting is ours (`csrc/volya_printf.c`) with floating-point digits from Rust's formatting (`src/libc.rs`), checked against the system's natively; most math comes from Rust's compiler-builtins (a port of musl's libm; the native build uses the system's, and results may differ in the last bit); ctype is the "C" locale; `rand` is ours on every target (below); there are no files (`dofile` and `loadfile` fail to open), stdin is empty, `print` output is discarded.
- **Rust API** (`Lua`): create a state, `exec` or `compile` a named chunk, `call` a global function, `register` Rust functions; values are nil, booleans, numbers, strings (bytes) and tables. Lua's longjmp never crosses Rust frames: every Lua call that can raise runs in C inside `lua_cpcall` (`csrc/volya_glue.c`), Rust only reads values, from stack slots C reserved beforehand (tables up to 64 levels deep), which allocates and raises nothing, and gets errors as `Result`s; a Rust function's results or error are handed back to C, which pushes or raises them; a panic in one becomes a Lua error natively (wasm aborts on panic).
- **Loading scripts** (`loader`, docs/behavior/script-loading.md 2; #109). `Scripts` is a game script state over the game's file trees, lent per read through a `Trees` implementation (an `Rc<dyn Trees>`, as the loader is called back from Lua), like the web platform's `with_trees`: archive tree and game root; scripts are read from the archive tree. It must be dropped before the platform unmounts the files. Script name N is `$game_scripts$N.script`, compiled as the game builds the chunk (the file's bytes unchanged after the one-line namespace prefix, default or `-_g`; none for `_G`). The loader's Lua side (`src/loader.lua`) runs before any script and its entry function is kept in the registry; scripts reach it only through C functions (the globals' `__index` handler, `prefetch`) that call that entry, so no Lua function of the loader, and none of the Rust functions it holds, is reachable (jit.util reads only Lua functions' upvalues). `load_globals` is startup's `_G`; `load_namespace`, `exec` and `call` may load more. Failures (including an unmakeable path and a failing `__tostring`) are discarded in Lua as the original does and kept for the engine (`take_failures`). `Common` reads `script.ltx`'s `[common]` lists; calling the class registrators awaits the engine's API. Our choices where the spec is silent or Lua can't follow it: the fatal error can't unwind past a script's `pcall`, so the call it happens in returns `ErrorKind::Fatal` whatever scripts did, every later call does too, and every later load raises it again; its message's `namespace N: ` prefix; a non-table before the last component is fatal too; `prefetch` converts numbers and raises for other non-strings; `_G` is compared case-sensitively; an unreadable file isn't remembered as missing; chunks are named `@` plus our lowercase path relative to the game root.
- **Shipped scripts:** all 437 of the Russian edition's scripts with loadable names compile as the game builds their chunks except 4 that aren't Lua, none reachable (spec 4.1); the 2 `*.script` files under `config\` are never loaded.

## Collision

- A level's collision mesh (`level.cform`, docs/formats/level-cform.md) stays in memory while the level runs as vertex indices and one material index per triangle, with a uniform grid over x and z (2 m cells) listing each cell's triangles: 42 MB for `l01_escape`. It is streamed from the file and indexed under `st_loading_cform` without holding the file or per-triangle temporaries (about 45 ms and 44 MB peak, native release, measured).
- The movement layer (`volya-engine-core::movement`, docs/behavior/player-movement.md) turns each frame's actions into the movement state and the desired acceleration, and runs the body at the fixed step from an accumulator of the display frame time; the camera follows the body's eye.
- The player character's state (`volya-engine-core::character`, docs/behavior/player-state.md: conditions, profile, inventory) is created with the level on New Game and kept by it. Each frame its thresholds are evaluated once into the movement's limits before the movement update, a started jump takes its power, and the conditions then advance by the game time the frame advanced (so nothing changes while the game is paused or the page hidden). It holds what a save writes: it fills the player's record, builds its items' records and writes the client-data condition blocks. Its supplies take the ids after the player's registration in the offline simulation (docs/behavior/offline-simulation.md 8.1); the bolt, which the player receives on coming online (player-state.md 3.2), takes the next id once every New Game record exists.
- The player's body is our own small solver, not a physics library: the body never rotates, so it is a point mass with contact constraints using the spec's parameters (error reduction, constraint-force mixing, friction, bounce), solved by projected Gauss–Seidel. The movement layer drives it in two halves per fixed step (`collision::body`): the step's contacts first, then its forces.

## Particles

- The library (`volya-engine-formats::particles`, docs/formats/particles-xr.md) and the simulation (`volya-engine-core::particles`: effect instances, actions, regions, groups and the level's placed effects; docs/behavior/particle-lifecycle.md, particle-motion-actions.md, particle-appearance-actions.md, particle-groups.md, level-placed-effects.md). Arithmetic is `f32` per operation in the specs' order, also where a spec leaves the x87 precision believed or disputed (the motion actions' conventions; appearance 1.2); `sin`, `cos`, `exp`, `ln` and square roots are Rust's `f32` functions, so results may differ from the game's in the last bit. Every numeric vector of the specs is a unit test, the library-wide facts a game-data test.
- Random numbers: the shared generator and the C runtime's are each a state of the level's effects (`Random`), both starting at 1 (our choice: the starting state and the other parts of the game drawing from it are unestablished, lifecycle 2.1), so a level's effects are deterministic.
- A group's member effects report births and deaths as a list the group works through after the member's update, in their order (the children they make draw no random numbers, so this is the same as at once). A child naming no effect, or a looped birth or death child, is a fatal error (groups 2.3): the group stops there and the level's next update ends the game with it (`App::fatal`). Destroying a group stops and drops everything (TODO(#319)).
- Unestablished cases decided (#336): an action type id of 2 or above 31 fails the library's parse (believed a crash); unspecified types (0, 3, 5, 11, 13, 18, 20) are read with their sizes and do nothing; `follow` with no particle does nothing; the noise is NaN below t = −2³¹ too; a region of a kind above 10 is placed as stored; `level.ps_static` with a payload too short for its transform is an error; group chunk 7's members are read as chunk 4's without the birth and death names.
- The level (`LevelScreen`) reads `level.ps_static` and `particles.xr` under `st_loading_ai_objects` (after the objects in the game; our placement), and makes, places, plays and updates each record's instance there, at the engine clock of that frame; the first update after loading gets the rest of the load's time. Its effects run on the level's world clock, advanced by each level update's elapsed time: it stands still while the game is paused (the menu, the intro) and while the page is hidden (#93), as the game clock does. Each level update runs the scheduler's pass (level-placed-effects.md 5.2; every due instance, no budget: unestablished), then the drawing update (5.3) of every instance whose culling sphere meets the view of the latest frame's size; collision (docs/behavior/particle-collision.md, P5) is not implemented yet (#342).
- Drawing (docs/behavior/particle-drawing.md, #322): the frame values at birth and the frame animation are part of the simulation (they draw from the shared generator); the sprites are built on the CPU for each frame from the camera (`volya-engine-core::particles::sprite`), four vertices of 24 bytes a particle, uploaded with absolute indices (no base vertex) and drawn without storage buffers, so the WebGL 2 path draws them as WebGPU does. Each effect's shader is resolved with the level's (under `st_loading_textures`): class `PARTICLE` from `shaders.xr`; `particles\xadd` and `particles\xdistort`, scripted, implemented from the spec's section 5.3 (no Lua runs). Effects are tested against the view frustum (a sphere is rejected only when outside a plane by more than its radius) and the screen measure; sectors and `level.hom` are not (a superset). They are queued into the world pass as section 7.4 orders: `SET` after the priority 0 – 1 static draws, `ADD`, `ALPHA-ADD` and the scripted shaders' normal pass after the priority 2 – 3 ones, `BLEND` merged with the static strict-sorted draws back to front (on equal keys statics first, our choice). With a distortion list the world is drawn into a texture of its own with its depth kept, the distortion target (cleared to 127/255) gets element 4 of the scripted shaders back to front, depth-tested against the scene with the scene's view and projection (believed, TODO(#329)), and a composition pass looks the scene up at t + (D.rg − 0.5) · 0.05 into the frame; the presentation itself is otherwise unestablished (static-shading.md 10.2), so nothing else is applied. Distortion is always available (our renderer's programs exceed pixel shader 1.4).
- Measured, native release (`volya-engine-core/tests/particles_cost.rs`, M-series Mac): the library holds 1.8 MiB (parsed in 1.6 ms; the stage peaks 3.3 MB with the file); `l01_escape`'s one effect (7 particles) costs about 0.1 µs a frame and holds 3 KiB; `l12_stancia_2`'s 73 records (about 1,200 particles) 3 µs a frame on average, 33 µs at the 99th percentile, 0.5 MiB. In headless Chrome (`menu` suite, `debug_particles_bench`, timed over 20,000 frames): `l01_escape`'s effect 0.64 µs a frame, timer calls included; the wasm heap's high-water mark does not grow under `st_loading_ai_objects` (94 MiB before and after); with drawing, 99 MiB in the level after the first and the second New Game (98 before particles). The particles' pipelines (every pass the effects' shaders resolve to, with each culling) and their vertex and index buffers are made with the renderer and kept, the buffers grown and written with `Queue::write_buffer`: made with the first effect drawn, they stayed allocated amid the freed level, and the second New Game's collision world no longer fit there (99 → 112 MiB under `st_loading_shaders`); buffers made mapped each frame took the second New Game to 115 MiB (measured).

## Offline simulation

- `volya-engine-core::simulation` (docs/behavior/offline-simulation.md) keeps every object of a game, from `all.spawn` at a New Game (or a save's records on load), as its full record (`ObjectRecord`, docs/formats/sav.md 7; the largest kinds boxed), in a list indexed by id, changed in place (location, position, smart terrain, client data), so a save writes each record as it stands; what is not saved (online state, travel, smart-terrain looks) sits beside it. The actor's items are held by the character state, which takes the ids the registry reserves after the player, and the bolt's from the pool afterwards.
- It holds the whole game graph (the level points are read on demand, not kept), the patrol paths, and the current level's navigation data: `level.ai`'s positions (streamed, 6 of each vertex's 21 bytes) and the cross table (streamed). The spawn file is dropped once its records and paths are read, before the navigation data. Measured for a New Game on `l01_escape`, native release: graph and paths 1.8 MB, the registry of 8,641 objects 14.8 MB, navigation 7.1 MB, 23.7 MB at the peak; created in about 30 ms. `st_server_connecting` peaks and keeps 19.8 MB natively (`loading_memory.rs` and `simulation_cost.rs` assert budgets).
- It is created under `st_server_connecting` with its first switch pass (all objects evaluated once while the loading image shows). Every level update then runs one simulation update on the game clock with the actor at the player's feet: the switch pass over the current level's list, then up to `objects_per_update` scheduled stalkers and monsters. It runs only in updates, so it stands still while the game is paused or the page hidden. Measured per update, native release: median 21 µs, 99th percentile 37 µs while walking across the level.
- The smart terrains' scripts (acceptance, suitability, tasks) are behind a trait; without the scripts no object joins a smart terrain, so nothing travels yet.
- The level loads the visuals of every object of its list that is online or whose engine predicate *on* can hold, not only those online at the start; an object switching changes its instance's placement, which the presenter writes into the world's per-draw data: a hidden draw gets a bounding radius of 0, so the shaders' size test drops it. An object arriving on the level by travel has no loaded visual and stays undrawn.

## Hosting: GitHub Pages, project site

Served from `https://mmotorny.github.io/volya-engine/`, deployed with `cargo xtask deploy`: a local release build force-pushed as one commit to the `gh-pages` branch (#12). Tests are never deployed. No custom domain: it emphasizes the project's free, non-commercial nature.

Constraints this imposes:

- **No custom headers.** Never depend on cross-origin isolation. The dev server (`tools/devserver`) sends no such headers and a browser test asserts the page is not isolated.
- **Base path `/volya-engine/`.** All URLs are relative. The dev server serves under the same path.
- **Shared origin.** Every `mmotorny.github.io` project site shares one origin, so storage quota, OPFS, IndexedDB, caches and service worker registrations are shared with unrelated sites. Keep everything under a `volya-engine` namespace (OPFS directory, cache names, IndexedDB names), scope the service worker to `/volya-engine/`, and treat stored data as possibly modified by others: validate on load, never trust it blindly.
- **No cache control.** Pages sets its own short cache lifetimes; the service worker (`static/sw.js`) owns app versioning, with the established precache pattern (as in Workbox's injectManifest, without its Node tooling): `cargo xtask web` injects every file with a hash of its content into `sw.js`, so the script changes exactly when the build does; install downloads only changed files; of the two wasm builds (Rendering), only those the browser ran are kept: their files are marked with the build in `PRECACHE`, the page tells the worker which build the engine loaded (a message, no query parameters), and a build's file fetched while missing is kept too (#186); copies kept from before builds were recorded (`pkg/`, the one build until then) are updated like any kept file until the page names its build, and then dropped if it isn't theirs; kept files are served cache-first, so a page runs one consistent version, offline included; a new version waits until the page asks it to take over, then drops files that left the build. Updates download automatically by default (`static/update.js`) and never restart the app by themselves: once downloaded, the page offers Finish update (as Chrome does), and closing and reopening the app finishes it too. Players can turn automatic downloads off in Settings (metered connections); then nothing downloads by itself: the install refuses without consent, tells the page the update's size, and a tap downloads it. The only automatic transfer left is the browser's own check of `sw.js` (a few KB) when the app opens; with automatic updates the page also calls `registration.update()` on returning to the foreground, at most hourly. Settings' Check for updates calls it at once (#120): a new worker installing or waiting, or the worker's offer when downloads are off, leads Home, whose update row downloads or finishes it (a download the player asked for shows there with automatic downloads too); otherwise the result shows in the button's place for a few seconds. A failed `registration.update()` rejects with a TypeError whether the network is down or `sw.js` can't be had (Service Workers spec, Update; measured with the test server unreachable: Chrome "An unknown error occurred when fetching the script", Safari "Script … load failed", `navigator.onLine` still true), so it says offline only when `navigator.onLine` is false, and otherwise that it couldn't check. The setting lives in the service worker's cache, where both can read it. The version shown is one: the build's commit time and hash (`2026-11-24 00:47 · b0fa5b8`); Cargo's SemVer isn't shown. The `smoke` suite runs the real `sw.js` against a fake cache and checks every file with the test server's network cut; the harness drops service workers left by earlier runs.

## UX audit page

`/volya-engine/ux-audit/` shows every state of the app's own interface on each device (iPhone 17 Pro Max portrait and landscape, desktop Chrome), like a design file. Each frame is the live interface (`style.css`, `game-ui.js`) with a fake engine and fake updates (`ux-audit/frame.js`), so the page can't drift from the app; states live in `ux-audit/states.js`. It is for the project, not players: not kept offline by the service worker, `noindex`. Its frames load the app's files through the service worker, so after a deploy it shows the new version on a hard reload. States can be limited to some devices (`devices`). It flags states whose text differs by device, and keeps its view (zoom, devices, full length, scroll) across reloads and visits (localStorage).

## Game data: BYOA, local only

Game data never reaches any server. The user brings the GOG offline installer (Russian edition of the original Shadow of Chernobyl first; docs/roadmap.md); GOG's servers can't be used from the browser (no CORS on auth, API, content system or CDN).

- **Eager inflation, same on every platform.** The importer inflates every game file once into OPFS; the engine then reads plain files through the OPFS VFS with true random access, no on-demand inflation and no decompression cache. Game files are chains of independent zlib parts (10 MiB, the last up to ~18 MB) stored at known offsets in the `.bin` (docs/formats/gog-installer.md); the importer streams each file's parts, inflates them with `zlib-rs` as streams through fixed-size buffers (4 MiB read, 1 MiB written at a time, so the worker's heap doesn't grow with the parts), verifies part and file MD5s, and writes the file. Parts are independent, so import can inflate in parallel across workers.
- **Inno Setup only for headers.** The `inno` crate parses the `.exe` headers (~12 ms, measured) to find each game file's parts; only the importer uses it. It needs file install conditions exposed: we depend on the `expose-file-conditions` branch of the fork https://github.com/mmotorny/inno via `[patch.crates-io]`.
- **Storage.** Extracted game files take 5.55 GiB. Desktop Chrome: installer + extraction, 9.0 GB at peak and at rest (5.55 GB if the user deletes the installer); persistent file handles (IndexedDB) to the installer would allow re-import without re-picking (#20). iPhone Home Screen app (import must run inside the installed app; its storage is separate from the browser's): iOS copies every picked file into a temporary location, so the peak is installer + temporary + extraction, 12.5 GB; 9.0 GB at rest, 5.55 GB if the user deletes the installer. Precheck free space with `storage.estimate()` (the browser's allowance for the app, not the disk's free space), request `storage.persist()` (granted in the installed Home Screen app on the reference device, added from Chrome; not granted in a plain browser tab). Desktop Chrome never prompts: it grants silently when the site is installed or bookmarked, used a lot, or allowed notifications, and re-decides on each request (web.dev, Persistent storage); a fresh profile's tab is denied (measured, #63). Best-effort storage is evicted under storage pressure, least recently used site first, with no time limit in Chrome. So the import screen gives this device's advice for keeping the game before importing (install the app; on iPhone, import in the Home Screen app), and importing in a tab anyway accepts the risk: no storage warnings after. When an import finishes, a localStorage entry marks it: Chromium's eviction clears the site's quota-managed storage (the imported files, the service worker's cache) but not localStorage or cookies (measured: a 400 MB disk image held the profile, a second site filled it, Chrome evicted ours: files gone, cookie and localStorage kept), so a deleted game is said as such on the import screen; where the mark goes too (Safari's 7-day limit covers all script-writable storage; the user clearing site data) it's a first start. localStorage rather than a cookie: nothing sent to the server.
- **Original formats, no conversion.** The engine reads the game files as the importer extracted them: textures upload as stored (BC when the GPU has `texture-compression-bc`; transcoded at run time where it hasn't, Rendering above), audio and video are decoded from the original Vorbis and Theora, models and levels are parsed from their original formats. No install-time transcoding or cooking; reconsider only when measurements demand it.
- **Detect from the data, never by edition.** No edition-specific code paths and no tables of known editions: formats are decoded by what the data says (headers, chunk types, flags, paths), and content differences (languages, patches, mods) are resolved by what files exist. Edition identity (the MD5s in `import.json`) serves diagnostics only.
- **OPFS is a cache.** Storage can be wiped (user clearing data, deleting the app, eviction without persistent mode). At startup verify the import and offer re-import from the installer; show persistence and usage in the import screen.
