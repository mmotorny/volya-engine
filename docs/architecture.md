# Architecture

Decisions and the reasons behind them. Update this file when a decision changes.

## Crates

Split only where a split buys compile-time isolation, a compiler-enforced boundary, or reuse outside the product; subsystems (AI, physics, A-Life, UI) are modules, not crates.

| Package | Contents | Why separate |
|---|---|---|
| `crates/volya-engine` | The platform-free product: composes the role crates into one engine (screens such as the startup sequence and the title menu, driven by a clock and input, producing scenes the presenter turns into draw lists), defines the traits platforms implement (storage, input, audio, surface, clock), and hosts the test interface. | The product as one library every platform ships. |
| `crates/volya-engine-core` | Platform-free engine: VFS trait, native backend and game-archive tree, configuration loading, audio mixing, simulation (world, A-Life, AI, physics, scripting), save/load. | Deterministic and headless-testable; cannot reach rendering or any platform. |
| `crates/volya-engine-render` | `wgpu` renderer: textures, video textures, draw lists to frames. | Keeps `wgpu` rebuilds off the simulation's edit loop; keeps rendering out of simulation. |
| `crates/volya-engine-formats` | Parsers and decoders over `Read + Seek` or bytes, no I/O: the game's own formats (from clean specs) and the public ones it uses (DDS, Ogg Vorbis, Ogg Theora). | Reused by tools; one home for clean-room provenance and game-data tests. |
| `crates/volya-engine-script` | The script runtime: the vendored LuaJIT 1.0.3 interpreter (C), our C library for wasm32, and a thin safe Rust API (see Scripts). | Keeps the C build (build.rs, LLVM clang for wasm) and all `unsafe` FFI in one place; one home for the third-party source and its provenance. |
| `crates/volya-engine-installer` | GOG offline installer reader and extractor (Inno Setup headers, GOG parts). | Unrelated to the game; runs in the importer worker; has its own CLI. |
| `platforms/web` | Crate `volya-engine-web` (wasm `cdylib`: entry point, OPFS, workers, `OffscreenCanvas`) plus `static/` (HTML, JS, CSS, icons). Only package using `web-sys`. | Platform packaging and APIs; compiles to nothing elsewhere. |
| `platforms/ios` (later) | Crate `volya-engine-ios` (`staticlib`) plus the Xcode project / Swift shell. | Same, for iOS. VR decided when it starts (visionOS may sit with iOS). |

Dependencies point one way: `volya-engine-<platform>` → `volya-engine` → role crates (`render` → `core` → `formats`; `script`; `installer`). Everything in `crates/` builds and tests natively. Tooling lives in `tools/` (`devserver`, `xtask`).

## Threading: one engine thread, in a worker

The engine (VFS, simulation, scripting, A-Life, physics, rendering) runs on a single thread inside a dedicated Web Worker.

- **Single-threaded simulation** matches the original X-Ray engine's observable behavior and update order, keeps simulation deterministic, and fits comfortably within the reference device's budget (iPhone 17 Pro Max).
- **In a worker** because OPFS `FileSystemSyncAccessHandle` is worker-only. Synchronous reads let archive readers be plain `Read + Seek` Rust.
- **Rendering** uses WebGPU on an `OffscreenCanvas` transferred from the main thread. Verified on iPhone 17 Pro Max (WebKit, via Chrome for iOS) and desktop Chrome (#11). The iOS Simulator has no WebGPU adapter, so WebGPU checks need the real device.
  - The page sends the canvas's CSS size and `devicePixelRatio` on start and on change; the worker sizes the canvas and surface in device pixels. The frame loop runs in the worker on `requestAnimationFrame` (a 60 Hz timer where workers lack it) and presents only when something changed.
  - The game draws at its video mode (`vid_mode`, docs/behavior/options-screens.md section 9), not at the canvas's size: menus and 3D go to an offscreen frame of that size, which is drawn into the canvas scaled to fit with its aspect kept, black around it (#49). The resolution list offers the canvas's own size and the common 4:3, 5:4, 16:10 and 16:9 sizes that fit it (browsers expose no display modes); the page counts as windowed, so a stored mode not in the list is used as it is. Pointer positions are taken relative to the drawn picture.
  - Without WebGPU (or without an adapter) the engine still starts, without graphics; `status` and the page's status line say why.
  - A level's static world uploads `level.geom`'s vertex and index buffers as stored; packed attributes are decoded in the vertex programs (WebGPU vertex formats reproduce the spec's decoding). Its draws are recorded once into a render bundle replayed every frame; what depends on the camera (near/far shader variants, size culling) is decided per draw in the shaders from per-draw data. The CPU copy of the geometry is dropped after upload. Scripted shader definitions (Lua) are not run: the specified effect of each script the level uses is implemented directly.
  - A level's spawned objects (docs/behavior/level-objects.md) are loaded in its loading stages: the switch pass under `st_server_connecting`, the model files under `st_client_spawning`, their surfaces with the level's under `st_loading_textures`, their light inputs (rays against the collision world, taken converged at once) under `st_client_synchronising`. Each model file is read once and shared by every object showing it; its vertices are quantized as the first renderer stores them (16 bytes: `s16` position, `u8` normal, `s16` texture coordinate) into one vertex buffer for all models, with only the full-detail indices, uploaded with the static world and then dropped on the CPU. Objects are drawn at rest (every vertex at its stored position, transformed per object in the vertex program) in the world's render bundles, with element 1 of their model shaders (the projected light texture is unestablished); hanging lamps' lights are kept as data, not drawn.
  - Colour values pass through unconverted (non-sRGB targets). UI blending and filtering follow docs/formats/ui-layout.md (#23). Video frames upload as Y'CbCr planes, are packed unconverted into the video texture on the GPU and convert to RGB when drawn, after filtering (docs/behavior/startup.md 6.6; measured: ~0.2 ms per 876×400 frame vs ~1.2 ms converting on the CPU, native).
- **Main thread** owns DOM UI and input. It forwards normalized input events (touch, keyboard/mouse, gamepad) to the engine worker via `postMessage`. `platforms/web/static/main.js` starts the worker (`engine-worker.js`) and transfers the canvas; requests to the engine are `{type: "call", id, op, args}` messages answered by id.
  - The app always opens on its own home screen (a reminder of where the engine's settings live); its Play button (which also unlocks audio) launches the game when WebGPU is available: the engine owns the screen (input capture on), and the page hides its own interface until the player quits ("Yes" in the menu's quit box, or Q), which returns to the home screen.
  - Input (`static/input.js`: pointer events for mouse and touch, keyboard, polled Gamepad API) is forwarded as `{type: "input", event}` only while the engine owns the screen; otherwise the DOM UI keeps it. The engine turns this on with the `input_capture` op and tells the page with `{type: "capture", on}`. `volya-engine-core::input` reduces every source to the menu's mouse/keyboard vocabulary (touch = cursor there + left button; gamepad = arrow keys, Enter, Escape); `input_state` reports it. In a level the player's controls (`volya-engine::controls`) map every path onto the game's movement actions: keyboard and mouse by the game's bindings, with mouse look under Pointer Lock (taken on a click in the level, released when the level's controls stop); gamepad sticks and buttons; and the page's on-screen touch controls (`static/touch-controls.js`, DOM elements over the canvas, shown on touch devices while the level's controls are live), which send semantic messages (the stick's reach, past its rim too; look drags; buttons and the Crouch swipe) rather than raw contacts; the engine owns their logic (the sprint lock, the look curve over the drag speed the page measures: `volya-engine::controls`), the page only draws it and places the lock target. The engine tells the page when the level's controls go live or stop, and the toggles they show, with `{type: "controls"}`. Keys pressed with Control reach the engine only while the level's controls are live (Control is the crouch key); Chrome reserves Ctrl+W, Ctrl+T and Ctrl+N, which a page can't block outside fullscreen with the Keyboard Lock API (documented, not measured); the level offers that full screen (below).
- **Audio**: the engine worker decodes (Vorbis, `lewton`) and mixes (`volya-engine-core::audio::Mixer`); the page's AudioWorklet pulls mixed stereo blocks straight from the engine worker over a transferred MessagePort. Audio resumes on the first user gesture (browser policy). It is an output channel, not shared state.
- **I/O is synchronous on the engine thread**: `Read + Seek` over OPFS sync access handles (opened read-only through web-sys's unstable bindings, enabled in `.cargo/config.toml`: Chrome lets several copies of the app hold them, so two tabs or a tab and the installed app can both play; Safari ignores the mode and locks each file to one handle, so a second copy's Play reports its error, measured as `InvalidStateError`), for parsing, loading screens and in-game loads alike, like the original engine. Keep large reads out of the frame loop where practical. A browser shows a presented frame only once the worker yields, so a loading screen runs one load stage per engine frame: the frame that begins a stage draws its image, the next does that stage's work under it (docs/behavior/loading-screen.md). An I/O worker for streaming is deferred until measurements show hitches (#17).
- **Other workers** do self-contained jobs and exchange messages only, never simulation state: the importer (multi-GB unpack), and later, if profiling demands it, asset decoding.
- **No `SharedArrayBuffer`, no wasm threads.** This removes the need for cross-origin isolation (COOP/COEP), which GitHub Pages cannot provide. Revisit only with profiling data.

## Settings

- The options screen's settings and the key bindings live in a console (`volya-engine-core::console`): the variables of docs/behavior/options-screens.md section 7 with their kinds and ranges, the 77 actions' bindings, and every other `<name> <value>` line of the user configuration file kept as written, so settings of systems Volya Engine lacks survive. Lines a preset's script alone sets are not kept (the script sets them again at the next start); with that, the installer's `user.ltx` read and saved again is written byte for byte as shipped.
- The user configuration file (section 12) is Volya Engine's own `user.ltx` in the OPFS namespace beside the imported game, never written into the game's files. Without one, the installer's copy in the game root (`__support/userdocs/user.ltx`) is read. It is stored when the options screen closes and when the player quits from the menu: the original stores it only at exit, but a browser tab is usually closed without one.
- What the settings do: `vid_mode` sets the size drawn at (at the video restart Apply and Cancel run); `snd_volume_eff` and `snd_volume_music` the mixer's effects and music volumes, at once; `mouse_sens`, `mouse_invert`, `g_always_run` and the bindings the player's controls, of a running level too once the setting is applied; the `quit` binding which key skips movies; New Game sets `g_game_difficulty`. Every other setting is shown, edited and stored but does nothing yet: `renderer`, `_preset` (its script runs and sets the video settings, which do nothing), `rs_c_gamma`, `rs_c_contrast`, `rs_c_brightness`, `rs_fullscreen`, `rs_vis_distance`, `r__geometry_lod`, `r__detail_density`, `texture_lod`, `r__tf_aniso`, `r__supersample`, `r2_sun`, `r2_sun_details`, `r2_slight_fade`, `r2_ls_squality`, `ai_use_torch_dynamic_lights`, `rs_v_sync`, `rs_refresh_60hz`, `snd_efx`, `g_game_difficulty` (no gameplay yet), `hud_crosshair`, `cl_dynamiccrosshair`, `hud_weapon`, `hud_info`, `hud_crosshair_dist`, the bindings of actions without a system (weapons, inventory, quick save, the console, …), and the update check (an online service).
- The options screen opens from the title menu and from the menu during a game.

## The menu during a game

- The key bound to `quit` (and a gamepad's east button, the touch Menu button, and losing pointer lock, since the browser takes Escape to leave it) opens the menu over the level once the loading image is gone. Asked for while the image covers the level's first frames, it is not dropped: it opens in the first frame the player's controls are live, after the intro (a Volya Engine addition, decided by the user, #96; presses during the intro skip it). On the menu's main page the key closes it again (`volya-engine::menu_screens`, docs/behavior/save-load-screens.md section 2). The level stays loaded and paused; its world stays in the scene, covered, so its GPU copy is kept while nothing of it is drawn.
- The menu's save and load screens and its boxes are mouse screens; touch and gamepads reach them through the options screen's mapping (`volya-engine::dialog`).
- Typing the save screen's name without a keyboard is a Volya Engine addition, decided by the user (#94); the field keeps its own rules (the characters its keys type, its width limit), and physical keyboards type as before.
  - Touch (typographic quotes typed as plain ones; an input method's composed text sent when composing ends): the engine tells the page where the field is and whether it has focus (`{type: "text_field"}`); on touch devices the page lays a transparent text input over it (`static/text-entry.js`). A tap lands on the input, so the browser focuses it and raises the device's keyboard (a page can raise it only in the tap itself), and the same tap focuses the engine's field. Typed characters are sent as text (`["text", s]`, `Event::Text`) and the input emptied at once; Backspace, Enter and the arrows go as keys. The field losing focus (Enter) closes the keyboard.
  - Gamepad: an on-screen keyboard drawn by the engine (`volya-engine::on_screen_keyboard`), plain flat keys over the screen's bottom: the field's character keys as on a US keyboard, Shift (a toggle), Space, Backspace and Done, the last four drawn as line symbols rather than words (an arrow up, a space bar's bracket, an arrow left, a check mark). While it shows, the mouse and touch don't reach the screen under it; keys do. The field is a d-pad target; south pressing in it focuses it and opens the keyboard, which then takes the gamepad (d-pad moves, south presses, west is Backspace, east is Done) until the field loses focus.
- Saved games live in the `savedgames` directory of the OPFS namespace (`$game_saves$`, beside `user.ltx`). The page lists it when the game starts (names, modification times, the first 8 bytes of each `.sav`, all the validity test needs) and keeps the `.sav` files' `File` snapshots, from which the load screen reads a selected save synchronously (`FileReaderSync`); no access handle is held, so another copy of the app can delete saves meanwhile. The engine hands back files the player deleted and the page removes them (one file each, never a directory). Nothing writes saves yet, so the listing at start stays current.
- Writing and loading saves are stubs until #75 (`TODO(#75)` in `volya-engine::save_load`): the save screen's last step (`save N`) writes nothing and the screen stays; loading a valid save (load screen, last save) does nothing. Neither shows anything. The load screen shows no save picture (always `ui\ui_noise`).

## Full screen while playing

A Volya Engine addition, decided by the user (#85): the game crouches on Control, and outside full screen with Keyboard Lock the browser keeps Ctrl+W (close the tab), Ctrl+T and Ctrl+N from the page (documented: the Keyboard Lock specification and Chrome's article on it). Offered, never imposed (`static/fullscreen.js`):

- A small offer ("Full screen", and that it keeps such shortcuts in the game and that holding Esc leaves it, with a close control) shows in the level's top right corner on desktop browsers with `navigator.keyboard.lock` (desktop Chrome; Safari and Firefox lack the API, documented by MDN as limited availability) while the level's controls are live and the mouse is free; the system pointer shows with it. Not on macOS, read from `navigator.userAgentData.platform` (else `navigator.platform`): its browser shortcuts use Command, which is never locked (our choice). At most once per game, from Play until the player leaves: once hidden (by the click that takes pointer lock, the menu, accepting or closing it) it doesn't come back until the next game (our choice). The first click in the level takes pointer lock as before and hides it; it can't be clicked under the lock anyway. Presses on it stay with the page.
- Accepting, in the click (full screen needs a user gesture): `navigator.keyboard.lock()` with the keys bound to any action (the `bound_keys` op, read as the controls go live) but Tab, F4 and the OS keys, which stay the system's even when bound so Alt+Tab, Alt+F4 and the OS key still work (our choice), and W, T, N and Escape, then `requestFullscreen()` on the page's root, in the order the specification recommends (lock first, so the browser shows one exit notice). Keyboard Lock works only in full screen a page requested (documented, not F11's).
- Under the lock a short Escape reaches the game, which opens the menu as before; holding it two seconds leaves full screen (documented: the specification's long press, and Chrome's own notice says so). A hold begins as a press the page receives (documented: the specification delivers locked keys until the hold reaches two seconds; not measured), so the menu opens on the way out; the offer's note doesn't say so. Pointer lock works inside full screen as before (documented: the specification leaves it unchanged but for the exit notice; whether a short Escape still releases it under the lock is not measured, and either way the menu opens: a lost lock opens it too). Bindings changed while in full screen are locked anew as the controls go live again. Leaving full screen ends the lock; when the player leaves the game the page leaves the full screen it entered, then unlocks.
- Headless Chrome can't enter full screen from a synthesized click: the `menu` suite stubs `navigator.keyboard` and `requestFullscreen` and checks the calls and their order.

## A hidden page

A Volya Engine addition, decided by the user (#93): every browser throttles or suspends hidden pages, so the engine stops while the page is hidden (another tab, a minimised window, a Home Screen app sent to the background).

- The page listens to `visibilitychange` and tells the engine worker (`{type: "visibility", hidden}`). It is the one event for all of these: documented by MDN for tab switches, minimising and mobile app switches; measured in the iOS Simulator's Safari (an app switch fires `blur` then `visibilitychange` to hidden, the return `focus` then `visibilitychange` to visible; no `pagehide`, `freeze` or `resume`). Chrome's `freeze` only ever follows hidden (documented, Page Lifecycle API; Safari and Firefox lack it), so it needs no handler; `pagehide` ends the worker (bfcache, above). Believed, not measured: an iPhone Home Screen app behaves as Safari does.
- Hidden: in a level whose controls are live the menu opens, as a lost pointer lock opens it, with the same guard against an Escape closing it at once (`App::set_hidden`); the menu or one of its screens already open stays as it is; during the loading and the intro nothing opens. The app runs no update, so the engine clock, game time, movement and movies stand still; the first update back takes the clock on from where it stopped (a zero delta). The worker's frame loop idles (no update, no drawing) and the page suspends its AudioContext and sends the input a `blur` (everything released).
- Shown: the frame loop resumes and the page resumes audio (when the browser refuses without a gesture, the next gesture resumes it). The player resumes from the menu.

## Scripts

Scripts run on the runtime the original embeds (docs/behavior/script-environment.md): the public **LuaJIT 1.0.3** (Lua 5.1 alpha) in interpreter mode, decided by the user (#91, #97). `crates/volya-engine-script`.

- **Source.** `vendor/luajit-1.0.3/` holds only the files the interpreter needs (the Lua core, the base, table, string, math, jit and coco libraries, their headers, and `COPYRIGHT`), plus `lcoco.c`, not built, for its licence notice; all unmodified. `csrc/volya_jit.c` and `csrc/volya_coco.c` derive from `ljit_core.c` and `lcoco.c` and carry their MIT licence too. Licence: MIT (`COPYRIGHT` for Lua; the notice in `luajit.h` and `lcoco.c` for Mike Pall's parts). Provenance: `LuaJIT-1.0.3.tar.gz` from `http://luajit.org/download/LuaJIT-1.0.3.tar.gz` (luajit.org no longer serves 1.x releases; fetched from the Internet Archive's capture of that URL, `https://web.archive.org/web/20160318172846id_/http://luajit.org/download/LuaJIT-1.0.3.tar.gz`, whose captures from 2007 to 2016 all have the same SHA-1), 308,336 bytes, SHA-256 `e39204aad8d2a3f9ef74a4a515fedf3cce3f55ff247af8ae50f2a8cb01f257c3`. `LUA_VERSION` in its `lua.h` is `Lua 5.1 (alpha) + LuaJIT 1.0.3`, the spec's string.
- **Build** (`build.rs`, the `cc` crate). Natively with the system C compiler; for wasm32 with Homebrew's LLVM clang (Apple's has no wasm target), found at `/opt/homebrew/opt/llvm`, `/usr/local/opt/llvm` or `brew --prefix llvm`, else the build fails saying so. Vendored files are compiled from a copy in `OUT_DIR` whose `luaconf.h` (Lua's configuration header, meant for embedders) gets the build's only patch, in `build.rs`: numbers convert to integers with the header's own x86 method on every target (add 2^52 + 2^51, take the double's low 32 bits): rounding to nearest, ties to even, as the spec's x86 build does (2.5), and out-of-range values wrapping as there, where our targets' casts truncate; and string-to-number conversion is our own decimal-only `strtod` on every target (C99 libraries also read hexadecimal, `inf` and `nan`; Lua 5.1 alpha is written for ANSI C's). The release's other `luaconf.h` defaults stand (`string.gfind` is `gmatch`, `math.mod` is `fmod`, `table.setn` raises "obsolete"); the spec doesn't establish the original's.
- **No machine-code compiler.** DynASM and the x86 backend (`ljit_core.c`, `ljit_mem.c`, `ljit_backend.c`, `ljit_dasm.c`) aren't built; `csrc/volya_jit.c` implements the engine interface without them. Our choice: the `jit` library keeps every function, `jit.on`, `jit.off`, `jit.debug` and per-function modes change only flags, nothing is ever compiled (`jit.compile` and `jit.compilesub` return `jit.util.status.ENGINE_OFF`, every function's status is `ENGINE_OFF`). `jit.util`'s bytecode introspection (`stats`, `bytecode`, `const`, `upvalue`, `closure`, `closurenup`) works; `mcode`, `mcodeaddr` and `jsubmcode` raise "… is unavailable".
- **Coco without C stacks.** Coco's stack switching (`lcoco.c`) can't be done in wasm; `csrc/volya_coco.c` provides its C API with plain Lua threads, and Coco's coroutine library is kept (`create`, `resume`, `yield`, `wrap`, `cstacksize`, `coroutine.coco`). A yield across a C call (metamethod, `pcall`, iterator, Rust function) raises `attempt to yield across metamethod/C-call boundary` (#100).
- **`math.random`** uses one generator on every target, the C standard's example `rand` (`RAND_MAX` 32767, seed 1; `csrc/volya_rand.c`, swapped in for the C library's by a header included before every vendored file): our choice until the original's is established (#106).
- **Libraries.** Each state opens what the original's game state opens by default (spec 2.1): base, table, string, math, jit, coco; never io, os, debug or package.
- **Errors.** Lua's setjmp/longjmp: natively the C library's; in wasm32, LLVM's lowering to WebAssembly exception handling (`-mllvm -wasm-enable-sjlj`, legacy `try`/`catch` encoding) with our runtime for it (`csrc/wasm/libc.c`, the `__c_longjmp` tag in `c_longjmp.S`). Legacy exception handling is in Chrome 95+, Safari and iOS Safari 15.2+, Firefox 100+ (documented, MDN browser-compat-data); measured with the `platform` suite in Chrome 158 and the iOS 27.2 Simulator's Safari. The newer `exnref` encoding needs Chrome 137+ and Safari 18.4+, so it isn't used.
- **C library for wasm32** (`csrc/wasm`): headers and the functions the interpreter calls. Memory and Lua's allocator go through Rust's (aborting when memory runs out, so Lua never raises a memory error; a recoverable per-state budget is #107); `printf`-family formatting is ours (`csrc/volya_printf.c`) with floating-point digits from Rust's formatting (`src/libc.rs`), checked against the system's natively; most math comes from Rust's compiler-builtins (a port of musl's libm; the native build uses the system's, and results may differ in the last bit); ctype is the "C" locale; `rand` is ours on every target (below); there are no files (`dofile` and `loadfile` fail to open), stdin is empty, `print` output is discarded.
- **Rust API** (`Lua`): create a state, `exec` or `compile` a named chunk, `call` a global function, `register` Rust functions; values are nil, booleans, numbers, strings (bytes) and tables. Lua's longjmp never crosses Rust frames: every Lua call that can raise runs in C inside `lua_cpcall` (`csrc/volya_glue.c`), Rust only reads values, from stack slots C reserved beforehand (tables up to 64 levels deep), which allocates and raises nothing, and gets errors as `Result`s; a Rust function's results or error are handed back to C, which pushes or raises them; a panic in one becomes a Lua error natively (wasm aborts on panic).
- **Shipped scripts:** 409 of the Russian edition's 442 `*.script` files compile; the others stop at C-style comments or aren't Lua (#104).

## Collision

- A level's collision mesh (`level.cform`, docs/formats/level-cform.md) stays in memory while the level runs as vertex indices and one material index per triangle, with a uniform grid over x and z (2 m cells) listing each cell's triangles: 42 MB for `l01_escape`. It is streamed from the file and indexed under `st_loading_cform` without holding the file or per-triangle temporaries (about 45 ms and 44 MB peak, native release, measured).
- The movement layer (`volya-engine-core::movement`, docs/behavior/player-movement.md) turns each frame's actions into the movement state and the desired acceleration, and runs the body at the fixed step from an accumulator of the display frame time; the camera follows the body's eye.
- The player character's state (`volya-engine-core::character`, docs/behavior/player-state.md: conditions, profile, inventory) is created with the level on New Game and kept by it. Each frame its thresholds are evaluated once into the movement's limits before the movement update, a started jump takes its power, and the conditions then advance by the game time the frame advanced (so nothing changes while the game is paused or the page hidden). It holds what a save writes: it fills the player's record, builds its items' records and writes the client-data condition blocks. Its supplies take the ids after the player's registration in the offline simulation (docs/behavior/offline-simulation.md 8.1); the bolt, which the player receives on coming online (player-state.md 3.2), takes the next id once every New Game record exists.
- The player's body is our own small solver, not a physics library: the body never rotates, so it is a point mass with contact constraints using the spec's parameters (error reduction, constraint-force mixing, friction, bounce), solved by projected Gauss–Seidel. The movement layer drives it in two halves per fixed step (`collision::body`): the step's contacts first, then its forces.

## Offline simulation

- `volya-engine-core::simulation` (docs/behavior/offline-simulation.md) keeps every object of a game, from `all.spawn` at a New Game (or a save's records on load), as its full record (`ObjectRecord`, docs/formats/sav.md 7; the largest kinds boxed), in a list indexed by id, changed in place (location, position, smart terrain, client data), so a save writes each record as it stands; what is not saved (online state, travel, smart-terrain looks) sits beside it. The actor's items are held by the character state, which takes the ids the registry reserves after the player, and the bolt's from the pool afterwards.
- It holds the whole game graph (the level points are read on demand, not kept), the patrol paths, and the current level's navigation data: `level.ai`'s positions (streamed, 6 of each vertex's 21 bytes) and the cross table (streamed). The spawn file is dropped once its records and paths are read, before the navigation data. Measured for a New Game on `l01_escape`, native release: graph and paths 1.8 MB, the registry of 8,641 objects 14.8 MB, navigation 7.1 MB, 23.7 MB at the peak; created in about 30 ms. `st_server_connecting` peaks and keeps 19.8 MB natively (`loading_memory.rs` and `simulation_cost.rs` assert budgets).
- It is created under `st_server_connecting` with its first switch pass (all objects evaluated once while the loading image shows). Every level update then runs one simulation update on the game clock with the actor at the player's feet: the switch pass over the current level's list, then up to `objects_per_update` scheduled stalkers and monsters. It runs only in updates, so it stands still while the game is paused or the page hidden. Measured per update, native release: median 21 µs, 99th percentile 37 µs while walking across the level.
- The smart terrains' scripts (acceptance, suitability, tasks) are behind a trait; without the scripts no object joins a smart terrain, so nothing travels yet.
- The level loads the visuals of every object of its list that is online or whose engine predicate *on* can hold, not only those online at the start; an object switching changes its instance's placement, which the presenter writes into the world's per-draw data: a hidden draw gets a bounding radius of 0, so the shaders' size test drops it. An object arriving on the level by travel has no loaded visual and stays undrawn.

## Hosting: GitHub Pages, project site

Served from `https://mmotorny.github.io/volya-engine/`, deployed with `cargo xtask deploy`: a local release build force-pushed as one commit to the `gh-pages` branch (#12). Tests are never deployed. No custom domain: it emphasizes the project's free, non-commercial nature.

Constraints this imposes:

- **No custom headers.** Never depend on cross-origin isolation. The dev server (`tools/devserver`) sends no such headers and a browser test asserts the page is not isolated.
- **Base path `/volya-engine/`.** All URLs are relative. The dev server serves under the same path.
- **Shared origin.** Every `mmotorny.github.io` project site shares one origin, so storage quota, OPFS, IndexedDB, caches and service worker registrations are shared with unrelated sites. Keep everything under a `volya-engine` namespace (OPFS directory, cache names, IndexedDB names), scope the service worker to `/volya-engine/`, and treat stored data as possibly modified by others: validate on load, never trust it blindly.
- **No cache control.** Pages sets its own short cache lifetimes; the service worker (`static/sw.js`) owns app versioning, with the established precache pattern (as in Workbox's injectManifest, without its Node tooling): `cargo xtask web` injects every file with a hash of its content into `sw.js`, so the script changes exactly when the build does; install downloads only changed files; kept files are served cache-first, so a page runs one consistent version, offline included; a new version waits until the page asks it to take over, then drops files that left the build. Updates download automatically by default (`static/update.js`) and never restart the app by themselves: once downloaded, the page offers Finish update (as Chrome does), and closing and reopening the app finishes it too. Players can turn automatic downloads off in Settings (metered connections); then nothing downloads by itself: the install refuses without consent, tells the page the update's size, and a tap downloads it. The only automatic transfer left is the browser's own check of `sw.js` (a few KB) when the app opens; with automatic updates the page also calls `registration.update()` on returning to the foreground, at most hourly. The setting lives in the service worker's cache, where both can read it. The version shown is one: the build's commit time and hash (`2026-11-24 00:47 · b0fa5b8`); Cargo's SemVer isn't shown. The `smoke` suite runs the real `sw.js` against a fake cache and checks every file with the test server's network cut; the harness drops service workers left by earlier runs.

## UX audit page

`/volya-engine/ux-audit/` shows every state of the app's own interface on each device (iPhone 17 Pro Max portrait and landscape, desktop Chrome), like a design file. Each frame is the live interface (`style.css`, `game-ui.js`) with a fake engine and fake updates (`ux-audit/frame.js`), so the page can't drift from the app; states live in `ux-audit/states.js`. It is for the project, not players: not kept offline by the service worker, `noindex`. Its frames load the app's files through the service worker, so after a deploy it shows the new version on a hard reload. States can be limited to some devices (`devices`). It flags states whose text differs by device, and keeps its view (zoom, devices, full length, scroll) across reloads and visits (localStorage).

## Game data: BYOA, local only

Game data never reaches any server. The user brings the GOG offline installer (Russian edition of the original Shadow of Chernobyl first; docs/roadmap.md); GOG's servers can't be used from the browser (no CORS on auth, API, content system or CDN).

- **Eager inflation, same on every platform.** The importer inflates every game file once into OPFS; the engine then reads plain files through the OPFS VFS with true random access, no on-demand inflation and no decompression cache. Game files are chains of independent zlib parts (10 MiB, the last up to ~18 MB) stored at known offsets in the `.bin` (docs/formats/gog-installer.md); the importer streams each file's parts, inflates them with `zlib-rs` (measured ~17–19 ms per part in wasm), verifies part and file MD5s, and writes the file. Parts are independent, so import can inflate in parallel across workers.
- **Inno Setup only for headers.** The `inno` crate parses the `.exe` headers (~12 ms, measured) to find each game file's parts; only the importer uses it. It needs file install conditions exposed: we depend on the `expose-file-conditions` branch of the fork https://github.com/mmotorny/inno via `[patch.crates-io]`.
- **Storage.** Extracted game files take 5.55 GiB. Desktop Chrome: installer + extraction, 9.0 GB at peak and at rest (5.55 GB if the user deletes the installer); persistent file handles (IndexedDB) to the installer would allow re-import without re-picking (#20). iPhone Home Screen app (import must run inside the installed app; its storage is separate from the browser's): iOS copies every picked file into a temporary location, so the peak is installer + temporary + extraction, 12.5 GB; 9.0 GB at rest, 5.55 GB if the user deletes the installer. Precheck free space with `storage.estimate()` (the browser's allowance for the app, not the disk's free space), request `storage.persist()` (granted in the installed Home Screen app on the reference device, added from Chrome; not granted in a plain browser tab). Desktop Chrome never prompts: it grants silently when the site is installed or bookmarked, used a lot, or allowed notifications, and re-decides on each request (web.dev, Persistent storage); a fresh profile's tab is denied (measured, #63). Best-effort storage is evicted under storage pressure, least recently used site first, with no time limit in Chrome. So the import screen gives this device's advice for keeping the game before importing (install the app; on iPhone, import in the Home Screen app), and importing in a tab anyway accepts the risk: no storage warnings after. When an import finishes, a localStorage entry marks it: Chromium's eviction clears the site's quota-managed storage (the imported files, the service worker's cache) but not localStorage or cookies (measured: a 400 MB disk image held the profile, a second site filled it, Chrome evicted ours: files gone, cookie and localStorage kept), so a deleted game is said as such on the import screen; where the mark goes too (Safari's 7-day limit covers all script-writable storage; the user clearing site data) it's a first start. localStorage rather than a cookie: nothing sent to the server.
- **Original formats, no conversion.** The engine reads the game files as the importer extracted them: textures upload as stored (BC when the GPU has `texture-compression-bc`), audio and video are decoded from the original Vorbis and Theora, models and levels are parsed from their original formats. No install-time transcoding or cooking; reconsider only when measurements demand it.
- **Detect from the data, never by edition.** No edition-specific code paths and no tables of known editions: formats are decoded by what the data says (headers, chunk types, flags, paths), and content differences (languages, patches, mods) are resolved by what files exist. Edition identity (the MD5s in `import.json`) serves diagnostics only.
- **OPFS is a cache.** Storage can be wiped (user clearing data, deleting the app, eviction without persistent mode). At startup verify the import and offer re-import from the installer; show persistence and usage in the import screen.
