# Testing

## Strategy

The game renders to an opaque WebGL 2 canvas, so DOM-level tools can't see it. Tests go through the engine, not the page.

1. **Native Rust tests carry most of the weight**: formats, VFS, importer, simulation, scripting, save/load. The simulation is single-threaded and deterministic, so tests feed scripted input, step N frames and assert on state, headless.
2. **Rendering** is checked only where the renderer draws, in headless Chrome's WebGL 2 (the user: the Mac is not a target): the render self-test (`volya-engine-render`'s `selftest` module, run by the `render` suite through `render_selftest`) draws scenes of synthetic data, reads them back and compares them pixel by pixel with a tolerance. Committed references use only synthetic content; references rendered from game data stay local, like the data itself. Fidelity against the original is judged in headless Chrome (WebGL 2 through ANGLE on the Mac's GPU, BC textures as stored), never with ETC2 textures, which differ slightly from BC by design (#113, decided by the user). The self-test checks BC textures by every path the device has (as stored, ETC2, RGBA8; `Renderer::set_texture_path`; headless Chrome has all three), the build translates every program to GLSL ES 3.00 (`build.rs`), the ETC2 encoder is checked against a decoder written apart from it from the specification (`etc2::decode`, test-only, and for other crates' tests behind `volya-engine-formats`'s `etc2-decode` feature), a level's geometry uploaded in steps draws as one uploaded at once (`selftest/world.rs`), and with game data the `render-level` suite draws the level by each texture path against BC's picture and holds a loading for prepared textures and its world, and `volya-engine/tests/transcode.rs` transcodes the level's textures, with its time reported and PSNR per kind of block held to floors 0.05 dB below the encoder's (run it with `--release` for meaningful times).
3. **The engine test interface** (#14) lets tests inject input, step/pause frames, query state and read back the framebuffer: a direct API natively (`volya_engine::test_api`), and in the browser `await volya.call(op)` (plus `volya.status()`), which messages the engine worker and resolves with the op's JSON result. Ops live in `call` in `platforms/web/src/lib.rs`.
4. **Browser tests are thin** and cover only platform integration: startup, worker, WebGL 2 on `OffscreenCanvas`, OPFS, input forwarding, service worker. No WebDriver: each suite has a page, `tests/browser/<suite>.html`, served by the dev server at `/volya-engine/__test/<suite>.html` (never deployed). It starts the unchanged app, runs the suite and POSTs a report to the dev server, which fails on timeout; `cargo xtask e2e` opens `__test/run/<id>/<suite>.html` so reports match runs. Input is synthesized in-page; import tests feed the installer, served with HTTP range requests, through the same import path as picked files. The native file picker and gestures are not covered by automated tests.

## Tooling

All testing is local. `cargo xtask check` runs fast static checks (SPDX, licenses, fmt, clippy) and gates every push. `cargo xtask e2e [chrome] [iphone] [suite...]` runs native tests, builds the web app and runs every browser suite on each target, on demand only; naming suites runs only those (no native tests), e.g. `cargo xtask e2e chrome render`.

| Layer | How | Where |
|---|---|---|
| Native tests | `cargo test` | Mac |
| Browser suites | `tests/browser/<suite>.js`, run by `harness.js`; the dev server serves them under `/volya-engine/__test/`, never in `dist/` | Headless desktop Chrome (audio allowed without a gesture); Mobile Safari in a dedicated `Volya Engine iPhone 17 Pro Max` simulator (created on first run, left booted; Safari quit with its tabs deleted before and after each suite and `sim` run, and by a helper process if the run dies, as an open suite page holds its GPU memory) |

Add a browser suite by creating `tests/browser/<suite>.js` exporting `tests` (name → function, may be async), a `<suite>.html` page calling `runPage("<suite>")`, and listing it in `SUITES` in `tools/xtask/src/e2e.rs`. A test may return a string note for the report. Suites are silent on the machine running them: Chrome runs with `--mute-audio`, and `harness.js` puts a gain of 0 between anything and a live `AudioContext`'s destination (the iOS Simulator plays through one of the Mac's output devices and CoreSimulator accepts no route to none: measured, it falls back to the default device); suites measure audio before that gain, through the AudioWorklet into an `OfflineAudioContext`, and the context's state is unchanged by it. Tests report what really happens. In the iOS Simulator the app's BC textures are transcoded to ETC2 (no BC there), and the `render` and `menu` suites check pixels there too.

`VOLYA_DUMP_DIR=<dir>` keeps the frames suites dump, the browser's `VOLYA_DUMP_*`: `dump(name, capture)` (`harness.js`) encodes a `debug_capture` as PNG on the page and posts it to the dev server (`cargo xtask e2e` or `volya-engine-devserver`), which writes it to `<dir>/<suite>/<name>.png` (keep it outside the repository); without the variable nothing is encoded. Suites that draw game data (`KEPT_PROFILE` in `tools/xtask/src/e2e.rs`) run in Chrome with a profile kept in `target/chrome-profile/`, served on the port it last had (storage belongs to an origin), and import only what its storage lacks, so the game is imported once; delete the directory to import afresh. The `import` and `menu` suites keep fresh profiles, as they test the import.

`VOLYA_SIM_MEDIA=<dir>` makes `cargo xtask e2e` record each iphone suite (H.264) and screenshot its end into that directory (keep it outside the repository); `cargo xtask simshot [path]` takes a screenshot of the test simulator and `cargo xtask simrec <path> <seconds>` records it.

### Shared conformance checks

Behavior every backend must share is written once in Rust and run on each backend: e.g. `vfs::conformance::check` runs natively against `StdVfs` and, via the `vfs_selftest` op, against the OPFS VFS in the engine worker on every browser target; `volya_engine_script::selftest::check` (the runtime's libraries, number formatting, strings, tables, errors, coroutines, `jit`, the Rust API, C-style comments and the script loader on files of its own) runs natively and, via the `script_selftest` op, in the wasm build in the `platform` suite. Natively, `volya-engine-script` also compares our wasm `printf` and `strtod` with the system's. Math functions are not compared: wasm takes them from Rust's compiler-builtins (a port of musl's libm), the native build from the system's libm, and the two may differ in the last bit of a result (believed, not measured), so the self-test checks math to 6 decimals.

### Real touches in the simulator

`cargo xtask sim STEP...` drives Safari in the test simulator with real touches (`tools/simdriver`, an XCUITest; no window, no extra permissions), for what in-page synthesized input can't reach: system sheets such as the file picker, iOS gestures, the path from the screen to the page. Steps: `open <url>`, `wait <s>`, `tap <x> <y>` (screen points), `tap-text <label>`, `hold <x> <y> <s>`, `drag <x1> <y1> <x2> <y2>`, `double-tap <x> <y>`, `pinch <scale>` (two fingers on the page; a pinch doesn't always zoom an unguarded page, so repeat it), `expect-text <label>`, `screenshot <path>`. A step that fails stops the run with the reason. Example: `cargo xtask sim "open http://localhost:8080/volya-engine/" "tap-text Play" "wait 3" "screenshot /tmp/s.png"`. Browser zoom (docs/architecture/web-platform.md) is checked against real gestures with `tests/browser/gestures.html` (not a suite; its flags and output are in the file), e.g. `cargo xtask sim "open http://localhost:8080/volya-engine/__test/run/1/gestures.html#play+controls" "wait 3" "double-tap 220 600" "pinch 3" "wait 1" "expect-text scale 1.00"`. What WebGL 2 holds per resource is measured with `tests/browser/webgl-memory.html` (not a suite; its experiments are in the file) while sampling `footprint` of the Simulator's processes (#443). XCUITest can't hold independent fingers on different spots at once; multi-finger input stays covered by in-page tests. Files for pickers go in the simulator's "On My iPhone" folder: the `File Provider Storage` directory of the `group.com.apple.FileProvider.LocalStorage` app group in the device's data.

### Setup

- rustup (installs the toolchain from `rust-toolchain.toml`; `xtask` installs the matching `wasm-bindgen` CLI).
- `cargo-deny`.
- Homebrew LLVM (`brew install llvm`): its clang builds the script runtime's C for wasm32 (`cargo xtask web`, `cargo xtask check`).
- Google Chrome.
- Xcode with an iOS simulator runtime.

### Dev server

Mimics GitHub Pages (served under `/volya-engine/`, the app's page without custom headers; every other response with COOP and COEP, so test pages, which run without the service worker, are cross-origin isolated, docs/architecture/web-platform.md, Isolation) and serves the browser suites: `cargo xtask web --dev && cargo run -p volya-engine-devserver`, then open `http://localhost:8080/volya-engine/`. Opening `/volya-engine/__test/<suite>.html` runs that suite and prints its report in the server's terminal.
