# Testing

## Strategy

The game renders to an opaque WebGL 2 canvas, so DOM-level tools can't see it. Tests go through the engine, not the page.

1. **Native Rust tests carry most of the weight**: formats, VFS, importer, simulation, scripting, save/load. The simulation is single-threaded and deterministic, so tests feed scripted input, step N frames and assert on state, headless.
2. **Rendering** is checked only where the renderer draws, in headless Chrome's WebGL 2 (the user: the Mac is not a target): the render self-test (`volya-engine-render`'s `selftest` module, run by the `render` suite through `render_selftest`) draws scenes of synthetic data, reads them back and compares them pixel by pixel with a tolerance. Committed references use only synthetic content; references rendered from game data stay local, like the data itself. Fidelity against the original is judged in headless Chrome (WebGL 2 through ANGLE on the Mac's GPU, BC textures as stored), never with ETC2 textures, which differ slightly from BC by design (#113, decided by the user). The self-test checks BC textures by every path the device has (as stored, ETC2, RGBA8; `Renderer::set_texture_path`; headless Chrome has all three), the build translates every program to GLSL ES 3.00 (`build.rs`), the ETC2 encoder is checked against a decoder written apart from it from the specification (`etc2::decode`, test-only, and for other crates' tests behind `volya-engine-formats`'s `etc2-decode` feature), a level's geometry uploaded in steps draws as one uploaded at once (`selftest/world.rs`), and with game data the `render-level` suite draws the level by each texture path against BC's picture and holds a loading for prepared textures and its world, and `volya-engine/tests/transcode.rs` transcodes the level's textures, with its time reported and PSNR per kind of block held to floors 0.05 dB below the encoder's (run it with `--release` for meaningful times).
3. **The engine test interface** (#14) lets tests inject input, step/pause frames, query state and read back the framebuffer: a direct API natively (`volya_engine::test_api`), and in the browser `await volya.call(op)` (plus `volya.status()`), which messages the engine worker and resolves with the op's JSON result. Ops live in `call` in `platforms/web/src/lib.rs`.
4. **Browser tests are thin** and cover only platform integration: startup, worker, WebGL 2 on `OffscreenCanvas`, OPFS, input forwarding, service worker. No WebDriver: each suite has a page, `tests/browser/<suite>.html`, served by the dev server at `/volya-engine/__test/<suite>.html` (never deployed). It starts the unchanged app, runs the suite and POSTs a report to the dev server, which fails on timeout; the suite's test (`xtask suite`) opens `__test/run/<id>/<suite>.html` so reports match runs. Input is synthesized in-page; import tests feed the installer, served with HTTP range requests, through the same import path as picked files. The native file picker and gestures are not covered by automated tests.

## Tooling

All testing is local, and every test is a Bazel target (docs/architecture/build.md), its result cached and shared by every worktree. `bazel test //:checks` runs fast static checks (SPDX, licences, fmt, clippy) and gates every push. `bazel test //...` runs every test that isn't `manual`: the static checks, unit and game-data tests and the smoke, platform, render and import suites on Chrome. A browser suite is `//tests/browser:<suite>_<target>` (dashes as underscores, e.g. `bazel test //tests/browser:render_level_chrome`), the rest `manual`; `:chrome` and `:iphone` name every suite on a target, `:game_chrome` the game suites.

| Layer | How | Where |
|---|---|---|
| Native tests | `bazel test //crates/...` | Mac |
| Browser suites | `tests/browser/<suite>.js`, run by `harness.js`; the dev server serves them under `/volya-engine/__test/`, never in `dist/` | Headless desktop Chrome (audio allowed without a gesture); Mobile Safari in a dedicated `Volya Engine iPhone 17 Pro Max` simulator (created on first run, left booted; Safari quit with its tabs deleted before and after each suite and `sim` run, and by a helper process if the run dies, as an open suite page holds its GPU memory) |

Add a browser suite by creating `tests/browser/<suite>.js` exporting `tests` (name → function, may be async), a `<suite>.html` page calling `runPage("<suite>")`, and listing it in `SUITES` in `tools/xtask/src/e2e.rs` and in `tests/browser/BUILD.bazel`. A test may return a string note for the report. Suites are silent on the machine running them: Chrome runs with `--mute-audio`, and `harness.js` puts a gain of 0 between anything and a live `AudioContext`'s destination (the iOS Simulator plays through one of the Mac's output devices and CoreSimulator accepts no route to none: measured, it falls back to the default device); suites measure audio before that gain, through the AudioWorklet into an `OfflineAudioContext`, and the context's state is unchanged by it. Tests report what really happens. In the iOS Simulator the app's BC textures are transcoded to ETC2 (no BC there), and the `render` and game suites check pixels there too.

`VOLYA_DUMP_DIR=<dir>` keeps the frames suites dump, the browser's `VOLYA_DUMP_*`: `dump(name, capture)` (`harness.js`) encodes a `debug_capture` as PNG on the page and posts it to the dev server (a browser suite's runner or the dev server), which writes it to `<dir>/<suite>/<name>.png` (keep it outside the repository); without the variable nothing is encoded. Suites that draw game data (`KEPT_PROFILE` in `tools/xtask/src/e2e.rs`) run in Chrome with a profile kept for the machine in `~/Library/Caches/volya-engine/chrome-profile/` (one Chrome at a time, under a lock), served on one fixed port (storage belongs to an origin; a profile holding another origin's storage is deleted), and import only what its storage lacks, so the game is imported once; delete the directory to import afresh. The `import` and `game-startup` suites keep fresh profiles, as they test the import; the other game suites start from the kept import.

`VOLYA_SIM_MEDIA=<dir>` (`--test_env`) makes each iphone suite record itself (H.264) and screenshot its end into that directory (keep it outside the repository); `bazel run //tools/xtask -- simshot [path]` takes a screenshot of the test simulator and `bazel run //tools/xtask -- simrec <path> <seconds>` records it.

### Shared conformance checks

Behavior every backend must share is written once in Rust and run on each backend: e.g. `vfs::conformance::check` runs natively against `StdVfs` and, via the `vfs_selftest` op, against the OPFS VFS in the engine worker on every browser target; `volya_engine_script::selftest::check` (the runtime's libraries, number formatting, strings, tables, errors, coroutines, `jit`, the Rust API, C-style comments and the script loader on files of its own) runs natively and, via the `script_selftest` op, in the wasm build in the `platform` suite. Natively, `volya-engine-script` also compares our wasm `printf` and `strtod` with the system's. Math functions are not compared: wasm takes them from Rust's compiler-builtins (a port of musl's libm), the native build from the system's libm, and the two may differ in the last bit of a result (believed, not measured), so the self-test checks math to 6 decimals.

The `fidelity` suite (#521, Chrome only) compares our frames with the original's. Its views are `tests/fidelity/views.rs`, included by both engines: name, the title menu or a New Game's level seen from the start view or a camera track's eye, yaw and pitch, and the seconds after play starts, the video mode (1920×1080, full screen), the field of view (67.5°) and the settings: every video and advanced setting of the options screen at its best-quality end (the user's decision, #561; the derivation, with the specs' sections, is in the file), and the sound lines. `user_ltx` writes them into the shipped `user.ltx`, one file per view, `<view>.user.ltx`, kept by the capture beside the view's frame with the file the original rewrote when it quit, `<view>.saved.ltx`. Its render checks (`selftest/fidelity.rs`, one per view, frame named after it) start from the view's `<view>.user.ltx` (the page passes it), apply its settings as the app does (`app::level_settings`, `app::frame_settings`), place a track view's camera before each level update up to the view's moment, composing each frame of the last second as the app does (the detail pass draws only when it ran in the previous frame too, detail-objects.md 5.1), and draw (the start view: the player as the game placed it). Before any pixel, `fidelity.js` compares the file our console then writes (`Console::save`, as the original's `cfg_save` at quit) with the original's `<view>.saved.ltx` byte for byte: when they differ, the run is invalid, the test fails with the first differing line and no pixel difference is reported. Then it compares each frame with the original's (`//tests/fidelity:frames`, Bazel's capture actions, which `//tests/browser:fidelity_chrome` serves as its references) and reports the pixels differing by more than 16 in a channel, the mean and largest difference, and whether they are within its thresholds (5 % of pixels, mean 8); it is a report, never a failure, since Wine's Direct3D 9 isn't pixel-exact. With `VOLYA_DUMP_DIR` it keeps `fidelity/<view>.png` (ours), `<view>-original.png` and `<view>-heat.png` (matching pixels dimmed, differing ones yellow to red), and the two rewritten files, `<view>.saved.ltx` (ours) and `<view>-original.saved.ltx`. A difference found there becomes an issue fixed through a spec, never by tuning code to the pixels.

### Real touches in the simulator

`bazel run //tools/xtask -- sim STEP...` drives Safari in the test simulator with real touches (`tools/simdriver`, an XCUITest; no window, no extra permissions), for what in-page synthesized input can't reach: system sheets such as the file picker, iOS gestures, the path from the screen to the page. Steps: `open <url>`, `wait <s>`, `tap <x> <y>` (screen points), `tap-text <label>`, `hold <x> <y> <s>`, `drag <x1> <y1> <x2> <y2>`, `double-tap <x> <y>`, `pinch <scale>` (two fingers on the page; a pinch doesn't always zoom an unguarded page, so repeat it), `expect-text <label>`, `screenshot <path>`. A step that fails stops the run with the reason. Example: `bazel run //tools/xtask -- sim "open http://localhost:8080/volya-engine/" "tap-text Play" "wait 3" "screenshot /tmp/s.png"`. Browser zoom (docs/architecture/web-platform.md) is checked against real gestures with `tests/browser/gestures.html` (not a suite; its flags and output are in the file), e.g. `bazel run //tools/xtask -- sim "open http://localhost:8080/volya-engine/__test/run/1/gestures.html#play+controls" "wait 3" "double-tap 220 600" "pinch 3" "wait 1" "expect-text scale 1.00"`. What WebGL 2 holds per resource is measured with `tests/browser/webgl-memory.html` (not a suite; its experiments are in the file) while sampling `footprint` of the Simulator's processes (#443). XCUITest can't hold independent fingers on different spots at once; multi-finger input stays covered by in-page tests. Files for pickers go in the simulator's "On My iPhone" folder: the `File Provider Storage` directory of the `group.com.apple.FileProvider.LocalStorage` app group in the device's data.

### Windows programs under Wine

`bazel run //tools/xtask -- wine run DIR -- EXE [ARGS...]` runs a 32-bit Windows program headless in Apple's `container`: Wine in an arm64 Debian VM, its x86 code under box64 (Rosetta runs no 32-bit x86 in Linux VMs, measured), drawing into Xvfb with Wine's audio driver set to none, so nothing shows or sounds on the Mac. `DIR` is the working directory (`/work` in the container) and what the program writes there stays on the Mac; the exit code is passed on. Each run is a fresh container with a fresh Wine prefix (about 10 s of setup), waits for memory first, starts the `container` service if it wasn't running and leaves it as it found it; the container is stopped afterwards, also on errors and Ctrl-C (a reaper process). `WINEDEBUG` and `WINEDLLOVERRIDES` are passed through (defaults `fixme-all` and `mscoree,mshtml=`; a value replaces the default). `bazel run //tools/xtask -- wine image` builds the image from `tools/xtask/wine/Containerfile` (run and check build it when missing): a 64-bit Wine in WoW64 mode (32-bit Windows code in a 64-bit process; the amd64 WoW64 build of [Kron4ek's Wine builds](https://github.com/Kron4ek/Wine-Builds), stable 11.0, as 11.22 aborts at start under box64) run by box64 (built from a release, MIT), which wraps the container's arm64 X11 and Mesa libraries. `bazel run //tools/xtask -- wine check` builds a Direct3D 9 smoke test (`tools/xtask/wine/d3d9smoke.c`) with MinGW in the container, runs it, and checks the colour it cleared to (about 18 s). Wine and MinGW in the images are copyleft tools that run only inside the container; nothing links them or ships them.

### The original game as a black box

`bazel run //tools/xtask -- original [--new-game] [--quit] [SECONDS]` runs the shipped game unmodified under `wine` (docs/clean-room.md, Sources) and captures its display from outside. Its install folder is Bazel's `@gog_original` (docs/architecture/build.md, Game data): every `ru-RU` game file in the installer's layout, cloned copy-on-write from the extracted game files, with the generated `fsgame.ltx` (read-only) and the empty `userdocs` folders. Each run clones that folder into `<installer cache>/original-runs/<unix time>/game/`, so what the game writes stays in its run, adds what the install creates beyond the game files (docs/formats/gog-install-additions.md): the support data `user.ltx` and `traffic.net` in the user folder, the registry values (imported from the run's `install.reg` into the view 32-bit programs read; `wine.log` lists the install key in both views) and the empty `userdocs` folders; the Wine prefix's Documents folder is the run's `documents/`, so the game's user folder and logs land there. It starts the launch task (`bin/XR_3DA.exe` in `bin`) with `--skipmemcheck -silent_error_mode -nosound -ss_tga -ltx steer.ltx` (docs/behavior/steering-the-original.md), `steer.ltx` being the fidelity views' file (`tests/fidelity/views.rs`'s `user_ltx`: the shipped `user.ltx` with full screen at 1920×1080, the best-quality settings and silent volumes), on a 1920×1080 Xvfb display (Wine offers the display's size as a mode, which the game keeps in full screen only when it lists it: display-mode.md A.5). Every 5 s it saves the display as `frames/<seconds>s.png` (from Xvfb's `-fbdir` framebuffer file; dialogs and errors are drawn there too), and after SECONDS (default 300) `frames/final.png` and the Wine user's folder (`prefix/users/`), then stops the container; with `--quit` it first ends the game normally by typing its `quit` console command into the display (`xdotool`), which writes the game's log (`documents/STALKER-SHOC/logs/`) and rewrites `steer.ltx`, and waits up to 60 s for it to exit. Wine's output is `wine.log`. The game shows its logo videos from about 20 s and its title menu by about 65 s (measured). `--new-game` adds `-start server(all/single/alife/new) client(localhost)`: the loading screen from about 25 s, the New Game intro from about 55 s and play from about 240 s (measured). Everything in the run folder is game assets: never committed, published or deployed.

`bazel build //tests/fidelity:frames` captures the original's frame of each fidelity view (`tests/fidelity/views.rs`) into `fidelity/<view>.png`, with the configuration file the run started from (`<view>.user.ltx`) and the one the game rewrote when it quit (`<view>.saved.ltx`; a run that did not rewrite it fails), as actions: Bazel captures a place again only when its inputs change (docs/architecture/build.md, Game data); `//tools/xtask:capture title|level OUT` is the procedure. The title menu: a run without a level, captured at 130 s, then `quit`. The New Game views, in one run (`tools/xtask/src/original/views.rs` cites the spec's sections): camera tracks written to the saves folder, `-start` a New Game, the intro waited out (nothing pressed: whether it can be skipped is unestablished), each start view captured at its `seconds` after play starts (every New Game view's frame is the game's own screenshot without its HUD, which it draws over every displayed frame of a level, a track's too: `demo_record recorder` typed into the console starts the camera recorder from the view, its F12 key draws one frame with every HUD switch off and saves it, also as TGA, and Esc ends it, steering-the-original.md 5.1; the display at that moment, HUD included, is kept as `display/<view>.png`; console lines are typed a key every 250 ms, as faster keys were lost at the game's frame rate; a failed capture keeps its run folder and names it) (before any track: a track's precache of 50 frames shows black, 80 to 95 s at the views' settings, measured), then each track view's `demo_play <view>,4` typed into the console 120 s before its `seconds` (its 15 keys held for 60 s of track time), the display polled until it is black and then until it is no longer black (the precache over) and captured at its `seconds`, at least 10 s after the precache; then `quit`, with no precache pending (quitting during one crashes at exit, exit code 5, which fails the task). A black capture is not kept.

### Setup

- Bazelisk (`brew install bazelisk`): it runs `.bazelversion`'s Bazel through `tools/bazel`, which downloads the Rust toolchain, the crates, wasm-bindgen and the wasm32 LLVM.
- `cargo-deny` (the licence check), and rustup's cargo for its advisories (`update`).
- Google Chrome.
- Xcode with an iOS simulator runtime.
- Apple's `container` (for `wine`, `original` and the fidelity captures).

### Dev server

Mimics GitHub Pages (served under `/volya-engine/`, the app's page without custom headers; every other response with COOP and COEP, so test pages, which run without the service worker, are cross-origin isolated, docs/architecture/web-platform.md, Isolation) and serves the browser suites: `bazel run //tools/devserver` (the unoptimised test site, `//platforms/web:site_dev`), then open `http://localhost:8080/volya-engine/`. Opening `/volya-engine/__test/<suite>.html` runs that suite and prints its report in the server's terminal.
