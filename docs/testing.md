# Testing

## Strategy

The game renders to an opaque WebGL 2 canvas, so DOM-level tools can't see it. Tests go through the engine, not the page.

1. **Native Rust tests carry most of the weight**: formats, VFS, importer, simulation, scripting, save/load. The simulation is single-threaded and deterministic, so tests feed scripted input, step N frames and assert on state, headless.
2. **Rendering** is checked only where the renderer draws, in headless Chrome's WebGL 2 (the user: the Mac is not a target): the render self-test (`volya-engine-render`'s `selftest` module, run by the `render` suite through `render_selftest`) draws scenes of synthetic data, reads them back and compares them pixel by pixel with a tolerance. Committed references use only synthetic content; references rendered from game data stay local, like the data itself. Fidelity against the original is judged in headless Chrome (WebGL 2 through ANGLE on the Mac's GPU, BC textures as stored), never with ETC2 textures, which differ slightly from BC by design (#113, decided by the user). The self-test checks BC textures by every path the device has (as stored, ETC2, RGBA8; `Renderer::set_texture_path`; headless Chrome has all three), the build translates every program to GLSL ES 3.00 (`build.rs`), the ETC2 encoder is checked against a decoder written apart from it from the specification (`etc2::decode`, test-only, and for other crates' tests behind `volya-engine-formats`'s `etc2-decode` feature), a level's geometry uploaded in steps draws as one uploaded at once (`selftest/world.rs`), and with game data the `render-level` suite draws the level by each texture path against BC's picture and holds a loading for prepared textures and its world, and `volya-engine/tests/transcode.rs` transcodes the level's textures, with its time reported and PSNR per kind of block held to floors 0.05 dB below the encoder's (run it with `--release` for meaningful times).
3. **The engine test interface** (#14) lets tests inject input, step/pause frames, query state and read back the framebuffer: a direct API natively (`volya_engine::test_api`), and in the browser `await volya.call(op)` (plus `volya.status()`), which messages the engine worker and resolves with the op's JSON result. Ops live in `call` in `platforms/web/src/lib.rs`.
4. **Browser tests are thin** and cover only platform integration: startup, worker, WebGL 2 on `OffscreenCanvas`, OPFS, input forwarding, service worker. No WebDriver: each suite has a page, `tests/browser/<suite>.html`, served by the dev server at `/volya-engine/__test/<suite>.html` (never deployed). It starts the unchanged app, runs the suite and POSTs a report to the dev server, which fails on timeout; the suite's test (`xtask suite`) opens `__test/run/<id>/<suite>.html` so reports match runs. Input is synthesized in-page; import tests feed the installer, served with HTTP range requests, through the same import path as picked files. The native file picker and gestures are not covered by automated tests.

## Tooling

All testing is local, and every test is a Bazel target (docs/architecture/build.md), its result cached and shared by every worktree. `bazel test //:checks` runs fast static checks (SPDX, licences, fmt, clippy) and gates every push. `bazel test //...` runs every test that isn't `manual`: the static checks, unit and game-data tests and the smoke, platform, render and import suites on Chrome. A browser suite is `//tests/browser:<suite>_<target>` (dashes as underscores, e.g. `bazel test //tests/browser:render_level_chrome`), the rest `manual`; `:chrome` and `:iphone` name every suite on a target, `:game_chrome` the game suites.

| Layer | How | Where |
|---|---|---|
| Native tests | `bazel test //crates/...` | Mac |
| Browser suites | `tests/browser/<suite>.js`, run by `harness.js`; the dev server serves them under `/volya-engine/__test/`, never in `dist/` | Headless desktop Chrome (audio allowed without a gesture); Mobile Safari in a dedicated `Volya Engine iPhone 17 Pro Max` simulator (created on first run, left booted; Safari quit with its tabs deleted before and after each suite and `sim` run, and by a helper process if the run dies, as an open suite page holds its GPU memory; Safari's website data deleted before and after each suite, so every suite starts from empty storage) |

Add a browser suite by creating `tests/browser/<suite>.js` exporting `tests` (name → function, may be async), a `<suite>.html` page calling `runPage("<suite>")`, and listing it in `SUITES` in `tools/xtask/src/e2e.rs` and in `tests/browser/BUILD.bazel`. A test may return a string note for the report. Suites are silent on the machine running them: Chrome runs with `--mute-audio`, and `harness.js` puts a gain of 0 between anything and a live `AudioContext`'s destination (the iOS Simulator plays through one of the Mac's output devices and CoreSimulator accepts no route to none: measured, it falls back to the default device); suites measure audio before that gain, through the AudioWorklet into an `OfflineAudioContext`, and the context's state is unchanged by it. Tests report what really happens. In the iOS Simulator the app's BC textures are transcoded to ETC2 (no BC there), and the `render` and game suites check pixels there too.

`VOLYA_DUMP_DIR=<dir>` keeps the frames suites dump, the browser's `VOLYA_DUMP_*`: `dump(name, capture)` (`harness.js`) encodes a `debug_capture` as PNG on the page and posts it to the dev server (a browser suite's runner or the dev server), which writes it to `<dir>/<suite>/<name>.png` (keep it outside the repository); without the variable nothing is encoded. Suites that draw game data (`KEPT_PROFILE` in `tools/xtask/src/e2e.rs`) run in Chrome with a profile kept for the machine in `~/Library/Caches/volya-engine/chrome-profile/` (one Chrome at a time, under a lock), served on one fixed port (storage belongs to an origin; a profile holding another origin's storage is deleted), and import only what its storage lacks, so the game is imported once; delete the directory to import afresh. The `import` and `game-startup` suites keep fresh profiles, as they test the import; the other game suites start from the kept import.

`VOLYA_SIM_MEDIA=<dir>` (`--test_env`) makes each iphone suite record itself (H.264) and screenshot its end into that directory (keep it outside the repository); `bazel run //tools/xtask -- simshot [path]` takes a screenshot of the test simulator and `bazel run //tools/xtask -- simrec <path> <seconds>` records it.

### Shared conformance checks

Behavior every backend must share is written once in Rust and run on each backend: e.g. `vfs::conformance::check` runs natively against `StdVfs` and, via the `vfs_selftest` op, against the OPFS VFS in the engine worker on every browser target; `volya_engine_script::selftest::check` (the runtime's libraries, number formatting, strings, tables, errors, coroutines, `jit`, the Rust API, C-style comments and the script loader on files of its own) runs natively and, via the `script_selftest` op, in the wasm build in the `platform` suite; `volya_engine_core::physics::ode::fall_check` (the physics solver steps a falling body within 0.1 mm of the closed form) runs natively and, via the `physics_selftest` op, there too. Natively, `volya-engine-script` also compares our wasm `printf` and `strtod` with the system's. Math functions are not compared: wasm takes them from Rust's compiler-builtins (a port of musl's libm), the native build from the system's libm, and the two may differ in the last bit of a result (believed, not measured), so the self-test checks math to 6 decimals.

### Real touches in the simulator

`bazel run //tools/xtask -- sim STEP...` drives Safari in the test simulator with real touches (`tools/simdriver`, an XCUITest; no window, no extra permissions), for what in-page synthesized input can't reach: system sheets such as the file picker, iOS gestures, the path from the screen to the page. Steps: `open <url>`, `wait <s>`, `tap <x> <y>` (screen points), `tap-text <label>`, `hold <x> <y> <s>`, `drag <x1> <y1> <x2> <y2>`, `double-tap <x> <y>`, `pinch <scale>` (two fingers on the page; a pinch doesn't always zoom an unguarded page, so repeat it), `expect-text <label>`, `screenshot <path>`. A step that fails stops the run with the reason. Example: `bazel run //tools/xtask -- sim "open http://localhost:8080/volya-engine/" "tap-text Play" "wait 3" "screenshot /tmp/s.png"`. Browser zoom (docs/architecture/web-platform.md) is checked against real gestures with `tests/browser/gestures.html` (not a suite; its flags and output are in the file), e.g. `bazel run //tools/xtask -- sim "open http://localhost:8080/volya-engine/__test/run/1/gestures.html#play+controls" "wait 3" "double-tap 220 600" "pinch 3" "wait 1" "expect-text scale 1.00"`. What WebGL 2 holds per resource is measured with `tests/browser/webgl-memory.html` (not a suite; its experiments are in the file) while sampling `footprint` of the Simulator's processes (#443). XCUITest can't hold independent fingers on different spots at once; multi-finger input stays covered by in-page tests. Files for pickers go in the simulator's "On My iPhone" folder: the `File Provider Storage` directory of the `group.com.apple.FileProvider.LocalStorage` app group in the device's data.

### Direct3D 9 probes

`tests/d3d9probes/` holds small Direct3D 9 programs of our own, no game data, each isolating one documented rule at its edges on synthetic scenes: texel centres and the half-pixel offset, rasterization, bilinear weights, mip selection and LOD bias, anisotropy, BC1/BC3 decoding, alpha test, blending, fog and the gamma ramp (each file's header lists its cases). They build into one executable, `d3d9probes.exe` (llvm-mingw's i686 clang, static, no link timestamp, against the Universal C Runtime, so Windows 10 or later: `bazel build //tests/d3d9probes:exe`, `@llvm_mingw`), which writes `results/<probe>/<case>.png` (RGBA, alpha kept), `results/info.txt` (adapter and capabilities) and `results/scenes.bin`, the log of every case's states, textures and vertices that a replay through our renderer draws (format in `probe.h`). It prints a line per failed Direct3D call and exits with 1 if any failed.

### Direct3D 9 probes on real hardware

The probes run on real Direct3D 9 hardware on demand: on the user's Windows PC, by a Claude Code session there (Remote Control), from these steps. The runner is a zip of `d3d9probes.exe` and `README.txt` (`bazel build //tests/d3d9probes:runner`), published as the asset `d3d9probes.zip` of a GitHub prerelease of this repository tagged `d3d9probes-<12 hex digits of its SHA-256>`, so no binary is committed: on the Mac, `bazel run //tools/xtask -- d3d9probes release` builds it and publishes it unless that release exists, then prints the tag and the download URL. Run it after changing the probes, from `main`. The results come back as a commit on a branch: synthetic frames, no game data.

On the Windows PC, in PowerShell, with `git` and `gh` signed in to an account that can push to `mmotorny/volya-engine`, from the desktop of the logged-in user (the program opens a small window for its device):

1. The newest runner's tag (or the one the requester named):
   `$tag = gh release list --repo mmotorny/volya-engine --json tagName --jq '[.[] | select(.tagName | startswith("d3d9probes-"))][0].tagName'`
2. Download and unpack it into a fresh folder:
   `$run = "$env:TEMP\$tag"; Remove-Item -Recurse -Force $run -ErrorAction Ignore; gh release download $tag --repo mmotorny/volya-engine --pattern d3d9probes.zip --dir $run; Expand-Archive "$run\d3d9probes.zip" -DestinationPath $run`
   (without `gh`: `Invoke-WebRequest https://github.com/mmotorny/volya-engine/releases/download/$tag/d3d9probes.zip -OutFile "$run\d3d9probes.zip"` into the created folder.)
3. Run it, keeping its output as bytes (`cmd`, not PowerShell's redirection, which writes UTF-16):
   `Set-Location $run; cmd /c ".\d3d9probes.exe > log.txt 2>&1"; $LASTEXITCODE`
   It takes seconds. 0: every Direct3D call succeeded; 1: some failed, named in `log.txt`; bring the results back either way. `results\info.txt` names the adapter.
4. Commit the results to a new branch from `main`, in a clone of the repository (`git clone https://github.com/mmotorny/volya-engine.git` if there is none), under `tests/d3d9probes/hardware/<gpu>/` as the runner wrote them (`results\` and `log.txt`), `<gpu>` the adapter in lower case with dashes (e.g. `rtx-4090`):
   `git fetch origin; git switch -c d3d9probes-hardware-<gpu> origin/main`
   `$dest = "tests\d3d9probes\hardware\<gpu>"; New-Item -ItemType Directory -Force $dest; Copy-Item -Recurse "$run\results" $dest; Copy-Item "$run\log.txt" $dest; Set-Content -LiteralPath "$dest\release.txt" -Value $tag -NoNewline`
   `git add $dest; git commit -m "D3D9 probes on <adapter>: results of $tag" -m "Part of #578"` (`tests/d3d9probes/.gitattributes` keeps the files' bytes as written, CRLF included)
   `git push -u origin HEAD`
5. Report the branch name and the exit code. A session on the Mac lands the branch; `hardware/<gpu>/` is then one of the suite's references.

### The probes through our renderer

The `d3d9probes` suite (#588, Chrome only, `manual`: `bazel test //tests/browser:d3d9probes_chrome`) replays each reference's `scenes.bin` through our GL layer and compares the frames with that reference's PNGs. Its references are `//tests/d3d9probes:references` (`build/d3d9probes.bzl`, served as the suite's references): `d3d9probes/<gpu>/` from each `tests/d3d9probes/hardware/<gpu>/results/` committed, in the order `references.json` lists them. The replay (`volya-engine-render`'s `d3d9probes.rs`, the `d3d9probes_replay` test op, on a WebGL 2 context of its own) draws each case into an RGBA8 target of its size with the probe program (`probe.wgsl`) and makes our renderer's choices where it has them: the alpha test compares `a · 255` with the reference, as our programs' `a · 255 <= ref` discard does for GREATER; the LOD bias goes through `textureSampleBias`; vertex fog blends with a factor computed at each vertex, clamped and interpolated (the specular alpha); FOGTABLEMODE LINEAR, which the original never enables (static-shading.md 9.3), is computed per pixel on the pixel's z, as Direct3D 9's table fog; the gamma ramp read back goes through `RampPass` (entry `round(v · 255)`, then the target's rounding, where the probe's CPU mapping takes `ramp[v] >> 8`). Positions are moved half a pixel (window = Direct3D position + 0.5: Direct3D 9's pixel centres are at integer coordinates; our UI and world programs make no such move). A state the replay doesn't model, at a value other than the one it assumes, fails that case. The suite decodes the PNGs itself (no canvas, which premultiplies) and reports per probe and case the pixels differing in any channel (RGBA), the largest difference and the first differing pixel; it is a report, never a failure for a difference. With `VOLYA_DUMP_DIR` it keeps `d3d9probes/<reference>-<probe>-<case>.png` and `…-ours.png`, made opaque. A difference the specs don't explain becomes an issue through the spec route, never tuned away in code.

### The original game as a black box

The original runs unmodified on the user's Windows PC, on its real Direct3D 9 driver (docs/clean-room.md, Sources), never on the Mac. Its frames of the fidelity views are `//tests/fidelity:frames` (`build/original_frames.bzl`): the files in this machine's `~/Library/Caches/volya-engine/original-frames/fidelity/` (`<view>.png`, the configuration file the run started from, `<view>.user.ltx`, and the one the game rewrote when it quit, `<view>.saved.ltx`), watched, so new frames rerun the suite; without the folder the suite reports every view as having no frame of the original. Game assets: local only, never committed, published or deployed. The frames there now came from a software renderer (Wine's Direct3D 9 in a headless VM, retired) and are to be replaced by captures on the Windows PC.
