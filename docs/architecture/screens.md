# The game's screens

The game's own interface, drawn by the engine (`crates/volya-engine`). The app's own interface (home, import, Settings) is the page's: [web-platform.md](web-platform.md#the-page).

## Fatal errors

- What a spec makes fatal is fatal here, never recovered from (AGENTS.md). While a level loads, the error fails the load. Otherwise it is kept and taken by `App::fatal` at the end of the update: the game ends, as when loading fails, and the title menu says why.
- Routed there: the level (sound rules, the simulation's switch pass, a placed effect's group), the sound system's frame, the New Game intro, the inventory screen, the menu's screens (one that fails to open, a message box the data lacks, a save's menu data), fonts, and building a frame (`App::scene`: a missing texture, a font, text layout). `App::scene`'s `ErrorKind::Unsupported` (a layout our decoders lack) is not fatal.
- An error from the title menu itself, which already says why, leaves the menu as it is rather than opening it again each frame.
- Failures of the platform (storage, GPU uploads, the presenter's reads) aren't the original's and stay recoveries of the app shell; a storage read failing while drawing is fatal through `App::scene` (#339).

## Settings

- The options screen's settings and the key bindings live in a console (`volya-engine-core::console`): every command of docs/behavior/console-commands.md with its kind, range, built-in value, status and help text, the 77 actions' bindings, the line processing, `help`, and the saving rule; an unknown name prints `! Unknown command:` and is not kept. It holds the log of docs/behavior/console-log.md (`console::Log`: how a text becomes lines, the message forms, `flush` and `clear_log`), its own lines and the rest of the engine's (`App::fatal` writes the error), for whoever shows them. The diagnostic commands of docs/behavior/console-diagnostics.md print their lines from the figures and counts the program's parts measure as a line is printed (`console::Meters`, set once by the platform: on the web the wasm heap's live bytes, the wasm memory, and the renderer's resources, docs/architecture/memory.md); `App` writes a load's phase lines and, after the platform released the renderer's resources (docs/architecture/memory.md, GPU memory), the shutdown's resource counts with any resource left by name. The actions whose effects are other specifications' are its caller's. The log file's bytes are made on every occasion of console-log.md 3.3 that exists here (the console's setup, `flush`, `clear_log`, quitting, `App::fatal`) and handed over by `App::take_log_file`, which the web platform stores (below). The installer's `user.ltx` read and saved again is written byte for byte as shipped (`tests/options.rs`).
- The user configuration file (section 12) is Volya Engine's own `user.ltx` in the OPFS namespace beside the imported game, never written into the game's files. Without one, the installer's copy in the game root (`__support/userdocs/user.ltx`) is read. It is stored when the options screen closes and when the player quits from the menu: the original stores it only at exit, but a browser tab is usually closed without one.
- The game's log file (docs/behavior/console-log.md 3) is always kept, byte for byte, as `logs/xray_player.log` in the OPFS namespace (`$logs$` under `$app_data_root$`; a fixed user name, as a browser has no Windows account; decided by the user, #646), written on 3.3's occasions that exist here (a game's start, `flush`, `clear_log`, quitting, `App::fatal`) through its own sync access handle, opened and closed for each write, latest write last, `logs/` created when missing. A write that can't open it adds 3.9's line, naming `volya-engine\logs\xray_player.log`, to the log while the game runs. After a fatal error the report only: a browser has no stack trace of the game (3.3). `-nolog` has no command line here. The app's Settings offers it with the diagnostic log in Download logs, and Delete saves, settings, and logs deletes it (#669, [diagnostics.md](diagnostics.md)).
- The console window of docs/behavior/console-window.md is `volya-engine::console_window`, drawn over the frame below the statistics overlay. It opens with a key bound to `console` over the title menu, over the menu in a game and over a level whose controls are live (not under the loading image, our choice, as the menu). While it is open it takes every key, and the receiver below gets nothing: the releases of what was held as it opens, and the game's cursor stays where it was. When it closes, the level gets presses of the held keys of 3.4. A held Shift is released as it closes (3.4's reading of the dispute with console-input.md, #630). While it is open the level's controls are not live, so the page releases pointer lock and hides its touch controls; opening it by touch is #642. Insert's clipboard is read on the page and sent with the press (#639). Entered lines run in the console, and its actions are #647.
- What the settings do: `vid_mode` sets the size drawn at (at the video restart Apply and Cancel run; [rendering.md](rendering.md#the-canvas-and-the-video-mode)); `snd_volume_eff` and `snd_volume_music` the mixer's effects and music volumes, at once; `mouse_sens`, `mouse_invert`, `g_always_run` and the bindings the player's controls, of a running level too once applied; the `quit` binding which key skips movies; New Game sets `g_game_difficulty`; `rs_c_gamma`, `rs_c_brightness` and `rs_c_contrast` the display's gamma ramp, at once; `r__supersample` the off-screen target (at the video restart, as `vid_mode`); `r__detail_density` the detail objects of cells built from then on ([rendering.md](rendering.md#presentation-and-gamma), [rendering.md](rendering.md#detail-objects)); `rs_vis_distance` the far plane, every frame; `r__geometry_lod` (with `r1_ssa_lod_a`, `r1_ssa_lod_b`) the size thresholds, every frame; `texture_lod` the textures loaded from then on, `r__tf_aniso` and `r1_tf_mipbias` the samplers ([rendering.md](rendering.md#textures)); `r1_dlights`, `r1_dlights_clip` and `r1_glows_per_frame` the lights and glows, every frame; `r1_lmodel_lerp` the projected light's fade, every frame; `rs_fullscreen` the page's full screen ([input.md](input.md#the-options-screens-full-screen)); `rs_stats` the statistics overlay (display-mode.md part B, `volya-engine::statistics_overlay`: the frame, the engine's update, the drawing and the sound measured, the draw calls counted, every other value 0). `rs_refresh_60hz` and `rs_v_sync` have nothing to act on (the browser presents once per display refresh, as display-mode.md A.8). `r2em on` and `off` switch the console's material message, printed after a number while on (console-misc-settings.md 9; nothing draws by it). Of console-misc-settings.md's other settings, `g_eventdelay` has no observable effect and `snd_acceleration` no counterpart in a browser; `g_autopickup` and `g_corpsenum` act only in multiplayer games (#629), `cl_cod_pickup_mode` waits for taking items and the HUD (#627), `cam_slide_inert` for the look cameras (#628). `check_for_updates` prints only the original's failure to send the query, `! Unable to send query for patch!`: the original's patch service is not reachable from the web build. The other settings are shown, edited and stored only.
- The options screen opens from the title menu and from the menu during a game.
- A deviation decided by the user (#364): Volya Engine draws only the static renderer, so the renderer list's dynamic entries, `renderer_r2a` and `renderer_r2`, are disabled (`options::DYNAMIC_RENDERERS`): drawn as options-screens.md 4.6's disabled rows (text alpha 128), never chosen by mouse, touchpad or gamepad (the list has no keyboard control), so the restart message (section 10) doesn't open. A stored `renderer` naming one (a `user.ltx` written by the original) is kept as written and shown as `renderer_r1`, without counting as a change, so Apply doesn't rewrite it. The controls enabled only with entries 1 or 2 (section 6.3) stay disabled. The dynamic renderers: #385.

## The menu during a game

- The key bound to `quit` (and a gamepad's east button, the touch Menu button, and losing pointer lock, since the browser takes Escape to leave it) opens the menu over the level once the loading image is gone. Asked for while the image covers the level's first frames, it opens in the first frame the player's controls are live, after the intro (a Volya Engine addition, decided by the user, #96; presses during the intro skip it). On the menu's main page the key closes it again (`volya-engine::menu_screens`, docs/behavior/save-load-screens.md section 2).
- The level stays loaded and paused; its world stays in the scene, covered, so its GPU copy is kept while nothing of it is drawn.
- The save and load screens and the boxes are mouse screens; touch reaches them through the touchpad, gamepads through the options screen's mapping (`volya-engine::dialog`). Typing a save's name: [input.md](input.md#text-entry-without-a-keyboard).

## Saved games

- Saves live in `savedgames/` of the OPFS namespace (`$game_saves$`, beside `user.ltx`), behind the product's `SaveFiles` trait.
- The engine worker (`platforms/web/src/game.rs`) lists it when the game starts: every file with its modification time, and for the `.sav` files in it the first 8 bytes (all the validity test needs) and a `File` snapshot, from which the load screen reads a selected save synchronously (`FileReaderSync`). No access handle is held, so another copy of the app can delete saves meanwhile; a stale snapshot fails to read and counts as invalid.
- Files the player deleted come back through `App::take_deleted_saves`; the worker removes each, one file at a time, never a directory.
- Writing and loading saves: #75 (`TODO(#75)` in `volya-engine::save_load`).

## The inventory screen

- docs/behavior/inventory-screen.md, in `volya-engine::inventory_screen` (#110). Its layout is loaded when the level is made (the `_16` rule of that moment); the moves between places act on the player character's inventory (`volya-engine-core::character::inventory`). Its open parts: #111.
- The key bound to `inventory` opens it over the running level (a gamepad's north button and the touch Inventory button too: our design); the game is not paused.
- While it shows, only the keyboard's keys it doesn't use reach the character (`Controls::keys_only`); mouse, wheel, gamepad and touch are the screen's. The level's controls count as stopped, so the page hides its touch controls, releases pointer lock (the cursor follows the absolute pointer; an exit the page makes releases no held key and opens no menu, so a held W walks on) and turns touch into the touchpad.
- The quit key closes it (the spec's Escape); the page being hidden opens the menu over it, as in a level (our choice).
- The `debug_give_item` op puts an item into the inventory with an id from the simulation's pool (test builds only: the `test-ops` feature of `volya-engine-web`, which `cargo xtask e2e` and `web --dev` enable and the deployed build lacks).
