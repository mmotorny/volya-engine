# Rendering

`crates/volya-engine-render` draws; `crates/volya-engine` turns screens into scenes and draw lists (`scene.rs`, `present.rs`); `platforms/web/src/gpu.rs` owns the device and the canvas.

## WebGL 2

The browser renderer draws through WebGL 2 only (decided by the user, #449), with its own GL layer ([The GL renderer](#the-gl-renderer)). Its drawing is tested in headless Chrome only (docs/testing.md).

- The engine worker draws on an `OffscreenCanvas` transferred from the main thread (`gpu.rs` `connect`). The iOS Simulator's WebGL 2 has ETC2 and ASTC, no BC (measured).
- `status().gpu` reports how BC textures reach the GPU (`bc`, `etc2`, `rgba8`). Without WebGL 2 the engine still starts, without graphics: `status().gpu.state` is `unavailable` with a `message`, and the page shows "This browser can't run the game" with it.
- WebGL 2's vertex programs have no storage buffers and its draws no base vertex. The world reads its per-draw records from an RGBA32F texture (9 texels a draw, 64 draws a row; `world.wgsl`'s `record`), indexed by instance. Index ranges are rebased at upload: each range a draw uses is written with the draw's first vertex added (a range used from two first vertices is written twice), 32-bit where they pass 16 bits; draws then start at vertex 0. The objects' ranges stay 16-bit: each is written relative to a first vertex within 16 bits below its own, which its vertex array's attribute offset supplies (one vertex array per first vertex); 32-bit only for a draw whose own vertices pass 16 bits.
- WebGL's cost is per call (about 1 µs in the iOS Simulator, 0.07 µs in headless Chrome; measured with `debug_gl_calls`, #429), so the GL layer calls WebGL only for state that changes ([State tracking](#state-tracking)). A surface's textures are two sets, each bound only when it changes: its light maps and environment map (shared by many surfaces), then its base and detail textures.
- The canvas's WebGL 2 context is made by the platform without depth or stencil (the renderer draws into its own textures and blits the frame into the canvas): the default framebuffer's depth buffer would take canvas-size memory nothing reads ([memory.md](memory.md#gpu-and-javascript-memory), #443). The first vertex provokes (`WEBGL_provoking_vertex`): with WebGL's last, ANGLE's Metal backend rewrites the indices of every draw whose program has a flat varying into a buffer of its own, all held until the submission finishes (#443).
- WebGL copies uploads at each call (documented, WebGL 2 specification), so nothing waits in the wasm heap for the GPU, and a WebGL sync object never signals in the task it was issued (documented, same). Uploads still go in pieces with waits for the GPU between them (a fence, polled each task turn), for the GPU process's memory on the phone (#443): the level's geometry after each 2 MiB piece, the textures before one would take what is written since the last wait past 2 MiB (`Renderer::texture_bytes_written`).
- The build translates every program from WGSL to GLSL ES 3.00 with naga (`build.rs`, into `glsl::STAGES` with each program's samplers and uniform blocks), so a program WebGL 2 can't run fails the build (#468) and no shader translator ships.

## Textures

- Textures upload as stored: BC when the GPU has `texture-compression-bc` ([game-data.md](game-data.md#original-formats-no-conversion)). Every level is written in bands of rows of at most 2 MiB.
- Without BC they are transcoded at run time to ETC2 (`volya-engine-formats::etc2`, our encoder from the Khronos Data Format Specification: BC1 to RGB8, or RGB8A1 when the texture has cut-out texels; BC2 and BC3 to RGBA8 with EAC alpha); with neither BC nor ETC2 they are decoded to RGBA8.
- ETC2 over ASTC (#113): ETC2 takes BC's memory (127 MiB of textures for `l01_escape` either way, measured natively); ASTC 4×4 takes 64 % more (BC1's 4 bits a texel become 8) for a difference visible only magnified; ASTC 6×6 is worse than ETC2 and slower (measured with astcenc on the level's textures).
- The encoder fits every texel's colour whatever its alpha: the game's alpha is often data (light maps keep a lighting term there). Method (#183): it works from a BC block's four colours, judges ETC1 tables and T/H candidates along the grey axis (as etcpak's table search), tries planar only where the best unquantized plane could win and T/H only where the error is large and the colours differ in hue, and walks T/H distances outwards while they improve (QuickETC2, Nah 2020). `volya-engine/tests/transcode.rs` holds its quality to floors per kind of block.
- The release build compiles `volya-engine-formats` at `opt-level = 3`, about twice as fast as `"s"` for the encoder (measured natively).
- Transcoding stays on the engine worker, decided by the user: transcode workers only if the encoder alone leaves a load well above a few seconds.
- Nothing is stored: every load transcodes again, decided by the user, as stored transcodings would take as much storage as the BC textures (133 MB for the first level, 2.05 GB for all the game's BC textures; measured), too much on a phone on top of the game. Textures outside a level's preparation (the menus') are transcoded when first drawn.
- Texture quality (docs/behavior/texture-quality-filtering.md part 1, `volya-engine-core::texture_quality`): a 2D texture loses its top levels by `texture_lod` and `[reduce_lod_texture_list]` as it is read, prepared or by the presenter (`Scene::texture_quality`), so a level's textures take the value at its load and the menus' keep theirs; a video restart reloads none. A block-compressed top level smaller than whole 4 × 4 blocks (a small file's lower levels) is decoded to RGBA8, the same texels: WebGL takes compressed textures only at multiples of 4. At `texture_lod` 4 the start view's textures take 34.7 MiB against 127.1 (headless Chrome, `render-level`, measured).
- Texture filtering (part 2): the maximum anisotropy and mip bias in force, the settings after each execution of either and the engine's 4 and −0.5 after each device reset (an Apply or Cancel of the options, every level's start; `SamplerStates`), reach each frame (`Scene::filtering`, `WorldFrame::filtering`): the anisotropic samplers (the world's base and detail, the grass, the clouds, the particles') are taken at it from the sampler cache, and, WebGL 2's samplers having no level-of-detail bias, the programs sample every mipmapped texture with `textureSampleBias`. The options screen is written when it closes (our choice), which is not the original's status read at shutdown, so it applies neither variable.

## Level preparation

Always (`textures::wanted`; #184, #355): the browser's GPU process copies what the engine hands it later, so uploads made at the level's first frame stalled that frame's presentation on an iPhone (believed, from its diagnostic log).

1. A New Game's loading waits under `st_loading_textures` once its work is done (`App::set_prepare_textures`, our addition) while the platform prepares the level's textures, about 30 ms of them per task turn so frames run between and the loading screen keeps drawing: each is read into one buffer and uploaded in bands of at most 2 MiB, each band transcoded (without BC) into another buffer just before it is written (`Renderer::begin_texture`, `TextureUpload::step`), both buffers reused; the presenter takes them at the world's upload (`Renderer::add_prepared`).
2. Once the level is made the loading waits under its last caption while the platform uploads the level's geometry and the objects' models a few pieces per turn (`App::world_to_prepare`, `Presenter::prepare_world`, `Renderer::begin_geometry`, `GeometryUpload::step`); the placed effects' world clock receives the wait (`LevelScreen::wait`). The objects' CPU geometry goes once uploaded.
3. Each piece then waits until WebGL reports the GPU done with what was submitted (`onSubmittedWorkDone`, giving up after 30 s; `load.gpu_wait_ms`), so the copying happens while the loading image shows and the staging goes ([WebGL 2](#webgl-2)).
4. Last, the level's start view is drawn into a frame of its own that is never shown (`gpu::warm_up`, span `prepare.warm_up`), whole, the GPU waited for: the world's making and the first-draw work come before the level shows (#376). Drawing it 40 calls a turn (#437) worked around ANGLE's per-submission index rewrite, gone since #443; without the pieces the warm-up took 72–76 ms instead of 410–425 and the first caption to the first level frame 2.08–2.10 s instead of 2.50–2.57, the longest frame meanwhile 67 ms against 50–67 (headless Chrome, measured, the menu suite's `warm_up_ms`, `warm_up_frame_max_ms`; #448). The static world's merged calls draw fixed groups (at most 16 draws, drawn whole when any may show), so their index ranges are the same every frame. What the loading screen shows is unchanged.

## The canvas and the video mode

- The page sends the canvas's CSS size and `devicePixelRatio` on start and on change; the worker sizes the canvas and surface in device pixels. The frame loop runs in the worker on `requestAnimationFrame` (a 60 Hz timer where workers lack it); while the game runs its screen is drawn every frame.
- The game draws at its video mode (`vid_mode`, docs/behavior/options-screens.md section 9), not at the canvas's size: menus and 3D go to an offscreen frame of that size, drawn into the canvas scaled to fit with its aspect kept, black around it (#49). Pointer positions are taken relative to the drawn picture.
- The resolution list offers the canvas's own size and the common 4:3, 5:4, 16:10 and 16:9 sizes that fit it, at least 800 wide (the canvas's size alone if none is left); browsers expose no display modes. The page counts as windowed, in its full screen too ([input.md](input.md#the-options-screens-full-screen)), so a stored mode not in the list is used as it is.

## The static world

- `level.geom`'s vertex and index buffers upload as stored; packed attributes are decoded in the vertex programs (the vertex formats reproduce the spec's decoding).
- Its draws are encoded each frame, in a fixed order per step (priorities 0–1 and 2–3), only those that can show: the program's ssa test and the camera's frustum, each with a margin, so the programs still decide and the picture is unchanged (#415, #387). Strict-sorted draws are ordered each frame. What depends on the camera (near/far shader variants, size culling) is decided per draw in the shaders from per-draw data. The size thresholds follow `r__geometry_lod`, `r1_ssa_lod_a` and `r1_ssa_lod_b` every frame (object-detail-level.md 1): the shaders' ssa_min, the camera pass's (static visuals, billboards, portals), the effects' and the grass's.
- Index ranges are rebased at upload ([WebGL 2](#webgl-2)), laid out per index buffer by surface, vertex buffer and draw, so the draws of a surface and buffers that follow one another in a step read consecutive ranges and are merged into one draw call (#387): the same triangles in the same order. A merged draw's vertices name their own draw's record through a vertex buffer of draw ids (4 bytes a vertex) made at upload from the ranges' spans; vertices more than one draw reaches (a tree's instances) carry `SHARED`, and such a draw is a call of its own with the draw as the instance.
- A progressive visual (ogf.md 8.3) uploads the indices of every detail window and draws, each frame, the window of its sphere's measure; its call merges with no other, since its range changes as the camera moves. Light passes draw the camera's window (our choice for static visuals, #621); a cell of the projected light texture the window last drawn (object-projected-light.md 4.3). The windows are one table for the world (a `level.geom` record shared by tree instances once), each draw naming its run.
- No CPU copy of the geometry is kept: the loading stage reads only the buffers' layout, the spatial stage checks the draws' indices a piece at a time, and the presenter streams the file to the GPU in pieces of at most 2 MiB with `Queue::write_buffer`, each piece's staging freed once WebGL reports it done ([WebGL 2](#webgl-2)).
- Scripted shader definitions (Lua) are not run: the specified effect of each script the level uses is implemented directly (`shading.rs`).
- Billboard groups (docs/formats/ogf.md 7, static-shading.md 8.4; #558): their faces are kept from the level's visuals by the camera pass (`LevelVisibility`), each group's `details\lod` entry resolved to a set of two textures (the atlas and its `_nm`) with the surfaces. Each camera pass builds the quad of every group it lists for its billboard on the CPU (`BillboardGroup::quad`, six 76-byte vertices), set by set; the renderer writes them into one vertex buffer made with the level for every group (`billboards.wgsl`, `webgl/billboards.rs`) and draws them twice, element 4 before the sky and element 1 after it (static-shading.md 10.3).

## Objects

- A level's spawned objects (docs/behavior/level-objects.md) load across its stages: the switch pass under `st_server_connecting`, the model files under `st_client_spawning`, their surfaces with the level's under `st_loading_textures`, their light inputs (rays against the collision world, taken converged at once) under `st_client_synchronising`.
- Each model file is read once and shared by every object showing it; its vertices are quantized as the first renderer stores them (16 bytes: `s16` position, `u8` normal, `s16` texture coordinate) into one vertex buffer for all models, with the indices of every detail window, uploaded with the static world and then dropped on the CPU.
- Objects are drawn at rest (every vertex at its stored position, transformed per object in the vertex program) with the world's draws, with element 1 of their model shaders, or element 0 for a receiver of the projected light texture (below). Each mesh's draw carries the mesh's own header sphere, its centre placed by the object's transform and its radius as stored, so the shaders' size test drops a small part alone (object-detail-level.md 3); a skinned progressive mesh's draw chooses its detail window each frame from that sphere's measure, and the light passes draw the same window (object-detail-level.md 4). An object switching changes its instance's placement in the world's per-draw data; a hidden draw gets a bounding radius of 0, so the size test drops it.

- The projected light texture (docs/behavior/object-projected-light.md; #552): the receivers and the 100 slots are kept by the level's camera pass (`projected_light.rs`), each slot's cell as last given out with a version; the renderer keeps the 512 × 512 texture with its depth buffer for its run (`WorldPrograms`) and draws a cell whenever its version is new to it, so a frame computed but not drawn, or a new renderer, still gets every cell: the cell's pixels cleared to its colour with a scissored clear, then the receiver's sector's static draws in the cell's query box with element 4 of their surfaces (`vs_lmap_l` … in `world.wgsl`), the camera of section 4.1 in a frame-constants slot of their own. Receivers' draws hold their slot's C′, h and slot in their records (c_bias, params.x), written only when they change; the model programs (`fs_model`, `fs_model_env`) take the cell's texel where params.x is set. A cell clears to its receiver's approximate colour as of the receiver's last full update (`projected_light::Estimates`, (0, 0, 0) before any): one a frame, of the object drawn at the frame's turn among the camera pass's dynamic items, glows counted, whose sphere is not outside the view frustum (object-visibility.md 7), its tracked lights smoothed by frame time, *h* and *s* the objects' converged visibility values; the actor, drawn by no object, has none; `r1_lmodel_lerp` is read every frame (0.1 before set) and handed to the frame's constants.

## Particles

docs/behavior/particle-drawing.md (#322); the simulation: [simulation.md](simulation.md#particles).

- The frame values at birth and the frame animation are part of the simulation (they draw from the shared generator). The sprites are built on the CPU each frame from the camera (`volya-engine-core::particles::sprite`), four vertices of 24 bytes a particle, drawn without storage buffers.
- Each effect's shader is resolved with the level's under `st_loading_textures` (`particle_drawing::resolve`): class `PARTICLE` from `shaders.xr`; `particles\xadd` and `particles\xdistort`, scripted, implemented from the spec's section 5.3 (no Lua runs).
- Effect objects are chosen by the camera pass ([Visibility](#visibility)), then each effect by the screen measure.
- They are queued into the world pass as section 7.4 orders (`ParticleQueue`): `SET` after the priority 0–1 static draws; `ADD`, `ALPHA-ADD` and the scripted shaders' normal pass after the priority 2–3 ones; `BLEND` merged with the static strict-sorted draws back to front (on equal keys statics first, our choice).
- With a distortion list the world's depth is kept; the distortion target (two 8-bit channels, the red and green `postprocess_d` reads, #433; cleared to 127/255) gets element 4 of the scripted shaders back to front, depth-tested against the scene with the scene's view and projection (believed, #329); the presentation's `postprocess_d` looks the scene up at t + (D.rg − 0.5) · 0.05 ([Presentation and gamma](#presentation-and-gamma)). When every sprite of the list lies wholly outside one plane of the view volume (tested on the CPU with a margin), the pass is not drawn, the world's depth not kept, and `postprocess_d` reads a 1 × 1 texture of the clear value instead: the same picture (#433).
- The particles' pipelines (every pass the effects' shaders resolve to, with each culling) and their vertex buffer are made with the renderer and kept, the buffer grown and written with `Queue::write_buffer`: GPU objects made with a level, or buffers mapped at creation, stayed allocated amid the freed level and split the wasm heap, so the next level's collision world no longer fitted (measured, #357). At the world's upload the buffers are grown to the most particles the level's objects can hold at once (every placed record and zone, and the largest ambient effect; `Renderer::reserve_particles`), so nothing is made on the GPU while the level runs. Each sprite is six vertices (its two triangles) drawn without indices.

## Lights

The records and their sources: [simulation.md](simulation.md#dynamic-lights).

- The camera pass's camera sector, sector and portal traversal and per-sector static visuals (each node's sphere-and-box test, exact, none below a node wholly inside; occlusion-tests.md 7) are CPU work in `volya-engine-core::visibility` (level.md 9, traversal-options.md), apart from the renderer; the camera sector's ray reads each collision triangle's sector, kept by the collision world (2 bytes a triangle). Its occlusion is `volya-engine-core::occlusion` (level-hom.md, occlusion-grid.md, occlusion-tests.md): the `level.hom` mesh loaded once, the 64 × 64 grid drawn on the CPU at the start of each camera pass, and the portals' polygon test and the static visuals' cached box test (`Occlusion::portal_hidden`, `visual_hidden`) given to the traversal; about 40 µs more a frame in l01_escape, most of it the grid (release, measured). The occluder search tests each triangle against the frustum's planes rather than the original's search structure, whose extra candidates are unestablished.
- The level runs the camera pass each frame before its lights (`level_visibility::LevelVisibility`, made from the level before its visuals are dropped; the occlusion mesh read with the level): the lights are listed by it (dynamic-lights.md 4, object-visibility.md 5, 6.3): nearest first, a record's sector found by the ray of level.md 9.1 from its position, visited with a frustum its sphere meets, then the cached box test of C ± R; the light passes are made with occlusion off (occlusion-tests.md 4), and our light passes make no occlusion test.
- A surface carries its light elements (`Surface::light`: program, alpha reference, priority; dynamic-lights.md 6.1); the draws whose elements have priority 0 or 1 are listed once per world, grouped by program and surface.
- Each light pass (`WorldFrame::lights`) draws again, after the sky and before the priority 2–3 step, those whose bounding sphere meets both the light's frustum and the camera's (a superset of what the camera's pass submitted), with one of five light pipelines (`vs_light_*` and `fs_light` in `world.wgsl`) and the pass's constants at a dynamic offset of one uniform buffer. All are made with the renderer (`Renderer::new`), the constants buffer grown only past 64 passes in a frame. No storage buffer or base vertex is needed beyond the world's own.
- The positions are `@invariant` in both passes, so the light passes' depth test meets the drawn surfaces.
- Glows are particle batches (`ParticleProgram::Glow`, `Flare`; `ParticleQueue::Glow`) drawn after the strict-sorted passes, their textures loaded with the world.

## Visibility

The camera pass (docs/behavior/visibility-scope.md) runs on the CPU in the level's update, each frame before its lights (`LevelScreen::lights_frame`; a test moving the camera runs it too), with the size the frames are drawn at: the video mode, which the app gives the level before each update (`LevelScreen::set_view_size`, #566), so the first update and a test that draws once at the end cull for the frame drawn; the frame draws what it keeps (`level_visibility::Seen`, `WorldScene::seen`, `WorldFrame::drawn`).

- Static draws: those of the visuals the traversal reached in each visited sector (`LevelVisibility::static_draws`, each visual's draws listed at load), still also held to the camera's frustum and size test with a margin; a merged group with a member left out is drawn in runs without it. Light passes still draw their superset, depth-tested against what was drawn.
- Dynamic items (object-visibility.md 3 – 6): the light records, the object instances placed and the effect objects with a culling sphere, nearest first by their sphere centres in one loop: each item's sector found again from its sphere's centre when its sphere changed, the first frustum of its visited sector its sphere is not outside, then the cached box test (lights C ± R, objects their model's box under their transform, effect objects their instance's box); an effect object kept is advanced then queued (particle-drawing.md 7.1). Glows take the same sector and frusta in their own gathering (glows.md 3), which draws nothing from the shared generator.
- Without a camera sector nothing is gathered: only the sky draws.
- The portal fade (portal-fade.md): the fade list's portals, nearest first from the eye of the frame's last traversal (the last light pass's, else the camera's), as the particles' `Portal` program in queue `Fade` after the priority 2–3 step (degenerate quads carry the fan's triangles).
- A new effect's box is empty (unestablished, P2 1; our choice), so a group member playing before any particle lives adds nothing to its group's culling sphere.
- l01_escape at 1024 × 768 (`draw-calls` suite, headless Chrome, `r__supersample` 2): draw calls before → after start 1486 → 415, start-yaw-90 1506 → 414, start-yaw-180 857 → 147, start-yaw-270 177 → 98, outdoors 1229 → 404, overview 1289 → 724; WebGL calls 5157 → 2154, 5318 → 2154, 3329 → 948, 927 → 633, 3429 → 1319, 3537 → 2366; encoding 7, 7, 5, 4, 4, 6 ms → 5, 4, 3, 3, 3, 3 ms. The start view's pixels are unchanged (`render-level`'s "the camera pass keeps the draws").

## Presentation and gamma

- docs/behavior/frame-presentation.md (`volya-engine-render::present`, `postprocess.wgsl`): a level's world is drawn into an off-screen target of the game's size times √`r__supersample` per axis (rounded, clamped to 128 … 2048, made even), with its distortion target and depth buffer, when the setting is above 1 (the shipped `user.ltx` has 2: 1448 × 1086 at 1024 × 768), the screen effects are active, or the previous frame had a distortion pass; the presentation quad (`postprocess`, or `postprocess_d` after a distortion pass) reduces it onto the game's frame, offset by `r1_pps_u` and `r1_pps_v`; menus and the HUD draw onto the frame, in the presentation quad's pass when there is one, so the frame is written once (#433). The main menu with its glass lens (title-menu.md 4.6, `scene::Lens`, `MenuLens`) is drawn into the target instead, the cursor excepted: the lens's offset map `ui\ui_magnifier` into the distortion target, placed with the target's layout factors, and the frame presented through `postprocess_d` with the values in force (#571). `r__supersample` applies at the video restart, as `vid_mode`. The target is built whenever the game's size or the setting changes (`Renderer::prepare_presentation`, called by the presenter every frame, so before any level). The level hands over the identity every frame (the screen effects wait for their spec, #190); the noise texture `fx\fx_noise2` is located with the level's textures. A frame drawn straight to the screen leaves its distortion pass undrawn (its picture is not shown) but counts as one with a distortion pass. *T*_s and the world's ssa_min use the target's size.
- docs/behavior/display-gamma.md (`volya-engine-core::display`, `ramp.wgsl`): the display colour settings always equal `rs_c_gamma`, `rs_c_brightness` and `rs_c_contrast` (copied from all three whenever one is executed), so every frame takes the table of their values (`Scene::ramp`, none for the identity of the shipped values); the renderer's last pass maps every channel of the whole canvas, letterbox included, through it (entry / 65535), drawing the frame offscreen first. The warm-up re-applications set the same ramp again, which this platform never loses.
- Measured natively (`volya-engine/tests/presentation.rs`, dev profile, 1024 × 768 with readback): the start view at 2 against 1 costs no measurable frame time (65 ms, readback-bound). In headless Chrome at `l01_escape`'s start, `r__supersample` 2 against 1 and the grass drawn or not change the frame CPU (3.5 – 3.8 ms) not measurably (#415).

## Detail objects

- `level.details` (docs/formats/level-details.md; `volya-engine-formats::level_details`) is read under `st_loading_details` from a stream, its slot grid kept compact for the level's run (#411): up to three records many slots hold kept once, the rest as stored (16 bytes a slot), two bits a slot saying which, decoded on lookup; on `l01_escape` two records fill half the 523,452 slots, so the grid takes 4.4 MB instead of 8.4 (measured natively); where the codes would save less than they cost (`l12_stancia`, `l12_stancia_2`) every record is kept as stored, never more than the file's grid. The grid is one block held in the file cache under the file's path, counted against `level.details`'s share (docs/architecture/memory.md, File-backed data, rule 5), not in *h* (#692); a level without the file has no detail objects. The `[details]` sway values are read with it and the cache of docs/behavior/detail-objects.md set up (`volya-engine-core::details`, `volya-engine::level_details`); the models' shader is resolved with the level's under `st_loading_textures` (a `D_STILL ` definition, its `Alpha-blend` the alpha test; `build_details` located and prepared as the level's textures). Unestablished cases take the simplest reading (#407): a malformed file fails the load, an id past the model count leaves its part out, models with different shaders are not supported (none ship).
- The pass runs in the level's update, before its camera pass (5.2), once per engine frame (the level's update count, paused frames included), not while the world is covered (a frame without one, the menu closed in it, runs it in its scene): the cache follows the camera's cell, builds every entry when all are pending (the second frame after loading; the first draws nothing, #407) and the seven nearest pending a frame otherwise, culls by groups and entries (no near plane), tests each entry left with its cached occlusion test at the frame's view, with occlusion on as the previous frame left it and the tests' matrix of the previous drawing, the first scan drawing the grid early (5.2 step 3, occlusion-tests.md 2.1 step 3), refreshes each entry's lists every 15 – 29 frames and collects them per model and list. An entry re-initialised by a camera move hands out nothing until rebuilt. `r__detail_density` is read when an entry is built; *W* is the sound rules' (#352: without audio output it stays 0); *T*_s is the world's ssa_min.
- Drawing (`volya-engine-render::details`, `details.wgsl`): the models' vertices as the programs read them (u, v and the height fraction in 1/16384 steps) in one vertex buffer, indices rebased per model, uploaded with the world; each frame's instances (32 bytes) go to an instance-stepped vertex buffer made with the world for every instance a frame can draw (48 × 48 entries at density 0.2's 121 positions: 8.5 MiB), each draw binding its range (no first instance, no base vertex, no storage buffer). After the priority 0–1 draws and before the sky: sway 1 of every model, sway 2, still; both faces, depth less-or-equal with writes, alpha test 200, no fog, no dynamic lights.
- Measured with `l01_escape` at density 0.2: the cache around the start holds 25,774 instances (11 MB with the grid), its first update builds all 2,401 entries in 19 ms natively in release, later passes about 30 µs (`volya-engine-core/tests/details.rs`); outdoors 4,677 instances drawn in 21 draws add about 7 ms to a 1024 × 768 dev-profile frame with readback (`volya-engine/tests/details.rs`). The load's native peak rose from 80 to 91.8 MB; the wasm heap in headless Chrome after a New Game from 105–110 to 114–121 MiB (#411).

## Colour and video

- Colour values pass through unconverted (non-sRGB targets). UI blending and filtering follow docs/formats/ui-layout.md (#23).
- Video frames upload as Y'CbCr planes, are packed unconverted into the video texture on the GPU and convert to RGB when drawn, after filtering (docs/behavior/startup.md 6.6): about 0.2 ms a 876×400 frame against 1.2 ms converting on the CPU (measured natively).

## The GL renderer

There is no native GL path (the user: the Mac is not a target): the renderer talks only to WebGL 2, through web-sys's `WebGl2RenderingContext` (no glow, glutin, CGL, desktop GL or ANGLE of our own), and every test that draws runs in headless Chrome, whose WebGL 2 is ANGLE on Metal, as Safari's is. A frame can be drawn into a framebuffer it is given (WebXR's `XRWebGLLayer`) as well as the canvas: designed for, not built.

### The GL layer

`volya-engine-render::gl`, the only code calling WebGL, safe Rust over web-sys. It compiles natively too (web-sys builds for any target), so the crate's platform-free code (draw lists, culling, rebasing, transcoding) keeps its native unit tests; nothing calls WebGL natively.

|---|---|---|
| `Gl` | The context, its state cache, call counts by kind, the extensions found (`WEBGL_compressed_texture_s3tc`, `_etc`, `EXT_texture_filter_anisotropic`, `EXT_disjoint_timer_query_webgl2`, `WEBGL_provoking_vertex`, `WEBGL_lose_context`) | Once, from the canvas's context made by the platform as today (no depth, stencil or antialias) |
| `Buffer` | A `WebGLBuffer`, its size and use (vertex, index, uniform); written with `bufferSubData` | Static ones with their data; dynamic ones (UI, particles, details' instances, frame constants) with the renderer, grown only past their size, as now |
| `Texture` | A `WebGLTexture`, 2D or cube, format, size, levels; base and top level set once at creation | With its data, level by level in bands (`texSubImage2D`, `compressedTexSubImage2D`) |
| `Sampler` | A `WebGLSampler`: filters, mip filter, wrap, anisotropy | One per distinct description, cached by it, bound to texture units: no per-bind texture parameters |
| `Program` | A linked program, its uniform blocks bound to fixed binding points and its samplers to fixed texture units at link (one `uniform1i` each, once), the locations of its few plain uniforms | With the renderer, as the pipelines are now |
| `VertexArray` | A `WebGLVertexArrayObject` with the attribute layout, vertex buffers and index buffer bound | Once per (vertex layout, vertex buffers, index buffer): the level's buffers each with 16-bit indices, no merging (#429's 32-bit merge is not needed) |
| `Framebuffer` | A `WebGLFramebuffer` with its colour and depth attachments | Once per render target (the frame, the supersampled target and its distortion target, the video's packing), remade when its size changes |
| `Destination` | Where a finished frame goes: the canvas's default framebuffer, or a given `WebGLFramebuffer` with a viewport (an XR layer's, one per eye) | Each frame, by the platform |
| `Fence` | A `fenceSync`, polled with `getSyncParameter` | Per submission the platform waits on (`submitted_work_done`, `gpu.done_ms` once a second) |

A pipeline becomes a `Program` with a `RasterState` (blend, depth test and write, cull, front face, colour mask): plain values the cache compares. Bind groups go: each program's textures sit on fixed units, numbered across programs so that what stays (the world's records texture, a surface group's light maps and environment map) stays bound when the program changes.

### State tracking

`Gl` keeps what it last set: program, vertex array, framebuffers (draw and read), viewport, scissor, each unit's texture and sampler, the active unit, each uniform binding point's buffer range, blend enable, factors and equation, depth test, function and mask, cull face, front face, colour mask, clear values, and the first-instance uniform's value per program. A setter calls WebGL only when the value differs; a draw sets what it needs and nothing else. `debug_gl_calls` (wrapping the context's methods on the page side) counts the calls a frame makes.

### How the renderer's parts map onto it

- **UI** (`ui.wgsl`): one dynamic vertex buffer and its vertex array; a batch binds its texture to unit 0 (the UI sampler there once, the movie sampler for Y'CbCr) and draws.
- **Video**: the Y'CbCr planes are textures written each frame; the packing pass draws into the video texture through its framebuffer.
- **World**: the level's vertex and index buffers as stored, one vertex array per (layout, vertex buffer, index buffer); the per-draw records texture on its unit for the level's run; the frame constants one uniform buffer written once a frame; light maps and environment (a surface's first group) and base and detail (its second) bound only when they change; merged calls name their draw by the existing per-vertex draw id; a shared draw's record comes from the first-instance uniform, set only when it changes (WebGL 2 has no base instance). Index ranges stay rebased at upload, 16-bit. Objects' models are one more vertex buffer with its vertex array; their placements live in the records texture as now.
- **Sky and clouds**: their buffers and vertex arrays made with the renderer; the cube maps on their units.
- **Details**: the models' buffer and the instance buffer; a draw's instance range is the instance attributes' offset, so each draw sets those attributes again (about 21 draws a frame outdoors), the one place attributes change per draw.
- **Particles and glows**: one dynamic vertex buffer and vertex array, written once a frame; each queue's batches draw ranges of it.
- **Lights**: the light passes' constants in one uniform buffer, each pass binding its range (`bindBufferRange`).
- **Presentation and supersample**: the target's colour, distortion and depth textures in two framebuffers (the scene's, and the distortion's with the scene's depth attached), made by `prepare_presentation`; the presentation quad draws into the frame.
- **Distortion**: the distortion framebuffer, depth-tested against the scene's depth, as now.
- **Ramp and fit**: passes from the offscreen frame into the frame, as now.
- **The frame and its destination**: every pass draws into the renderer's own frame texture with positions' y flipped in the vertex programs (so a texture's first row is the picture's top), and the frame is blitted, flipped, into the `Destination` (`blitFramebuffer`). An XR destination would get the same blit per eye, or the last pass drawn into it directly.
- **Readback for tests**: `readPixels` from the frame's framebuffer, synchronous (tests only).
- **GPU timing**: `EXT_disjoint_timer_query_webgl2` where the browser has it; elsewhere none.

Context loss is the platform's (`webglcontextlost`); `debug_lose_device` uses `WEBGL_lose_context`. In WebKit `fenceSync` and `getSyncParameter` are synchronous messages to the browser's GPU process (read in WebKit's source), so a fence made right after a frame's calls waits for the GPU process to take all of them in: a frame's own fence (`gpu.done_ms`) is made at the next task turn's poll instead (`Device::on_done_later`).

### Shaders

The WGSL is the source. A build script translates each program to GLSL ES 3.00 with naga (`ADJUST_COORDINATE_SPACE` and `FORCE_POINT_SIZE`, WebGL 3.00, unchecked bounds, overrides processed), and writes each program's sources with its texture-sampler pairs and uniform blocks by name; the GL layer binds them by name at link. naga at run time, translating WGSL in the browser, would cost about 1.21 MB of wasm (385 KB gzipped): measured with a release build (`opt-level = "s"`, LTO) of a wasm library that only parses WGSL and writes GLSL ES 3.00. A program can move to hand-written GLSL if it needs what naga doesn't give.

### Tests: drawing in the browser

Drawing tests run in headless Chrome only; non-drawing checks stay native tests, each test file split so its loading, simulation and draw-list checks run without a GPU.

- **Render self-test** (#470): the render crate's scenes and their checks live in a module compiled into test builds (`selftest`) and run in the engine worker by a `render_selftest` op, as `script_selftest`; the `render` suite runs it (#471).
- **Suites by render area**, so a change runs only its own, cheapest first: `render` (synthetic scenes and the small `gamedata.dbb`; seconds), `render-screens` (the title menu, save, load, inventory and options screens, #473), `render-level` (a New Game's start view, objects, lights, a caged lamp, the torch, zones, artefacts, grass, presentation, texture quality and filtering, particles, #472; the camera pass's draws and the portal fade), `draw-calls` (#474). Their checks are Rust in `volya-engine`'s `selftest` module, run in the engine worker by `render_game_selftest` on the imported game and renderers of their own, as the render self-test is.
- **A kept import**: game-data render suites use a Chrome profile kept under `target/` between runs, so the game is imported once (a suite imports only what the profile's `import.json` lacks); the `import` and `menu` suites keep fresh profiles, as they test the import.
- **Frame dumps**: a suite posts a capture as PNG (encoded on the page with an `OffscreenCanvas`) to the dev server, which writes it to `<VOLYA_DUMP_DIR>/<suite>/<name>.png` when the variable is set: the `VOLYA_DUMP_*` variables' equivalent, never committed.
- **Reference frames**: a view whose exact pixels matter is compared with a frame the same build drew in the same run, with an earlier run's dumps (`VOLYA_COMPARE_DIR`, served under `__test/reference/`, compared on the page), or with another revision's build (the parity test); references from game data are never committed.

### The parity test

`bazel run //tools/xtask -- parity [REV]` builds the test app (`//platforms/web:site_test`) at a git revision (`HEAD` by default; a detached worktree under `target/parity/`, its own Bazel workspace sharing the caches) and from the working tree, serves both from one dev server on the kept profile's origin, and runs the `parity` suite on each in headless Chrome, one after the other. The suite runs the render checks on game data (`selftest::PARITY`: the title menu and a video, a New Game's start view and an outdoor one, its objects, lights and glows, a caged lamp's glass and glow, the torch, a campfire's and an artefact's particles, the placed distortion effect, the grass, the presentation at `r__supersample` 1 and 2, and the draw-call views with the trees blended and unblended, `Renderer::set_unblended_trees`), all at 1024 × 768. The first run keeps every frame (`target/parity/frames-base`); the second is served them as references and compares its own on the page pixel by pixel (both made opaque first), reporting the pixels that differ per view, and fails where a view its check holds exact differs: every view but the blended trees', whose blending noise doesn't repeat (#435). With no changes it checks that the views repeat. The render self-test's synthetic scenes are checked by the `render` suite instead.
