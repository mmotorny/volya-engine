# Scripts

Scripts run on the runtime the original embeds (docs/behavior/script-environment.md): the public LuaJIT 1.0.3 (Lua 5.1 alpha), interpreter only, decided in #91. Crate `crates/volya-engine-script`.

## Build

- `build.rs` with the `cc` crate: natively the system C compiler; for wasm32 the clang of Bazel's pinned LLVM (wasi-sdk's, docs/architecture/build.md; Apple's has no wasm target), which the target names in `VOLYA_WASM_CLANG`.
- Vendored files compile from a copy in `OUT_DIR`, patched by `build.rs`; each replacement must match exactly once. `csrc/volya_rand.h` is force-included before every vendored file.
- `llex.c`: the original's C-style comments (docs/behavior/script-loading.md 1), in every chunk: a case for `/` where a token can start; `//` to the next LF; `/* */` without nesting, needing no end and counting no line breaks, a `*` taken with the byte after it.
- `luaconf.h`: numbers convert to integers with the header's x86 method on every target (add 2^52 + 2^51, take the double's low 32 bits): round to nearest, ties to even, as the spec's x86 build does, with out-of-range values wrapping, where our targets' casts would truncate. String-to-number is our decimal-only `volya_strtod` (`src/libc.rs`) on every target: C99 libraries also read hexadecimal, `inf` and `nan`; Lua 5.1 alpha is written for ANSI C's. The release's other defaults stand (`string.gfind` is `gmatch`, `math.mod` is `fmod`, `table.setn` raises "obsolete"); the spec doesn't establish the original's.

## Runtime

- **No machine-code compiler.** DynASM and the x86 backend (`ljit_core.c`, `ljit_mem.c`, `ljit_backend.c`, `ljit_dasm.c`) aren't built; `csrc/volya_jit.c` implements the engine interface without them. The `jit` library keeps every function: `jit.on`, `jit.off`, `jit.debug` and per-function modes change only flags; `jit.compile` and `jit.compilesub` return `jit.util.status.ENGINE_OFF`, every function's status is `ENGINE_OFF`. `jit.util`'s bytecode introspection works; `mcode`, `mcodeaddr` and `jsubmcode` are replaced in `csrc/volya_glue.c` and raise "jit.util.X is unavailable".
- **Coco without C stacks.** Stack switching can't be done in wasm: `csrc/volya_coco.c` provides Coco's C API with plain Lua threads, and Coco's coroutine library is kept (`create`, `resume`, `yield`, `wrap`, `cstacksize`, `coroutine.coco`). A yield across a C call (metamethod, `pcall`, iterator, Rust function) raises `attempt to yield across metamethod/C-call boundary` (#100).
- **`math.random`**: one generator on every target, the C standard's example `rand` (`RAND_MAX` 32767, seed 1; `csrc/volya_rand.c`), until the original's is established (#106).
- **Libraries**: what the original's game state opens by default (spec 2.1): base, table, string, math, jit, coco; never io, os, debug or package (`open_libs`, `csrc/volya_glue.c`).
- **Errors**: Lua's setjmp/longjmp. Natively the C library's; in wasm32 LLVM's lowering to WebAssembly exception handling (`-mexception-handling -mllvm -wasm-enable-sjlj`, legacy encoding) with our runtime (`csrc/wasm/libc.c`, the `__c_longjmp` tag in `csrc/wasm/c_longjmp.S`). Legacy exception handling is in Chrome 95+, Safari and iOS Safari 15.2+, Firefox 100+ (documented, MDN browser-compat-data; measured with the `platform` suite in Chrome and the iOS Simulator's Safari); the newer `exnref` encoding needs Chrome 137+ and Safari 18.4+ (documented), so it isn't used.
- **Memory**: Lua's allocator is the game scripts' pool on every target (`lua_alloc`, `src/libc.rs`; `volya_engine_core::memory_manager::GAME_SCRIPTS`, outside *h* and reported as *g*, docs/architecture/memory.md) and aborts when memory runs out, so Lua never raises a memory error; a recoverable per-state budget is #107.
- **C library for wasm32** (`csrc/wasm`): headers and the functions the interpreter calls. `malloc` and friends are Rust's (`volya-engine-core`'s `c_heap`, shared with the physics solver's C++); `printf`-family formatting is ours on every target (`csrc/volya_printf.c`, floating-point digits from Rust's formatting, checked against the system's natively); `frexp` and `modf` are ours, other math comes from Rust's compiler-builtins (the native build uses the system's; results may differ in the last bit); ctype is the "C" locale; no files (`fopen` fails, so `dofile` and `loadfile` fail to open), stdin is empty, `print` output is discarded.

## Rust API

- `Lua`: create a state, `exec` or `compile` a named chunk, `call` a global function, `register` Rust functions. Values: nil, booleans, numbers, strings (bytes), tables, `Object` (an object with its engine part, by `EnginePart`: the object itself both ways, or a new object for a part made for one), and `Other` (functions, other userdata, threads by type name; read only).
- Lua's longjmp never crosses Rust frames: every Lua call that can raise runs in C inside `lua_cpcall` (`csrc/volya_glue.c`); Rust only reads values from stack slots C reserved beforehand (tables up to 64 levels deep, `MAX_DEPTH`; self-containing tables refused), which allocates nothing in Lua and raises nothing, and gets errors as `Result`s. A Rust function's results or error are handed back to C, which pushes or raises them; a panic in one becomes a Lua error natively (wasm aborts on panic). Engine behaviour that calls scripts in the middle of a member (a Rust function Lua calls, or a default implementation an engine call runs) re-enters the state running it with `call_kept_within`, a protected call of a kept function (the states running Rust code are a thread-local stack).

## Loading scripts

`loader`, docs/behavior/script-loading.md 2 (#109).

- `Scripts` is a game script state over the game's file trees, lent per read through `Trees` (an `Rc<dyn Trees>`, as the loader is called back from Lua), like the web platform's `with_trees`. Scripts are read from the archive tree. Drop it before the platform unmounts the files.
- Script name N is `$game_scripts$N.script`, compiled as the game builds the chunk: the file's bytes unchanged after the one-line namespace prefix (default or `-_g`); none for `_G`.
- The loader's Lua side (`src/loader.lua`) runs before any script; its entry function is kept in the registry, and scripts reach it only through C functions (the globals' `__index` handler, `prefetch`), so no Lua function of the loader, and none of the Rust functions it holds, is reachable (`jit.util` reads only Lua functions' upvalues; there is no debug library).
- `load_globals` is startup's `_G`; `load_namespace`, `exec` and `call` may load more. Failures (including an unmakeable path and a failing `__tostring`) are discarded in Lua as the original does and kept for the engine (`take_failures`). `Common` reads `script.ltx`'s `[common]` lists.
- Our choices where the spec is silent or Lua can't follow it: the fatal error can't unwind past a script's `pcall`, so the call it happens in returns `ErrorKind::Fatal` whatever scripts did, every later call does too, and every later load raises it again; its message's `namespace N: ` prefix; a non-table before the last component is fatal too; `prefetch` converts numbers and raises for other non-strings; `_G` is compared case-sensitively; an unreadable file isn't remembered as missing; chunks are named `@` plus our lowercase path relative to the game root.
- `tests/gog.rs` (`every_loadable_script_compiles`, with game data) holds the shipped scripts to this: all 437 of the Russian edition's scripts with loadable names compile except 4 that aren't Lua, none reachable (spec 4.1); the 2 under `config\` are never loaded.

## Script classes

`classes`, docs/behavior/script-api-script-classes-deriving-from-engine-classes.md (script API A, #197): the binding layer the rest of the script API registers engine classes on.

- **Where it runs.** The class system is C (`csrc/volya_class.c`): the global `class`, construction and `super`, members of script objects and class objects, `__finalize`, operators and the engine's calls into overrides, on the Lua API alone. `Lua::open_classes` opens it (`Scripts::new` does, before `_G` loads); Rust describes engine classes (`EngineClass`) and the engine calls overrides (`Lua::dispatch`); C calls Rust only through kept functions, as `register`'s are.
- **Classes** (script and engine alike) are userdata sharing one metatable (`__index`: defaults, then constants; `__newindex`: a member and a default; `__call`: construct). Each class's environment table, unreachable from scripts, holds its members (what objects see), defaults (`Class.name`), engine property getters and setters, constants, base, engine type (the engine class its objects are accepted as), and its objects' metatable. Deriving copies the base's tables at that moment, without `__init` and `__finalize`, and takes its engine type.
- **Script objects** are userdata holding `__ok` and their engine part's id, with their own fields in their environment table and their class's metatable (`__index` and `__newindex` as closures over the class's tables; `__gc`; the 12 operators, one shared closure each so `__eq`, `__lt` and `__le` apply across classes). `class` finds the caller's local `this` with `lua_getlocal` (the C API, not the debug library, which isn't opened).
- **Engine classes** register methods (a member and a default implementation, or none: `pure virtual function called`), properties (readable, optionally writable), integer constants, operators (methods named as metamethods), constructors (a parameter count and an argument-match score) and an optional engine base registered before, whose members they copy and whose methods accept their objects. Engine parts are Rust values (`Box<dyn Any>`) the state owns, identified by `EnginePart`, which their constructor receives; methods and properties get the part downcast to the type they were registered with, and refuse an object of another engine type or one without its part. Later specs add classes and members through `EngineClass`, nothing else.
- **Engine objects** (added for script API B): objects the engine makes, not scripts (`Lua::new_engine_object`: holding their part from the start, kept in the registry for the state's lifetime), and functions and methods returning them (`Lua::register_object_function`, `EngineClass::object_method`): the Rust function returns an engine part, which C turns into the object holding it (the engine object, else the script object), else nil. A global function making new script-owned objects (`create_ini_file`, added for script API F) is `Lua::register_with_objects`, whose `ObjectMaker` makes them as `Objects::new_object` does.
- **Objects in engine members.** An engine class registered `constructible` is constructed by scripts calling it (`vector()`): Rust picks the constructor taking as many arguments with the best score, or raises; the class's `script_construct` makes the part and returns it as an `Object`, which C pushes as a new object of the class (the `adopt` hook names its engine class). Members registered `…_with_objects` get `Objects`: the parts of object arguments as copies, or `Operand::This` for the storage the member has borrowed (the object itself, or a reference to it), so aliasing follows the member's own order; and objects as results: the object itself, a new object for a new part, or a reference object sharing the object's storage (`Rc`), which keeps it alive (our choice where the specs leave its use after collection unestablished).
- **Engine calls** (`Lua::dispatch`, spec 5): the script object from a weak table keyed by engine part, the method among its class's members; the engine's own member means not overridden, and the engine class's default implementation runs in Rust; otherwise a protected call without a handler. `Conversion` says what becomes of the result: nothing, the value, or an integer (Lua's number conversion, rounded as `luaconf.h` converts). A failure is `OverrideFailure`: the log line (none for `cannot resume dead coroutine`) and the fatal error `LUA error: <message>`; `Scripts::dispatch` stops the state on it, as the loader's fatal error does.
- Our choices where the spec has the outcome unestablished: deriving from a value that isn't a class raises `the base of class 'N' is not a class`; deriving again copies again and replaces the base; an engine method or property on another class's object or on one without its engine part raises (our wording); `super` constructing again replaces the engine part; the script object owns its engine part, released after its `__finalize` chain; errors in `__finalize` are discarded; operator methods get the operands as Lua passes them; deriving from a script base also takes its engine properties, constants and engine type; `__ok` is false only for an object of a class with a base whose engine part isn't constructed; a dispatched method the class doesn't have fails as a call of nil. Calling an engine class from a script fails (it has no `__init`, 2.1); constructing engine objects from scripts belongs to the specs of the classes concerned.
- Review gaps (#897) read the simplest way, marked `TODO(#897)` in the tests: classes and script objects are userdata to `type` (gap 3); `tostring` of an object without `__tostring` is that operator's missing error, as 7.2 reads (gap 3); under `-_g`, `class` is nil in namespaced scripts like any global (gap 4). The cast-failure handler's log line (gap 2) awaits the first conversion that can fail; the dispatched names passed as parameters (gap 1) need nothing here.
- Tests: `selftest::classes`, a check per section on every target (natively one test each, `tests::classes`), with test engine classes; `tests/gog_classes.rs` (with game data) scans the Russian edition's 439 scripts for the spec's counts (380 declarations of 355 names in 190 scripts, 286 with a base; 380 engine base calls in 86 pairs, 22 script base calls), loads every script with a Lua name over test engine classes named after the 33 engine bases, and finds every declaration of the scripts that ran to their end as a class, with its own `__init`, each of the 255 reaching an engine base calling `super` with a listed constructor's argument count, and every base call's default.

## The object factory

`object_factory`, docs/behavior/script-api-class-ids-and-the-object-factory.md (script API C, #199): class ids, the factory scripts register classes in, `clsid`, and creating objects by class id.

- **Where it runs.** The entries are Rust (`ObjectFactory`: id, class-id name, and the engine's sides or a script entry's form and slot), sorted on use, so numbers and lookups are Rust's (`number`, `entry_for`; ids are 64-bit, beyond Lua's exact numbers). The class objects of script entries, the factory object and `register` are Lua (`object_factory.lua`, a kept chunk like the loader's), with what it needs of the class system as C tools (`csrc/volya_class.c`: an object of a class without `__init`, constructing an engine object, taking an engine part over, releasing it); names resolve through the loader (`resolve` in `loader.lua`: the namespace loaded, then raw fields). `Scripts::new` registers the engine class `object_factory` (no constructor; `register` set as its member from Lua) and installs the chunk; the factory itself is made on first use with the engine's 134 entries.
- **Startup.** `Scripts::call_class_registrators(&Common)`, after `load_globals`: each registrator that resolves to a function is called with the factory object, a script error fatal (`LUA error: …`, the state stopped); then `clsid` is registered as an engine class whose constants are the entries' positions. Startup as a whole, the `[common] script` list and the rebuild are the entry points' (below).
- **Creation.** `create_client_object(id)` and `create_server_object(system, section)` give `Created`: the class id asked for and either an engine entry's kind for the caller to make (`O_ACTOR`'s by `GameTypeKind`) or the engine part of the script object a script entry's class made, which the engine then holds (the C tools keep the object alive) until `release_object`. A missing side, a script error, a result that isn't an object (`cannot cast lua value to <its class's engine type>`, our choice of name) or one without an engine part (our wording) is fatal and stops the state. The simulation's objects are created through it (Simulation objects, In the app).
- Our choices where the spec is silent: `register` raises `object_factory:register: no form of it takes these arguments` when the receiver isn't the factory object or the arguments aren't 3 or 4 strings; an id past the last entry (undefined in the original) is fatal; a class-id name that isn't UTF-8 becomes its Windows-1251 text as a `clsid` constant, one with a NUL byte none. The 26 entries of a dedicated server aren't made.
- Review gaps (#935) read the simplest way, marked `TODO(#935)`: an engine client class (48 of the 52 shipped) is constructed by its constructor for the call's arguments, none, and that object's engine part is the client object (gap 1); gaps 2 and 3 need nothing here (the factory object is always passed; a rebuild is a new state).
- Tests: `selftest::object_factory`, a check per section on every target (natively one test each, `tests::object_factory`), with registrators and test engine classes of our own; `tests/gog_object_factory.rs` (with game data) scans the Russian edition's scripts for their `clsid` reads (26 scripts, 106 names, the 6 the table lacks with their readers, 88 names unread), runs startup's registrators over test engine classes (stand-ins for spec B's `editor()` and the namespace `game`) and finds the 54 registrations (51 four-argument, 3 three-argument), 188 entries of distinct ids and names, every `clsid` constant at its position and 5.3's values, and creates the objects of the 48 engine client classes and the 51 server classes.

## Engine services

`services`, docs/behavior/script-api-engine-services.md (script API B, #198): the console and render device objects, the global functions of its section 4 and the classes `DLL_Pure`, `ISheduled`, `IRenderable`, `ICollidable`, `IRender_Visual`, `CKinematicsAnimated`, `CBlend`; `prefetch` is the loader's.

The app feeds the device's frames and New Games' precache phase, loading phase and game type (`crate::scripts` of `volya-engine`); TODO(#941): the app's own console, the console window, the pause, the camera and device resets.
- `Scripts::register_engine_services` registers everything before `_G` loads and makes the single console and device objects; `Scripts::new_visual` makes a visual for scripts (an `IRender_Visual`, and with motion sets its `CKinematicsAnimated`).
- **Fatal errors** (CL 3.8): the report goes to the console's log and the state stops as the loader's fatal error does; every later call fails.
- **Stand-ins**: the vector fields are new tables `{x, y, z}` (#942); `PlayCycle` records the playbacks it starts (`KinematicsAnimated::blends`), which nothing plays (#943); `xrRender_test_r2_hw()` is false, as Volya Engine has no dynamic renderer (#385).

## Value types

`values`, docs/behavior/script-api-value-types-and-math.md (script API E, #202): `vector`, `matrix`, `Frect`, `Fbox`, `RPoint`, `fcolor`, `color`, `noise`, `duality`, `flags32`, `flags16` as engine classes, and `bit_and`, `bit_or`, `bit_xor`, `bit_not`, registered by `Scripts::new` after the class system, before `_G`.

- **Arithmetic** (spec 2.5): every formula in the spec's order of operations. `Sse` is an f32 in the SSE unit: IEEE single precision with flush-to-zero and denormals-are-zero (believed in effect; comparisons too). `X` is the x87 unit at 24-bit precision with the wider exponent range: each operation in f64, rounded once to a 24-bit significand (exact, as 53 ≥ 2 × 24 + 2), stored as f32 with one more rounding; sine, cosine and arctangent are f64's (the processor's extended results are established only up to them), from the C library natively and Rust's in wasm, which may differ in the last bit.
- **Conversions**: `number` arguments to f32 by one rounding (overflow to infinity); flags arguments truncated through 64 bits (`flags32`, `fcolor:set(number)`) or 32 bits (`flags16`), NaN and out of range 0; the bit functions truncate as SSE2 does (out of range −2³¹). Properties take Lua's number conversion of what is assigned (`libc::string_number` for strings).
- **Results** (2.3): s itself as the same Lua value, reference objects for the flags and colour methods, numbers, booleans or nothing. Vector-valued properties read as new vectors and assign by copy. `crossproduct` and `matrix:mul(a, b)` read an argument that is s after each stored component (2.6); the other methods copy their arguments first, which the spec shows is the same.
- Our choices where the spec has the outcome unestablished or depending on A: a call no overload matches, a non-vector assigned to a vector-valued property, reading or assigning `Frect` `lt` and `rb`, `matrix:getHPB` (numbers or nils) and `mk_xform` (no quaternion exists) raise (our wording); `color()`, `noise()` and `duality()` are zeros; `max` with a NaN gives the second operand, as `min` does (its test is disputed in review); `getP` with a NaN y gives −π/2.
- Review gaps (#938) read the simplest way, marked `TODO(#938)`: the flags methods without a check of their own follow the table (gap 1); a vector read from a property is owned by the script side and collected like a constructed one (gap 2).
- Tests: `selftest::values`, a check per section on every target (natively `tests::values`), recomputing every formula bit for bit in plain f32 over a fixed case and pseudo-random ones of mixed magnitudes (inputs where the orders of operations show), plus the worked examples; `tests/gog_values.rs` (with game data) recomputes the 250 loadable scripts (docs/behavior/script-loading.md 3: 893 and 195 root files of the `gamedata.db*` tree and the two binaries, 132 reached directly), holds them to section 10's counts, and uses the classes through the loader's state.

## Configuration and files

`files`, docs/behavior/script-api-configuration-and-files.md (script API F, #203): `ini_file` and its readers, `system_ini`, `game_ini`, `create_ini_file`, `token`, `token_list`, `rtoken_list`, `getFS()` with `FS`, `fs_file`, `FS_file_list`, `FS_file_list_ex`, `FS_item`, `command_line`, `user_name`.

- **State.** `FileSystem`, shared as `Rc<RefCell<_>>`: the path aliases (`append_path` adds to them), the index (`FileIndex`), the engine's `system.ltx` and `game.ltx` (`Rc<Config>`, one engine object each), the command line, the user name and the local time zone (`LocalTime`, UTC unless the platform gives its own). `Scripts::register_configuration_and_files` registers everything before `_G` loads; fatal errors are reported to the services' console and stop the state as B's do. The app registers it over the archive tree; TODO(#1003): the loose folders, the local time zone and the disk changes from the platform.
- **The index** is a view, not a copy (memory.md rule 3): the archive tree the `Trees` lend, looked up and listed through `Vfs` (`read_dir` for sizes and folders), under an overlay by full path (lowercase, `\` between folders, a folder's ending in `\`) of the loose files the platform lists (`set_loose_folder`: the saved-games folder and the other folders of `$app_data_root$`, with their sizes and times, read through `LooseFiles`) and of what scripts changed (a removed entry, a renamed one with where its bytes are). One-path members take the path as given, so a path with an upper-case letter or `/` is not found. Configurations load with `volya_engine_core::config` over the index (`IndexVfs`), so a file deleted from the index is a missing file.
- **Writing.** The index changes at once; disk changes are kept in order for the platform (`take_disk_changes`: delete, rename, write, remove folder, by full path), only for loose files: deleting or renaming an archive member changes its entry alone, as spec 5.4 has for archive members. On the web the platform applies them in Volya Engine's OPFS namespace (`savedgames/`, `logs/`, `screenshots/`), never to the imported game files. `file_copy` writes the new file without indexing it, `dir_delete` leaves the folders' entries (5.4 removes them from the disk only), `file_list_open_ex` doesn't re-read the disk (the index's loose files are what the platform last listed), and `create_ini_file` writes nothing.
- **Platform values.** `command_line()` is empty (Volya Engine has no command line) unless the engine sets one; `user_name()` is `player`, the log file's fixed user name (#646).
- Our choices where the spec has the outcome unestablished or believed: believed faults and crashes (`r_bool` of no value, a list holding no list, `FS_file_list_ex:GetAt` out of range, the one-argument `w_open`) are fatal errors (our wording); `FS_file_list:GetAt` out of range raises `invalid vector<T> subscript`; `token_list:remove` of an absent name raises, `id` and `name` of an absent entry give 0 and nil; `token.name` holds a copy; `fs_file` is a copy of the entry; an archive member's `vfs`, `ptr` and `modif` are 0 and its sizes the file's; `get_path` and `append_path` return nil, `w_open`, `w_close` raise; a section's missing-key and missing-section reports are failed checks whose expression is `fatal error`, LTX load errors fatal messages, an undefined alias's expression `alias defined`.
