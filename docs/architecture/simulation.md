# Simulation and the level

The level (`volya-engine::level::LevelScreen`) owns what runs while a game is played; the systems themselves live in `volya-engine-core`. Everything here advances only in the app's updates, so it stands still while the game is paused or the page hidden. Drawing: [rendering.md](rendering.md); sound: [audio.md](audio.md).

## Offline simulation

`volya-engine-core::simulation`, docs/behavior/offline-simulation.md.

- Every object of a game is kept as its full record (`ObjectRecord`, docs/formats/sav.md 7; the largest kinds boxed), from `all.spawn` at a New Game or a save's records on load, in a list indexed by id and changed in place (location, position, smart terrain, client data), so a save writes each record as it stands. What isn't saved (online state, travel, smart-terrain looks) sits beside it.
- It holds the whole game graph (the level points read on demand, not kept), the patrol paths, and the current level's navigation: `level.ai`'s positions (streamed, 5 of each vertex's 21 bytes, held in the file cache under its path) and the cross table (`level.gct` streamed, its distinct cells and a 2-byte index per level vertex held in the file cache under its path). At a New Game the spawn file is held whole in the file cache and read in place under `st_creating_new_game`, where the registry, the graph and the character are made, and goes at the stage's end, before the navigation data.
- It is created under `st_server_connecting`; its first switch pass (all objects evaluated once while the loading image shows) runs under `st_loading_ai_objects`, once the current level's navigation is read there (`level.ai` and `level.gct` in the file cache, docs/architecture/memory.md), and the level's objects are taken from it. Every level update then runs one simulation update on the game clock with the actor at the player's feet: the switch pass over the current level's list, then up to `objects_per_update` scheduled stalkers and monsters.
- The smart terrains' scripts (acceptance, suitability, joining, tasks) are behind the `SmartTerrains` trait (`Simulation::set_scripts`); offline travel is `simulation::travel`. Without the scripts no object joins a smart terrain, so none travels (#244).
- The level loads the visuals of every object of its list that is online or whose engine predicate *on* can hold, not only those online at the start (`objects::level_objects`); an object switching changes its instance's placement ([rendering.md](rendering.md#objects)). An object arriving on the level by travel has no loaded visual and stays undrawn (#412).

## Information portions

`volya-engine-core::info_portions`, docs/behavior/info-portions.md.

- The declarations (the `[info_portions]` files with every portion's children, and the article, dialog and task ids they name) are read once, at the first New Game, and kept in `GameData` for the run; the spec leaves the original's moment open, and reading them then keeps them off the startup.
- Dialogs (`volya-engine-core::dialogs`, docs/formats/dialog-files.md) are registered with the declarations, each id with its file and position, and loaded by id: a `Dialogs` parses a file again where it first loads one of its dialogs and keeps each dialog it read, where the original keeps the 14 documents open for the run (the files do not change while it runs).
- The level holds the state: each holder's list by object id, in the shape `sav` 9 part 1 saves; the player character's articles and tasks; the messages sent to the server, which the next level update applies again (3.1). Interface windows give their portions through `LevelScreen::give_player`; an undeclared id is the level's fatal error, after the index's listing goes to the log.
- The script part (action functions, the `inventory_info`, `article_info` and `task_state` callbacks, the dialogue window's rebuild mark) comes out as events in order, for the script interface (#220) and the dialogue window (#993); the level drops those it has no receiver for.

## Collision and movement

- A level's collision mesh (`level.cform`, docs/formats/level-cform.md; `volya-engine-core::collision`) stays in memory while the level runs: vertices and triangles coded losslessly (#793: blocks of 32 consecutive vertices, each coordinate's bits as their difference in the floats' order from the block's least, in as many bits as the block's largest takes; blocks of 16 consecutive triangles, each vertex index as its difference from the block's least, likewise; every query reads back the file's bits, so it answers as with the file's arrays), each triangle's material and sector in 2 bytes, and a bounding-volume tree (`collision::bvh`, #396): its leaves are runs of up to 16 consecutive triangles of the file (whose order keeps neighbours together, so no index list; a run ends where a triangle would grow its box past 1 m and its surface past half again the two's), ordered by the Morton code of their boxes' centres and split at its highest differing bit; 16-byte nodes with boxes in 16-bit steps of the level's extent. `CollisionWorld::read` streams and indexes the file under `st_loading_cform` without holding the file or per-triangle temporaries (the tree is built in its own array). For `l01_escape` it holds 20.1 MB (vertices 5.7 against 8.4 as stored, triangles 4.3 against 11.0 at 8 bytes, materials and sectors 2.8, tree 7.3; 30.1 with #371's grid of 9.3), built in about 170 ms against 67; a body step costs about 19.5 µs (15 before #793's coding) against 35, a particle's ray at the start 1.1 µs against 15–21 and a 5–100 m ray 8.4 µs (6.6 before #793) against 17–22; in Chrome's wasm the 5–100 m ray 13.6 µs against 9.9 before #793 (native release, measured, `tests/collision.rs`, `tests/particle_collision.rs`, `tests/collision_rays.rs`; in Chrome's wasm `debug_rays_bench`). Over the 31 levels the trees take 100 MB against the grids' 122. The level shares it (`Arc`) with the sound rules and the particles.
- Box queries return the triangles whose boxes overlap, in ascending order. Rays (`ray_nearest`, `ray_any`) offer their caller's test the triangles in the order of a uniform grid over x and z (2 m cells, doubled while the grid would pass 2²² cells), walked cell by cell from the ray's start, each cell's triangles (those whose box overlaps it) in file order, each once; the tree leaves out those whose box, widened by 1 cm, the segment misses. The results are the grid's but where a caller's Möller–Trumbore test reports a hit on a triangle the segment does not pass, which rounding does for a ray lying in the triangle's plane or a sliver's (about 1 random ray in 100,000 on the levels, `tests/collision_rays.rs`). The grid is not stored: a triangle's cells come from its box.
- The collision world is freed with its level, as the original's (docs/architecture/memory.md, rule 4); the next level's world is made anew.
- The movement layer (`volya-engine-core::movement`, docs/behavior/player-movement.md) turns each frame's actions into the movement state and the desired acceleration, and runs the body at the fixed step from an accumulator of the display frame time; the camera follows the body's eye.
- Ladders (`volya-engine-core::climbing`, docs/behavior/climbing.md) are the level's `climable_object` records, taken after the first switch pass under `st_loading_ai_objects` (before the world is shared): each one's box lives in the collision world beside the triangles, and the player's shapes collide with its faces as twelve triangles under the same contact rules (only while in front of it, section 1.3). The movement layer runs the climbing states at each fixed step before the forces and sets the climbing flag after the frame's physics; every input path drives it through the ordinary move, look and jump actions, with no control of its own.
- The player's body is our own small solver, not a physics library: the body never rotates, so it is a point mass with contact constraints using the spec's parameters (error reduction, constraint-force mixing, friction, bounce), solved by projected Gauss–Seidel. Each fixed step has two halves (`collision::body`), so the movement computes its forces from the step's contacts: `PlayerBody::begin_step` (the contacts), then `PlayerBody::finish_step` (the forces, the solve, the move).
- Movable bodies meet the player's body in the physics world (below; docs/behavior/physics-contacts.md 5, 7), not in the movement's solver. The doors under the door scheme (`volya-engine-core::door`, `level_doors`) keep their leaves' boxes where their shells' bodies hold them (`BodyBox`, read after every frame's physics) for the crosshair's pick and the route planner; the scheme's motor reaches the leaf's hinge (waking its shell), and its closed test reads the hinge's angle. The player's shapes take the actor section's `material` at the spawn (`creatures\actor`; physics-contacts.md 5), for the level's contacts too. The scheme is Rust standing in for the shipped scripts (#875).

## Navigation

`volya-engine-core::navigation` plans tap-to-move's routes ([input.md](input.md), #805). It is our own addition, built from our movement and collision, not from the original's AI.

- Not over `level.ai`: the specs establish only its vertices' positions, not their links (offline-simulation.md 3), and an AI graph has no ladders, jumps or crawl spaces for the player's body anyway.
- A grid of 0.3 m columns probed from the collision world while a search runs and dropped when it ends, so nothing is built at load and nothing is kept. One box query per column (0.56 m square, the search's vertical span) gives its floors (the front sides of solid walkable triangles, normal y ≥ 0.707, met by the column's centre line) and each floor's room: the tallest posture whose box (standing 1.8 m, crouch 1.5, low crouch 1.2, `ph_box*_size`) fits above 0.5 m over it, the ladders' boxes counting as walls. The spacing is under the box's width, so a wall between two columns meets one of their boxes.
- Edges, costed by time at the posture's speed (`walk_accel`, `run_coef`, `crouch_coef`): walking, crouching or crawling to a neighbour (8 ways, diagonals not cutting corners) within a 0.5 m step; walking off an edge down to 2.5 m (half the fall `ph_crash_speed_min` would need); a running jump up onto a ledge to 0.83 m (0.9 × the apex, `jump_speed²/2g` = 0.92 m) and across a gap or over an obstacle lower than 0.64 m (0.7 × the apex), within 1.8 m; and up or down a ladder, between the floor in front of its foot and the floor beyond its top. Measured in the movement on synthetic worlds: 0.7 m ledges are walked up, 0.9 m ones jumped onto from a run or from standing, 1.8 m gaps jumped.
- A* with the straight distance at running speed as heuristic, weighted 1.3; the target taken 0.3 m back toward the start, so a tap on a wall goes to its near foot. It ends at the first floor within 0.45 m of the target, or after 20,000 expansions or 8,000 without coming nearer (a roof nothing leads to); then the route goes to the nearest floor reached if it lies within 1.5 m of the target and takes at most twice the straight run's time plus 3 s (a tap high on a wall goes to its foot, not round to its far side), and otherwise there is none. The route's legs on foot at one posture are merged where the straight line between passes, and its ends are the feet and the tapped floor point.
- `Planning::run` expands it by parts, so a long search spreads over frames (tap-to-move gives it 600 expansions a frame).
- Cost on `l01_escape`, 70 targets 8–25 m around a point 1 m past the trader's locked door (native release, `tests/tap_routes.rs`, measured): median 13 ms, most 112 ms (8,404 expansions, 8,704 columns); the largest search holds 1.3 MB while it runs (native's 8-byte pointers), freed at its end. 59 targets the straight line can't reach are reached (the longest 30.9 m routes for 8 m straight); routes are followed to their ends by the movement on the level's collision world, `clmbl#8` climbed. The doors' leaves' boxes (the locked door's) are walls to the planner, as the ladders' boxes.

## Physics

- `volya-engine-core::physics::World` (docs/behavior/physics-world.md) holds what doesn't depend on the solver: the parameters fixed at creation, the frame's steps from an accumulator of the display frame time, `ph_frequency` and `ph_iterations`, the step's order, the per-step actions, the rest pass, the floor and freezing. Contacts and solving are behind `physics::Solver`; what the world steps behind `physics::Object` and `physics::Updater`.
- The solver is the public Open Dynamics Engine (decided by the user, 2026-11-27; the game ships an ODE build, physics-scope.md 1): the shipped library's base release, 0.5.0 (physics-library.md 1), core only, under its BSD option, compiled to wasm by Bazel in the shipped library's configuration, aiming at bit-exact parity with the game's build (the user's choice of 2026-11-27 over 0.16.6, whose floating-point order changed since 0.12); the game's changes to it (physics-library.md 3 – 6, and the arithmetic the black-box comparison established, physics-harness.md 2 – 5, physics-harness-2.md 5, physics-harness-3.md 8 and physics-harness-4.md 9) are a patch Bazel applies, `third_party/ode/shipped-library.patch`, whose added functions keep the spec's names (`dWorldAddBody`, `dJointCreateContactSpecial`, ...; the library-wide parameters are `dxGlobal`), and where the spec leaves a detail open, our choices, for the black-box comparison to check (#770): the auto-disable values when the library loads are 0 but the linear threshold, `dWorldCreate`'s (physics-harness.md 2); `dJointSetFixedQuaternionPos` sets three offset components; the load-time ERP and CFM are 6/11 and 1/880,000 rounded once; the special contact is the contact with its own rows function, which caps the normal row), and its floating-point environment (physics-library.md 7, 8) is reproduced: the build's `config.h` routes ODE's `sinf`, `cosf` and `atan2f` to `physics::ode::x87` (the x87 `fsin`, `fcos` and `fpatan` emulated: the value in double-double arithmetic, `fsin` and `fcos` reduced exactly by the instruction's 66-bit π, rounded to the extended format's 64 bits and then to the float; exact where the hardware's extended result is correctly rounded, believed; where the shipped library keeps the sine in the register, physics-harness-2.md 2.2 and 2.6, `fsin`'s extended result times or over a float, rounded once, through `volya_x87_sinf_times` and `volya_x87_sinf_over`) and `rand` to `physics::ode::msvc_rand` (the C run time's per-thread generator, starting at 1); `sqrtf` stays, as `fsqrt` at 24-bit precision is the correctly rounded float square root. NaN results are not made the x87's default NaN. Flush-to-zero and denormals-are-zero of the SSE arithmetic (physics-harness.md 7) are emulated in software on every target (wasm has no such mode; arm64's flush-to-zero detects tininess before rounding, x86's after, measured under Rosetta 2): in C++ ODE's `dReal` is `csrc/ode/include/ode/sse.h`'s single-precision class, whose arithmetic and comparisons read denormal operands as zeros of their sign and flush tiny results, the x87 functions and copies taking raw floats, and the operations physics-harness-3.md 8 names as the x87's (`dNormalize4`'s and the finite rotation's renormalisation, the angular speed without an axis, the hinge's half-angle sine, the slider's position, and physics-harness-4.md's getters' dots, hinge-2's sine and `dRFrom2Axes`'s lengths) computed by `sse.h`'s `dX87` helpers: rounded to 24 bits with the wider exponent, never flushed, rounded again to the float's grid when stored (a second patch, `third_party/ode/sse-arithmetic.patch`, makes the math macros give it; `M_PI` and `M_SQRT1_2` are ODE's single-precision ones, as with the shipped library's compiler). Each operation tests its operands and result off its dependency chain and takes an out-of-line path only for denormals; still the harness's stepped scenarios take about 3 – 3.6 times as long natively (joints 2.6 → 9.4 ms, contacts 5.3 → 15.2 ms, the falling-body check 7.2 → 22.9 µs; native release, measured). `dInfinity` is IEEE +∞ (inferred from the spec's +∞ set by a load-time initialiser, as MSVC's `HUGE_VALF` would be; 0.5.0's own Windows configuration uses `FLT_MAX`; the black-box comparison with the shipped library settles it, #770). Its BSD notices ship in the app's licence notices; ODE's names are not used to promote the app. Considered: ODE 0.16.6 with patches, our own solver, Rapier. It sits behind `physics::Solver` as `physics::ode::OdeSolver`, a minimal FFI over the functions the world uses; its build is in build.md (Build scripts). The groups of physics-world.md 4.2 are the library's worlds, which the shipped library makes plain lists (physics-library.md 3.1, believed there to be the game's use): each object's group lists its own bodies; a contact between two objects (`OdeSolver::add_contacts`, under 4.2's limits) moves one merged group's bodies and contacts into the other's list for the rest of the step; each merged group of an active object is stepped once, by the exact stepper when marked for it (a group's own request, joined by those of the groups merged into it, physics-shells.md 3.5, physics-contacts.md 1.6) with fewer than 30 joints, else by QuickStep, with the world's parameters set library-wide (with no world, as the game sets them); a group's id is never reused; then every group lists its own bodies again, and the step's contacts are detached and the joint group emptied (emptying leaves joints without a world attached, physics-library.md 6).
- The level's world (`volya-engine::level_physics`) is made under `st_client_spawning` with the console's `ph_frequency` step and the iteration count `ph_iterations` last passed (the library's 20 before it first runs), its floor 30 m below the collision mesh's box; it steps on the movement's display frame time (0 on paused frames), its steps run with the movement's in the player's update, each after the movement step it meets, those left over after them (`LevelPhysics::steps`, a `movement::StepHook`; our order: physics-world.md 2.1 puts the world after every object's update, but the player's body is one of its objects, which the movement steps), and follows the two commands before each frame. The player's body stays the movement's own solver, and in the world it is an object of its own (`physics::ode::character::OdeCharacter`, class 0x4 | 0x10, its four shapes, physics-contacts.md 5): a stand-in body of the player's mass that never turns, without gravity, placed at each world step where the movement step began, at the velocity it left; its contacts with movable bodies, under the player's rules for them (trader-door.md 3.3; the outer sphere only sets "blocked"; `collision::body::movable_contact`), join the stand-in and the movable body, so the movable body takes the reaction, and the change the solving made to the stand-in's velocity goes back to the player's body, which it moves for the step too (`PlayerBody::react`), with "blocked" for the next step, the touch flag and the count of contacts made, for the step-assistance decision (docs/behavior/step-assistance-movable-bodies.md; `collision::body::Reaction`); its contacts take the step replacement as the level's do. Its level contacts stay the movement's, and so do the ground and obstacle the drive and the decision read. The decision follows the spec's order: each movement step's contacts under the previous step's decision, then the probe (the level's mesh only; on with no stored acceleration) and the decision with the recorded position, starting at zeros (unestablished; the case consistent with the original's player staying on the floor at the trader's door), and the previous drive; as the world steps after the movement step, its touch flag reaches the decision a step late (#1041). The contacts (`physics::contacts`, `physics::ode::collide`, physics-contacts.md) follow the spec: each active object's collision pass, in their order, against the objects of the index (active or added and not stepped, by their boxes' overlap: the index's own test is open, #957) the class filter passes, then the level's mesh unless it ignores static; box and sphere pairs by the library's `dCollide`, a cylinder's with boxes and spheres by the game's own colliders as 4.3 states them, in their stated arithmetic (`physics::contacts::cylinder`; the cylinder's rotation is the least turn from +y to its axis, the game's is open, #1054), so the player's torso cylinder meets the movable bodies too; two cylinders get none (open, #957); the properties of the two materials, the callbacks, crossed-triangle records and their infinite friction, the liquid's damping; a pair's kept contact merges the groups and wakes a resting object, appended to the end of the active objects (as every activation is, our reading). The level contacts of spheres, boxes and cylinders, crossings and push-outs are section 3's (their open parts #957: a cylinder's ordinary contacts and closer overlap test are ours, its rim points as 4.3's box face gives them); motion rays are not cast (only thrown missiles get the mark). Its shells (`volya-engine-core::physics::shell`, docs/behavior/physics-shells.md) are built under `st_client_spawning` with the doors, for the physics objects, hanging lamps and skeleton objects online at the start (#949 for later ones): a shell is first a description (elements with their model-space frames, geometries and mass parts, joints, fixed elements, the solver request and collision marks) built from the record and the model's header, bones and user data (each model file read once, its meshes not), then activated in a group of its own (`physics::ode::shell::OdeShell`): bodies at their mass centres with ODE's mass functions, shapeless elements fixed, then the hinges (the other joint kinds wait for PH-7, #750), then the fixed bones, switched off when the record asks (not stepped until woken). Its geometries, collision class and the level state of each geometry are kept with it, its boxes beside it for the doors; the description is dropped. Objects are still drawn at their records' transforms (#948). Each element's divisors and drags act on its body before its group is solved (`Grouped::before_solve`); a woken shell does not rest again before PH-5 (#946). On `l01_escape` 197 shells, 2 awake at the start (buckets: a body of three cylinders and a handle, a box on a hinge; they fall onto the floor and the bodies rest there, one handle keeps bouncing off its hinge's stop, #1060), take 332 KB of the engine's heap and 92 KB of the library's, and a step with them costs about 0.03 ms; a step with the player's body pushing the locked door 0.04 ms (native release, measured, `crates/volya-engine/tests/shells.rs`, `door_contacts.rs`). Its `Physics`, `collider` and `solver` timers feed the statistics overlay through `volya-engine-core::perf_counter`, the platform's performance counter (the worker's `performance.now()`).

## The player character

- The character's state (`volya-engine-core::character`, docs/behavior/player-state.md: conditions, profile, inventory) is created with the level on New Game and kept by it.
- Each frame its thresholds are evaluated once into the movement's limits before the movement update, a started jump takes its power, and the conditions then advance by the game time the frame advanced.
- It holds what a save writes: it fills the player's record, builds its items' records and writes the client-data condition blocks.
- Its supplies take the ids after the player's registration in the offline simulation (offline-simulation.md 8.1); the bolt, which the player receives on coming online (player-state.md 3.2), takes the next id once every New Game record exists.

## Particles

The library (`volya-engine-formats::particles`, docs/formats/particles-xr.md) and the simulation (`volya-engine-core::particles`: effect instances, actions, regions, groups and the level's placed effects, `PlacedEffects`; docs/behavior/particle-lifecycle.md, particle-motion-actions.md, particle-appearance-actions.md, particle-groups.md, level-placed-effects.md, particle-collision.md).

- Arithmetic is `f32` per operation in the specs' order, also where a spec leaves the x87 precision believed or disputed; `sin`, `cos`, `exp`, `ln` and square roots are Rust's `f32` functions, so results may differ from the game's in the last bit. The specs' numeric vectors are unit tests, the library-wide facts game-data tests.
- Random numbers: the level holds the engine's one shared generator (`particles::random::Shared`, a handle its users clone), which the effects (`Random::uniform`, with the C runtime's generator of their own), the zones' lights, the detail objects and the occlusion draw from in the order they run (occlusion-tests.md 5); both start at 1 (our choice: the seed is unestablished, lifecycle 2.1), so a level is deterministic.
- A group's member effects report births and deaths as a list the group works through after the member's update, in their order (the children they make draw no random numbers, so this is the same as at once). A child naming no effect, or a looped birth or death child, is fatal (groups 2.3): the group stops there and the app ends the game with it. Destroying a group stops and drops everything (#319).
- Unestablished cases decided (#336): an action type id of 2 or above 31 fails the library's parse; unspecified types (0, 3, 5, 11, 13, 18, 20) are read with their sizes and do nothing; `follow` with no particle does nothing; the noise is NaN below t = −2³¹ too; a region of a kind above 10 is placed as stored; `level.ps_static` with a payload too short for its transform is an error; group chunk 7's members are read as chunk 4's without the birth and death names.
- The level reads `level.ps_static` and `particles.xr` (also without placed records: the zones and the weather use it) under `st_loading_ai_objects` (after the objects in the game; our placement), and makes, places, plays and updates each record's instance there; the first update after loading gets the rest of the load's time.
- The effects run on the level's world clock (the global clock), advanced by each level update's elapsed time. Each level update runs the scheduler's pass (level-placed-effects.md 5.2; every due instance, no budget: unestablished), then the drawing update (5.3) of every instance whose culling sphere meets the view of the latest frame's size.
- Every effect instance collides with the level's static collision mesh (P5): each ray walks the collision grid's cells from its start (`CollisionWorld::ray_nearest`), keeping the nearest front-side hit. Movable objects: #388.

## Zones and the weather's ambient effects

- Zones (`volya-engine-core::zones`; docs/behavior/zone-idle-effects.md, sound-anomalies.md) and the weather's ambient effects (weather-ambient-effects.md) are particle objects of the same `PlacedEffects` (each with its `Origin`), on the same world clock and generators, scheduled and drawn as the placed ones. Every effect the level's zone sections and the weather's ambient sets name has its shader and textures resolved with the level's.
- Artefacts (`volya-engine-core::artefacts`; docs/behavior/artefact-idle-effects.md; #408): the level's `ARTEFACT` and `SCRPTART` objects, their sections read with the level's objects under `st_client_spawning`, where those online are created with their models' bone 0 (at rest: objects play no motions, #234) and sphere; one coming online later is created then, one going offline destroyed. Their idle effects are particle objects of the same list (`Origin::Artefact`), their shaders and particle capacity counted with the zones'; their client and scheduled updates follow the zones' each frame, and their lights are records of the level's dynamic lights, given the artefacts' values after every frame's updates (`Artefacts::sync_lights`); none is on at the first level's start. Taking and releasing (P10 4.6, 4.7) exist for the inventory's pickups and drops (#255, #111); activation is #409; physics (the jumping impulse, sleeping) #278.
- The zone records of the level's objects (the class ids of the specs' behaviours: `Z_MBALD`, `Z_MINCER`, `Z_GALANT`, `Z_BFUZZ`, `Z_TORRID`, `Z_RADIO` and their scripted ids) are read under `st_client_spawning`, where those online are created (their idle effect started, their sounds the level's); one coming online later is created then.
- Each frame of the running level the zones' updates follow the effects' scheduler pass: fast-mode zones every frame, then the zones' scheduled pass. A state change arrives at once, the round trip being unestablished (#350).
- The idle light is a record of the level's dynamic lights, given the zone's values after every frame's updates (`Zones::sync_lights`), its colour from `lanims.xr`. The idle sounds play from the zones' per-frame start and stop events on the level's sounds.
- The ambient rule's effect object is made, stopped and removed through the `AmbientParticles` trait (`volya-engine-core::sound::ambient`, P11 3), a removed one deleted at the next frame's start; the wind (`weather::wind`) moves with the gust; the detail objects' sway reads it ([rendering.md](rendering.md#detail-objects)), the rain drops are not drawn.

## Dynamic lights

- Dynamic lights (docs/behavior/dynamic-lights.md) are light records in `volya-engine-core::lights::Lights`, one set per level (`LevelScreen::lights_mut()`). A source keeps its records for as long as it exists: `create()` gives a record with the spec's defaults (inactive, point, range 8, white), `destroy(id)` removes it; each frame it updates them with the setters (`set_position`, `set_direction`, `set_right`, `set_range`, `set_cone`, `set_colour` / `set_rgb`, `set_kind`, `set_active`, `set_shadow`, `set_texture`, `set_excluded`), which apply the spec's update thresholds (2.2), so setting an unchanged value every frame costs nothing. A record lights the frame while it is active and not excluded; how a source maps its own data onto its records is the source's spec. Hanging lamps, zones' idle lights and torches use the same records.
- `volya-engine::level_lights::LevelLights`, owned by `LevelScreen`, holds the records, the glows (`volya-engine-core::glows`) and the hanging lamps (docs/behavior/hanging-lamps.md). Their data is read in the loading stages: chunks 6 and 7 from the `level` file in the file cache under `st_loading_sectors_portals` (the glows' caption, console-diagnostics.md 2.4.1; the lights with them, our choice); `lanims.xr` (`volya-engine-formats::lanims`, docs/formats/lanims-xr.md) with the objects under `st_client_spawning` (our choice; when the game reads it is unestablished); the glows' textures and the light passes' attenuation textures with the level's under `st_loading_textures`.
- Each level update runs the lamps' frame on the global clock, sets the sun's records from the weather, and makes the frame's light passes and glow sprites from the latest frame's view; under the pause only the last two, with no time passing. The objects' sun-visibility ray goes along −d_B (dynamic-lights.md 11).
- A record's or a glow's sector matters only as whether it has one: whether the downward ray of level.md 9.1 from its position met a collision triangle or a portal (the portals' polygons are kept as triangles), since every sector is drawn ([rendering.md](rendering.md#lights)). The light choice's `level.hom` occlusion is not made (a superset).
- The settings `r1_dlights`, `r1_dlights_clip`, `r2_sun_lumscale` and `r1_glows_per_frame` are read from the console each frame.
- The glows' occlusion ray's static part tests every `level.cform` triangle, `materials\fake` too (glows.md 5.1). What the lamps and glows leave: #347.

## Torches

docs/behavior/torch.md (#360).

- `volya-engine-core::torch::Torch` holds a torch's logic over the level's records: spawn, switching, the owners that withhold its lights, placement, the player's aim smoothing, colour, the torch byte; night vision's request and its sound commands.
- `volya-engine::torch::PlayerTorches`, owned by `LevelScreen`, makes one of each torch item of the player character's inventory and follows the inventory each update: attached while it is the item in its own slot and `[actor] attachable_items` lists it; detached, it switches off; leaving the inventory, it leaves its owner and goes with its records (#362).
- `torch_definition` comes from the torch model's user data (chunk 17, its include resolved against `config\`), read with the objects under `st_client_spawning` with the player's model, whose attach bone is taken at rest (#362); the glow's shader is resolved with the level's. The first renderer's keys are used. Only the models' skeletons are read (`model::skeleton`: chunks 1, 13, 16), as parsing the player's whole model costs too much wasm heap.
- The `torch` and `night_vision` commands come from the keys bound to them, a gamepad's d-pad up and down, and the touch Torch and Night vision buttons (our design, #363); the engine tells the page what the two buttons show (`PlayerTorches::buttons`).
- The night-vision sounds are created with the level's sounds (a torch arriving later gets its own at its first command) and played 2D by the app from the commands an update leaves (`LevelScreen::take_torch_sounds`).
- Characters' torches spawn nowhere until scripts can switch them (#223). The owner known at spawn is the simplest reading of a disputed statement (#361).
